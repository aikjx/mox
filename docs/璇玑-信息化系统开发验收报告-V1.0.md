## 一、系统定位与建设目标

**璇玑**即本工作区的 **璇玑（Xuánjī）** 系统：以归一化信息关系图（IR）为单一事实源、对需求做全维度并行诊断与最优求解的企业级信息化系统。承接关图框架（12 节点类型 / 7 边类型 / 六维绑定 `REQ→FUN→BIZ→ALG→TSK→COD`），以前后两道强制闸门（⛨璇玑验证、治理）保障全链路可靠、可控、可审计。

**本轮建设目标**：在前序设计成果（全维流程图 / 璇玑子流程 / 机读流水线）之上，实装并验证所有架构功能，以信息化系统开发生命周期（需求分析→设计→实现→测试验证→交付）形式收口，确保工作区可编译、全测试通过。

## 六、测试分析验证

### 6.1 本轮修复的两个真实架构缺陷

**缺陷 A · 测试隔离（xuanji-system）**
- 现象：`store_persists_and_hashes_tokens` 并行下偶发 `Store::open().unwrap()` 恐慌。
- 根因：`temp_db()` 仅用 `process::id()` 作目录名 → 同二进制内所有测试线程共享同一 `xuanji.db`，并发 `remove_dir_all`/`Connection::open` 互相踩踏。
- 修复：改为进程内 `AtomicU64` 原子计数 + pid 的唯一目录，每次调用彻底隔离。
- 验证：`cargo test -p xuanji-system` → 实测 **82 项全过**（bin 55 + lib/main/集成 27；历史快照 22 已更新）。

**缺陷 B · 架构功能（primiflow-fusion）**
- 现象：`governance_g3_detects_duplicate_id` 失败——`rep.passed=false` 但 errors 不含 `"G3"`。
- 根因：`add_node` 用 `HashMap` 按 id 插入会静默覆盖同 id 节点，G3 基于 map keys 计数永远为 1，重复节点检测形同虚设。
- 修复：新增 `node_dups: HashSet<String>` 字段，`add_node` 检测到已存在 id 时记录；G3 合并 `node_dups` 判定。
- 验证：`cargo test -p primiflow-fusion` → 44 项全过（37+7）。
