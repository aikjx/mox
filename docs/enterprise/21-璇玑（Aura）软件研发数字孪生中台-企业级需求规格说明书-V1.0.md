### 1.2 建设背景（四大痛点 + 对应解法 = Aura）

传统企业软件研发存在**四大孪生断裂**（对应 Aura 的四个「补缺口」核心价值）：

| 痛点编号 | 传统研发痛点 | 现有工具的不足（DevOps / MBSE / 通用 KG） | Aura 的解法（对应 18 TOP-MASTER 的铁律） |
|----------|------------|------------------------------------------|------------------------------------------|
| P1 | **需求 ↔ 文档脱节**：需求变了文档不改，文档写了代码没实现。 | DevOps/MBSE 只管「交付过程」，不管「内容一致性」；通用 KG 是非结构化向量，不能做确定性绑定。 | **四归三连铁律**（18 §四.4）：需求 ↔ 架构 ↔ 业务流程 ↔ 文档四方同步更新 + 联盟责任/流程/代码三连。 |
| P2 | **业务流程 ↔ 架构割裂**：流程是流程、架构是架构，两张皮。 | MBSE 靠人工画 UML/SysML，不跟代码绑定；BPMN 只跑流程，不管代码结构。 | **10 大标准业务流程 × 六层金字塔双向锚点表**（18 §四 × 02 §0.1）：每个 BP 有 6 字段（输入/触发/动作/校验/输出/归档），并显式绑定 L6→L1 具体模块。 |
| P3 | **模块依赖混乱**：依赖循环、隐式依赖、改一处爆十处。 | 通用代码扫描只看到 import，看不到「业务语义依赖」。 | **八层图谱 L0~L7 · 14 节点族 × 19 边族**（18 §三）：确定性符号关系 + P9 判重闸门 + 11 探针（12 号验收报告）= 零孤儿节点、零循环依赖。 |
| P4 | **代码 ↔ 上层设计不一致**：架构图看着合理，真实代码是另一套。 | 传统平台没有「代码↔设计」的**双向实时绑定**；AIOps 只管运行时，不管研发时。 | **代码双向绑定 + xuanji_optimize 8 步无旁路闭环**（08 号文档）：代码变更自动同步图谱，⛨璇玑治理闸门 14 位专家校验器不允许代码与设计不一致。 |

基于此，Aura 依托「开发专家联盟 + 算法联盟」双联盟能力（= 三联盟中的开发+算法，加上产品联盟=完整三联盟模式），对标 AIS 企业级项目架构，**全维 Rust 自研底座（平台 services/ 15 Crate，见 02 §3.2）**，构建可落地、可扩展、可商用的自研研发孪生中台。

## 二、总体业务定位与边界定义（Aura 对外：我干什么 / 我不干什么）

### 2.1 核心定位（写死为一句话 + 两条副注）

**一句话核心定位**：
> **Aura = 以知识图谱为内核的研发资产数字孪生体系**。孪生对象 = **软件工程项目本身**（不是物理设备、不是硬件产线，这是与数字孪生赛道其它公司的核心差异，对外必须反复强调）；AI 算法作为**辅助能力**（做检索/推荐/挖掘的「提示器」），**不替代确定性工程关系**；**符号图谱（关图·八层图谱 L0~L7）= 唯一真相源**；向量语义层仅做检索与潜在关联推荐，**它的结果永远不能直接写入确定性关系**（必须经过算法联盟 C 的对账 Δ≤1e-6 校验 + 产品联盟 A 的确认才能落关图），**从根上杜绝大模型幻觉污染工程严谨性**。

两条副注（对外 FAQ 直接贴这两段）：
1. Aura **不是**工业 IoT 数字孪生平台：它不接 PLC/传感器、不做 3D 物理设备孪生可视化；它的「三维可视化」是关图节点的网络图+双璇玑十四维雷达图（= 研发资产的孪生，不是物理设备的孪生）。
2. Aura **不是**通用 AI 中台：它不做大模型训练/微调/推理托管；它的「AI 能力」是**算法联盟注册的 8 大确定性算法家族**（A1~A8，见§五），对外暴露 `POST /ai/engine/{process,analyze}` + 4 个算法端点 + 1 个图谱导出端点（AC-10 铁律，不删不改）。

3. **分层约束**：向量语义层（Embedding / 向量检索 / LLM 辅助）仅用于**模糊检索**与**潜在关联推荐**，其推荐结果 = 「建议边」，显示在 UI 待审核列表中，**绝对不得写入确定性 R1~R10 关系**。任何确定性关系写入 = 必须产品联盟 A 确认 + 算法联盟 C 对账 + 开发联盟 R 合入，且触发 P9 去重闸门。
4. **自检约束**：提供图谱校验引擎 = ⛨璇玑治理闸门 Verify 14 位专家（08 §五 Step 5），自动检测「孤立实体、断裂关系、矛盾依赖、循环依赖」四类缺陷，关图 P9 gate 棘轮基线 0 新增缺陷。

## 五、核心算法能力需求（Aura 对外 5 大算法 = 算法联盟适配）

> 本章是对外签约的「AI 能力清单」。实现层 = **严格复用 8 大算法家族（A1~A8）**，不新增第 9 家族（除非走 ADR 注册 + RACI 签 + 7×N 对账脚本）。权威链对齐表本章末尾 = 5 算法 ↔ A1~A8 映射矩阵，保证「对外 5 种能力」=「对内 8 种确定性算法的不同组合」，不分裂出两套算法口径。

### 5.1 Aura-Alg-01 · 文档解析算法（BP-01 需求接入核心）
| 条目 | 内容 |
|------|------|
| 对外功能描述 | 对非结构化 Word / Markdown / PDF 需求文档做**实体抽取**：识别需求条目（E1 REQ）、业务节点（E2 BIZ）、验收标准（挂到 REQ 属性）。降低人工录入成本，**抽取结果必须提供 UI 人工一键纠错按钮**，纠错结果 = 实时同步关图。 |
| 对外验收指标（可测） | ① 需求条目抽取 F1 ≥ 0.93；② 业务节点抽取 F1 ≥ 0.90；③ 人工纠错操作 ≤ 2 次/页即可纠正 95% 错误；④ 所有抽取节点通过 P9 去重 0 重复。 |
| 对外常见问题回答 | 「为什么不用通用 LLM 直接抽？」= 我们在内部确实用 Embedding 做召回，但最终写入关图的节点 = 必须通过 A5 激活扩散 + 六维绑定一致性校验的**确定性节点**；LLM 召回的候选 = 仅出现在人工审核列表，不直接写入关图。杜绝幻觉。 |
