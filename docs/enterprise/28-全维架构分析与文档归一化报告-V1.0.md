#### 2.1.3 新架构的设计意图（推断）

新架构遵循 **DDD（领域驱动设计）+ 模块化单体（Modular Monolith）** 模式：

- **core 层** = 领域模型 + 纯业务逻辑，无 I/O 依赖，可独立单元测试
- **svc 层** = 应用服务 + 基础设施适配（HTTP handler、DB repo、外部API client）
- **sdk 层** = 对外暴露的类型定义 + 客户端库，供其他域或外部系统引用
- **api 层**（规划中）= 域间契约定义（trait / interface / DTO），实现依赖倒置
- **svcapi 层**（规划中）= 服务间 API 绑定，可能用于 gRPC/REST 契约生成

这与开源最佳实践高度一致：
- `axum-harness`：agent-first modular monolith，ECS-style runtime composition
- `clean_axum_demo`：`domains/<feature>/api|domain|infra|dto` 结构
- Rust backend best practice：Application Layer → Domain Layer → Infrastructure Layer 依赖倒置

## 三、架构最优性诊断

### 3.1 新架构优势（做对了什么）

#### 3.1.1 DDD 分层方向正确

新架构的 `core → svc → sdk` 三层分离符合 DDD 与六边形架构最佳实践：

| 层 | 职责 | 依赖方向 | 可测试性 |
|----|------|---------|---------|
| core | 领域模型、纯业务逻辑、trait定义 | 无外部依赖 | ★★★★★ 纯函数单测 |
| svc | 应用服务、HTTP handler、DB repo、外部适配 | 依赖 core | ★★★☆ 集成测试 |
| sdk | 对外类型、客户端库 | 依赖 core 的类型 | ★★★★ 类型检查 |

这比旧架构的扁平15-crate模型有本质提升：旧架构中 `mox-expert`、`kg-hub` 等 crate 混合了领域逻辑与基础设施，难以独立测试和复用。

#### 3.1.2 域边界划分基本合理

8个域的划分对应清晰的业务能力边界：

| 域 | 业务能力 | 内聚性评价 |
|----|---------|-----------|
| kg | 知识图谱存储/算法/服务/流处理/融合 | ★★★★★ 核心域，最完整 |
| ai | AI意图/智能体/专家/流程编排 | ★★★★☆ 核心域 |
| flow | 算子/优化器/融合/桥接/WASM/PrimiFlow | ★★★★☆ 核心域 |
| data | 公式/归一化/标准/ETL/合规/目录 | ★★★★☆ 支撑域 |
| platform | 系统/IAM/元数据/编排/数据存储/企业服务 | ★★★☆☆ 横切域，职责偏多 |
| cloud | 云存储/卷/S3/文件器 | ★★★☆☆ 基础设施域 |
| voice | 语音DSP/ASR/意图/算子/桌面应用 | ★★☆☆☆ **疑似独立产品** |
| market | 模板市场 | ★★☆☆☆ 功能单薄，仅1 crate |

#### 3.1.3 Rust workspace 统一治理

Cargo.toml 使用 workspace 统一管理依赖版本，`[workspace.dependencies]` 集中声明 50+ 依赖，避免版本漂移。`default-members` 精确控制默认编译范围（排除需要额外工具链的 FFI 绑定）。这是企业级 Rust 项目的标准做法。

### 3.2 架构债与问题（哪里不够优）

#### 3.2.1 P0-1：voice 域边界存疑

voice 域包含 `mox-voice-desktop-app`（一个完整的桌面应用），与其他域的"库/服务"定位完全不同。语音能力（ASR/TTS/DSP）与知识图谱+AI编排的核心业务关联度低，桌面应用更是独立产品形态。

**判定**：voice 域应评估是否独立为单独仓库或 workspace，避免核心平台被语音产品的发布节奏、依赖（cpal/screenshots/enigo/global-hotkey 等桌面GUI库）拖累。

#### 3.2.2 P0-2：跨域依赖未治理

新架构未定义明确的跨域依赖规则。在 DDD 中，域间通信应通过 api 层的 trait/契约（依赖倒置），而非直接依赖其他域的 svc 实现。但当前：

- `api/` 层全部为空，域间 likely 通过直接 `use` 其他域的 svc 类型通信
- 没有 `Cargo.toml` 级别的依赖方向约束（如禁止 svc 层跨域直接依赖）
- 没有架构测试（arch test）验证依赖方向

**风险**：随着域数量增长，会形成"大泥球"（Big Ball of Mud），域边界名存实亡。

#### 3.2.3 P1-1：网关层职责过重

`mox-platform-gateway-svc` 作为唯一网关，可能承担了：HTTP 路由、鉴权、限流、聚合、WebSocket、OpenAPI 生成、子服务挂载等过多职责。旧架构中 `runtime` crate 就是类似的"上帝 crate"（聚合16个子服务 + Cordis5 插件内核 + RBAC + OpenAPI + 迁移引擎 + 治理）。

**建议**：网关应仅做路由转发 + 横切中间件（鉴权/限流/日志），业务聚合下沉到各域的 svc 层或专门的 BFF（Backend for Frontend）层。

#### 3.2.4 P1-2：可观测性未体系化

02-architecture.md §7.2 自承："指标：未采集"、"追踪：trace_id 注入（但跨crate链路未实现）"。新架构中未见统一的 observability crate 或标准化的日志/指标/追踪接入方式。

**企业级要求**：应建立 `mox-platform-observability`（或纳入 foundation），统一封装 tracing、prometheus metrics、opentelemetry tracing，所有 svc crate 强制接入。

#### 3.2.5 P1-3：market 域功能单薄

market 域仅 1 个 crate（`mox-market-template-svc`），与"算子商城/资产复用"的产品定位不匹配。旧架构中有 `template-market` + `business-catalog` 两个 crate 支撑商城能力，新架构中 market 域缺少 core 层（领域模型）和 sdk 层。

#### 3.2.6 P2-1：模块化单体→微服务的演进路径未规划

当前是模块化单体（所有 crate 编译为一个或少数几个二进制）。随着业务增长，需要明确：
- 哪些域可以独立部署（kg、ai 可能是高并发域）
- 域间通信从 in-process 调用迁移到 gRPC/REST 的预案
- 数据从共享 SQLite/PG 迁移到域专属数据库的边界

#### 3.3.2 AI Agent 架构对标

| 框架 | 架构模型 | 本项目对应 | 差距 |
|------|---------|-----------|------|
| **LangGraph** | Pregel 有向图，显式状态容器+检查点 | `mox-ai-flow-svc`（流程编排）+ `mox-ai-agent-svc` | 缺检查点/持久化状态机 |

| **Temporal** | 代码-first 持久化工作流，durable execution | `mox-flow-primiflow-svc` + `mox-flow-optimizer-core` | 缺持久化执行引擎，工作流重启后状态丢失 |
| **行业趋势** | 从框架复杂度回归软件工程优先，"手推Agent+Pydantic类型校验" | Rust 强类型系统天然适配 | ✅ 方向正确，Rust 的类型安全是优势 |

**关键洞察**：行业趋势（2026）是从 LangGraph/CrewAI 的"框架锁死"回归"软件工程优先"——用强类型、显式状态、可测试的代码构建 Agent，而非依赖框架的隐式魔法。本项目选择 Rust + DDD 分层，**方向完全正确**，但需要补齐：
1. 显式状态机 + 检查点（工作流持久化）
2. api 层强类型契约（域间 Agent 通信）
3. 可观测性（Agent 执行链路追踪）

#### 3.3.3 工作流引擎对标

| 引擎 | 范式 | 本项目对应 | 差距 |
|------|------|-----------|------|
| **Dagster** | 资产中心（Software-Defined Assets），声明式，自动血缘 | 关图（知识图谱）天然是资产模型 | 关图是元数据层，未与执行引擎深度联动 |
| **Airflow** | 任务中心，DAG 调度，Python 定义 | `mox-flow-optimizer-core`（CPM/RCPSP） | 调度器是算法库，非生产级调度服务 |
| **Temporal** | 代码-first，durable execution，自动重试 | 无对应 | **最大差距**：缺持久化工作流执行引擎 |
| **Prefect** | 现代 Python 工作流，混合执行模型 | 无对应 | — |

**判定**：本项目的工作流能力是"算法库级"（CPM关键路径、RCPSP资源约束），而非"生产级调度服务"。如果产品定位需要可靠的长时间运行工作流（如企业级研发流程自动化），需要引入或自研 durable execution 层。

#### 3.3.4 知识图谱平台对标（引自23号竞品报告，已校准）

| 产品 | 架构特点 | 本项目差距 |
|------|---------|-----------|
| Neo4j v5 | 原生属性图，Cypher/GQL，单机/集群 | ❌ 缺原生查询语言（Cypher兼容） |
| NebulaGraph v4 | 分布式，计算/存储分离，nGQL | ❌ 缺分布式分片存储 |
| ArangoDB v3.12 | 多模型（图+文档+键值），AQL | ⚠️ 关图是属性图，缺文档/键值模型 |
| TigerGraph v4 | 分布式深度图分析，GSQL | ❌ 缺分布式深度遍历 |
| Amazon Neptune | 云原生，PG+RDF双语，Bedrock GraphRAG | ⚠️ 缺云原生托管能力 |

**本项目独特优势**（无直接竞品）：
- 知识图谱 + AI 编排 + 研发数字孪生 + 三联盟治理的**复合态产品**
- 关图不仅是数据存储，更是"需求↔架构↔业务↔代码↔测试"全链路关联关系的**唯一事实基准**
- 八大算法家族（A1~A8）针对研发治理场景定制，非通用图算法
