# 模块化单体→微服务演进预案（MODULAR MONOLITH TO MICROSERVICES · ADR-16）

> **文档身份**：从当前「模块化单体（Modular Monolith）」演进到「微服务（Microservices）」的决策框架与执行预案。定义拆分触发条件、服务边界划分、拆分方法论、数据一致性策略、运维体系演进，确保在需要时可平滑、低风险地完成架构演进。
> **版本**：v1.0 ENT（2026-08-26 · 开发专家联盟）
> **权威链**：`18` TOP-MASTER > `02` 架构七视图 > `29` 跨域依赖规则 > **本文件(ADR-16)**
> **关联 ADR**：ADR-08(架构迁移)、ADR-09(跨域依赖)、ADR-15(voice独立化)

## §1 当前架构定位

### 1.1 为什么是模块化单体

| 维度 | 模块化单体优势 | 微服务劣势（当前阶段） |
|------|---------------|----------------------|
| **开发效率** | 一次构建、一次部署、IDE 全局跳转 | 多仓库/多服务联调复杂 |
| **事务一致性** | 本地事务，强一致 | 分布式事务（Saga/2PC），复杂度高 |
| **运维成本** | 一个进程，简单监控 | N 个服务，N 倍运维复杂度 |
| **团队规模** | <20 人高效协作 | 需要专职平台团队（>50 人） |
| **部署频率** | 统一发布，简单可控 | 独立部署但需服务发现/配置中心 |
| **调试** | 单进程断点调试 | 分布式链路追踪，调试困难 |

**结论**：当前阶段（团队 <20 人，业务快速迭代）模块化单体是最优选择。8 域 DDD 边界已为未来微服务拆分做好准备。

### 1.2 模块化单体的微服务就绪度

| 就绪条件 | 当前状态 | 说明 |
|----------|:--------:|------|
| 领域边界清晰 | ✅ | 8 域 DDD 划分，core/svc/sdk/api 四层 |
| 跨域依赖规则 | ✅ | ADR-09 5 条规则 + arch test 自动化 |
| API 契约先行 | ⚠️ | api 层目录已建，Phase 3 填充 |
| 数据隔离 | ⚠️ | 各域共享数据库，未按域分 schema |
| 可观测性 | ⚠️ | Phase 2 建设中（统一日志/指标/链路） |
| 配置管理 | ⚠️ | 环境变量，未引入配置中心 |
| 服务发现 | ❌ | 进程内调用，无需服务发现 |
| CI/CD | ⚠️ | 统一构建，未按服务独立发布 |

**就绪度评分**：6/10（领域边界和依赖规则已就绪，数据隔离和运维体系待建设）

## §2 微服务拆分触发条件

### 2.1 技术触发条件

| 条件 | 阈值 | 说明 |
|------|------|------|
| **构建时间过长** | `cargo build --release` > 15 分钟 | 单体构建成为开发瓶颈 |
| **部署耦合** | 一个域的变更需要全量回归测试 > 1 小时 | 独立部署需求强烈 |
| **扩展性瓶颈** | 某域需要独立扩缩容（如 AI 推理需要 GPU 节点） | 单体无法按域扩缩容 |
| **故障隔离** | 某域故障导致整个系统不可用 | 需要故障隔离（如 voice 不影响 kg） |
| **技术栈异构** | 某域需要不同语言/运行时（如 Python ML 服务） | 单体技术栈受限 |

### 2.2 组织触发条件

| 条件 | 阈值 | 说明 |
|------|------|------|
| **团队规模** | 开发团队 > 30 人 | Conway 定律：团队结构决定系统结构 |
| **团队自治** | 多个团队需要独立迭代/发布 | 独立团队需要独立服务 |
| **组织拆分** | 某业务线独立融资/独立公司 | 需要代码和部署完全独立 |

### 2.3 业务触发条件

| 条件 | 阈值 | 说明 |
|------|------|------|
| **SLA 差异化** | 某域需要 99.99% 可用性，其他域 99.9% | 独立 SLA 需要独立部署 |
| **合规隔离** | 某域数据需要独立合规审计（如金融/医疗） | 数据和部署物理隔离 |
| **第三方集成** | 某域需要对第三方开放 API，有独立的 API 管理需求 | 独立网关/计费/限流 |

### 2.4 拆分决策矩阵

当满足以下**任意 2 个条件**时，启动微服务拆分评估：
- 技术条件 ≥ 2 个
- 组织条件 ≥ 1 个
- 业务条件 ≥ 1 个

当满足**任意 3 个条件**时，必须启动拆分。

## §3 服务边界划分

### 3.1 按域拆分（推荐）

基于当前 8 域 DDD 划分，微服务边界与域边界一致：

| 微服务 | 包含 crate | 职责 | 拆分优先级 |
|--------|-----------|------|:----------:|
| **platform-service** | platform 域所有 crate | 网关/IAM/元数据/可观测性/企业能力 | 最后拆（底座） |
| **kg-service** | kg 域所有 crate | 图谱存储/查询/算法/融合 | P2 |
| **ai-service** | ai 域所有 crate | 专家系统/Agent/推理/模型适配 | P1（GPU 扩缩容需求） |
| **flow-service** | flow 域所有 crate | 工作流/算子/编排/优化 | P2 |
| **data-service** | data 域所有 crate | ETL/血缘/质量/数据服务 | P3 |
| **market-service** | market 域所有 crate | 需求/业务流程/模板市场 | P3 |
| **cloud-service** | cloud 域所有 crate | 存储适配/计算调度/多云 | P3 |
| **voice-service** | voice 域所有 crate | ASR/TTS/意图/桌面应用 | P1（已准独立，ADR-15） |

### 3.2 拆分顺序（Strangler Fig 模式）

```
Phase 0: 模块化单体（当前）
  └── 所有 8 域在一个进程中

Phase 1: 边缘域拆分（voice + ai）
  ├── voice-service（独立，ADR-15）
  ├── ai-service（GPU 扩缩容需求）
  └── 剩余 6 域在单体中

Phase 2: 核心域拆分（kg + flow）
  ├── kg-service（图谱核心，独立扩缩容）
  ├── flow-service（工作流引擎，独立部署）
  └── 剩余 4 域在单体中

Phase 3: 业务域拆分（data + market + cloud）
  ├── data-service
  ├── market-service
  ├── cloud-service
  └── platform 仍在单体中（底座）

Phase 4: 平台拆分（platform → 多个基础服务）
  ├── gateway-service
  ├── iam-service
  ├── meta-service
  ├── observability-service
  └── enterprise-service
```

### 3.3 不拆分的反模式

| 反模式 | 原因 | 正确做法 |
|--------|------|----------|
| ❌ 按技术层拆分（api-service / svc-service / db-service） | 分布式单体，每次变更涉及多个服务 | 按业务域拆分 |
| ❌ 拆得过细（每个 crate 一个服务） | 运维复杂度爆炸，网络开销大 | 按域聚合，8 个服务足够 |
| ❌ 共享数据库 | 数据耦合，无法独立演进 | 每服务独立数据库/schema |
| ❌ 同步调用链过长（A→B→C→D） | 级联故障，延迟高 | 异步事件驱动，CQRS |

## §4 拆分方法论

### 4.1 Strangler Fig（绞杀者模式）

1. **识别边界**：选择要拆分的域，确认其依赖关系（通过 arch test）
2. **创建 API 层**：为该域创建独立的 API 服务（Phase 3 已完成）
3. **路由切换**：网关将该域的请求路由到新服务（灰度）
4. **数据迁移**：将该域的数据从共享库迁移到独立库（双写→校验→切换）
5. **移除旧代码**：从单体中移除该域的代码
6. **验证**：全量回归测试 + 性能对比 + 故障演练

### 4.2 数据拆分策略

| 策略 | 适用场景 | 复杂度 | 一致性 |
|------|----------|:------:|:------:|
| **Schema 分离** | 同一数据库实例，不同 schema | 低 | 最终一致 |
| **数据库分离** | 独立数据库实例 | 中 | 最终一致 |
| **物理隔离** | 独立数据库服务器 | 高 | 最终一致 |

**推荐**：先 Schema 分离（低风险），再数据库分离（独立扩缩容）。

### 4.3 跨服务数据一致性

| 模式 | 适用场景 | 实现 |
|------|----------|------|
| **Saga 编排** | 长事务（如工作流执行） | 持久化工作流引擎（ADR-14） |
| **事件驱动** | 异步数据同步（如图谱变更通知 AI） | 事件总线（Redis Stream / Kafka） |
| **CQRS** | 读多写少，查询模型与写模型分离 | 物化视图 + 事件投影 |
| **API 组合** | 简单查询需要聚合多服务数据 | BFF 层聚合调用 |

### 4.4 服务间通信

| 通信方式 | 适用场景 | 技术选型 |
|----------|----------|----------|
| **同步 REST** | 简单请求/响应，用户等待 | axum + reqwest |
| **同步 gRPC** | 高性能内部调用，流式 | tonic |
| **异步事件** | 解耦、最终一致、高吞吐 | Redis Stream / Kafka |
| **WebSocket** | 实时双向通信（如语音流式） | tokio-tungstenite |

**原则**：优先异步事件，同步调用仅在用户等待的关键路径使用。

## §5 运维体系演进

### 5.1 基础设施

| 组件 | 模块化单体 | 微服务 | 技术选型 |
|------|:----------:|:------:|----------|
| **服务发现** | 不需要 | 必需 | Kubernetes Service / Consul |
| **配置中心** | 环境变量 | 必需 | Nacos / Apollo / etcd |
| **API 网关** | 进程内 | 独立 | Kong / APISIX / 自研 gateway |
| **链路追踪** | 进程内 | 跨进程 | OpenTelemetry + Jaeger |
| **指标监控** | 单进程 | 多服务聚合 | Prometheus + Grafana |
| **日志聚合** | 单进程 | 多服务聚合 | Loki / ELK |
| **CI/CD** | 单流水线 | 多流水线 | GitHub Actions / ArgoCD |
| **容器编排** | Docker Compose | Kubernetes | K8s |

### 5.2 部署策略

| 策略 | 描述 | 适用阶段 |
|------|------|----------|
| **蓝绿部署** | 新旧版本并行，流量切换 | 全阶段 |
| **金丝雀发布** | 小比例流量验证，逐步放大 | 微服务阶段 |
| **Feature Flag** | 功能开关，运行时切换 | 全阶段 |

### 5.3 故障隔离

| 机制 | 描述 | 实现 |
|------|------|------|
| **熔断器** | 下游故障时快速失败，避免级联 | `tower::balance` / `reqwest-middleware` |
| **限流** | 保护下游不被打垮 | 令牌桶 / 滑动窗口 |
| **舱壁隔离** | 线程池/连接池隔离，避免资源耗尽 | tokio 多运行时 / 连接池隔离 |
| **降级** | 非核心功能降级，保核心可用 | Feature Flag + 兜底响应 |

## §6 拆分成本与收益评估

### 6.1 成本估算

| 成本项 | 单次拆分（1个域） | 全量拆分（8域） |
|--------|:------------------:|:---------------:|
| 开发人力 | 2-3 人月 | 16-24 人月 |
| 运维基础设施 | 1 人月（搭建 K8s/监控） | 3-5 人月 |
| 数据迁移风险 | 中 | 高 |
| 性能回归风险 | 低（网络开销） | 中 |

### 6.2 收益估算

| 收益项 | 量化指标 |
|--------|----------|
| 独立部署 | 发布频率从 1 次/周 → 多次/天 |
| 独立扩缩容 | AI 服务 GPU 节点按需扩缩，成本降低 30% |
| 故障隔离 | 单域故障不影响全局，可用性从 99.9% → 99.95% |
| 团队自治 | 8 个团队独立迭代，交付效率提升 50% |
| 技术异构 | AI 域可用 Python，voice 域可用特殊音频库 |

### 6.3 投资回报（ROI）

- **拆分 1 个域（voice/ai）**：ROI > 1（6 个月回本）
- **拆分 4 个域（voice/ai/kg/flow）**：ROI > 1.5（12 个月回本）
- **全量拆分（8 域）**：ROI ≈ 1（24 个月回本，运维成本高）

**建议**：按需拆分，优先拆分 voice 和 ai（ROI 最高），其余域保持在单体中直到触发条件满足。

## §8 决策记录（ADR）

**决策 ID**：ADR-16
**日期**：2026-08-26
**决策**：当前保持模块化单体架构，不主动拆分微服务。当满足 §2 拆分触发条件时，按 §3 服务边界和 §4 方法论进行拆分。优先拆分 voice（ADR-15 已准独立）和 ai（GPU 扩缩容需求）。
**理由**：模块化单体在当前团队规模和业务阶段效率最高，8 域 DDD 边界已为未来拆分做好准备。微服务拆分是手段不是目的，按需拆分避免过早优化。
**关联**：ADR-09(跨域依赖)、ADR-14(持久化工作流)、ADR-15(voice独立化)
