## 2. 新增能力：`info-graph dedup`

以关图作为**能力指纹库**，对新需求做子图匹配。

```bash
info-graph dedup --graph graph.enterprise.json \
                 --spec docs/graph/requests/<新需求>.json [--fail-on-new]
```

判定规则（纯函数 `dedup_requirement`，可单测）：

| 判定 | 条件 | 语义 | 应采取的动作 |
|---|---|---|---|
| `reuse` | 候选能力节点**全部**存在 **且** 候选关系边零缺失 | 需求已被现有能力完整覆盖 | 直接编排，**不写新代码** |
| `incremental` | 部分能力存在（含"能力齐备但连接方式不同"） | 应在既有子图上扩展 | 局部扩展，避免重造系统 |
| `new` | 无任何对应能力 | 图中确实没有 | 人工确认确有必要，才允许立项 |

- `similarity = 命中能力节点数 / 候选能力节点总数`
- 输出结构化 JSON（供机器消费）+ 人类可读摘要（供评审）
- `--fail-on-new`：判定为 `new` 时 **exit 1**，CI 阻断

设计要点：**能力齐备但边不匹配 → 判 `incremental` 而非 `reuse`**。因为同一批能力用不同连接方式组合，本质是新的编排，需要显式扩展而不能声称"已存在"。

## 3. 修复的真实缺陷（4 项，均非假设、均有回归测试）

| # | 缺陷 | 影响 | 根因 | 修复 |
|---|---|---|---|---|
| D1 | **中文乱码** | 规格文件中的中文需求名输出为乱码，评审无法阅读 | `parse_str` 用 `byte as char`，把 UTF-8 多字节序列逐字节当作 Latin-1 码位 | 改为按原始字节累积、末尾统一 UTF-8 解码 |
| D2 | **`\uXXXX` 未实现** | 转义字符退化为字面量，emoji/补充平面字符损坏 | 未知转义分支吞掉 `u` 后留下 4 位十六进制文本 | 完整实现 `\uXXXX` 及 UTF-16 代理对解码 |
| D3 | **BOM 致静默空跑（最严重）** | `skeleton` 注入 **0 个 REQ 根**却返回 exit 0；`deviate` 随即"跳过"，门禁误判**通过** → **虚假合规** | `docs/graph/guantu.req.json` 带 UTF-8 BOM，手写解析器从 0 位遇 BOM 字节直接失败 | ① 解析器自动剥离 BOM；② `skeleton` 解析到 0 个需求根时 **exit 2 响亮失败** |
| D4 | **门禁在 Windows 上不可用 + 吞掉退出码** | ① 找不到 `info-graph.exe` 永远误判"未编译"；② 规格由仓库根移入 `docs/graph/` 后路径未跟随，`skeleton` panic 被吞，门禁继续以空图判"通过" | ① 未考虑 `.exe` 后缀；② `run()` 忽略 `returncode`；③ 规格路径硬编码在调用处 | ① `.exe` 优先解析；② `run(check=True)` 非零即失败并打印输出；③ 规格路径集中定义 + 启动断言存在 |

**核心教训已固化进代码注释与门禁文档**：*静默成功比响亮失败危险得多*。D3/D4 叠加的后果是门禁长期"绿灯"而实际什么都没校验。

## 4. 门禁强化（`tools/guantu_gate.py`）

在原有 5 步之上新增/强化：

- **step2.5 派生豁免（豁免沿血缘传递）**：若某节点的**全部**关联边对端都位于已豁免路径（如 `examples/out/` 下的生成 DDL），则该节点本身也是派生产物，不再要求溯源需求根。
  解决 `Data:DATA_R1S~R4S` 这类由 `CREATE TABLE` 解析产生、自身无文件路径因而逃过路径豁免的节点。本次豁免 5 个节点。
- **step5.5 棘轮（治理只允许单向收紧）**：问题消项或覆盖率提升时立即固化为新基线，已取得的治理成果**无法被后续提交悄悄回退**。
- **step6 P9 判重闸门**：对 `docs/graph/requests/*.json` 逐条判重，`new` 即阻断；目录不存在或为空则跳过，使能力可渐进启用。

新增新需求入口 `docs/graph/requests/`：含 `README.md`（规格格式、判定语义、查证与后续动作）与一份可运行示例 `REQ-2026-001-治理台指标看板.json`。

## 7. 后续建议（按价值排序）

1. **判重精度升级**：当前为节点/边**精确匹配**。可引入名称语义相似度（编辑距离 + 中文分词）与 `Business`/`Interface` 层匹配，让"命名不同但能力相同"的重复也能被识别。
2. **REQ 规格自动维护**：新需求判定为 `new` 并获批后，自动在 `guantu.req.json` 追加 REQ 根与绑定，减少手工编辑。
3. **接入 S1 需求接入阶段**：把 dedup 挂到 `xuanji-expert` 的 G0 归一化闸门之后，让判重在需求录入时即时反馈，而非等到 CI。
4. **扫描器增强**：`Interface`/`Function` 级节点需 AST 采集，届时判重可下沉到接口粒度，精度显著提升。
