# 可观测性体系设计文档（OBSERVABILITY ARCHITECTURE · ADR-12）

> **文档身份**：企业级可观测性体系总设计。定义日志/指标/链路三支柱统一架构，以及 `mox-platform-observability` foundation crate 的接口规范与集成方案。
> **版本**：v1.0 ENT（2026-08-26 · 开发专家联盟）
> **权威链**：`18` TOP-MASTER > `02` 架构七视图 > **本文件** > `mox-platform-observability` crate
> **关联 ADR**：ADR-08(架构迁移)、ADR-09(跨域依赖)、ADR-11(网关瘦身)、ADR-12(本文件)

---

## §1 设计目标与原则

### 1.1 核心目标

| 目标 | 验收标准 |
|------|----------|
| 统一采集：54+ crate 同一套 API | `cargo tree` 仅出现 tracing + mox-platform-observability |
| 三支柱贯通：trace_id 关联 Logs/Metrics/Traces | P99 慢请求可追溯完整 span 树 |
| 零侵入业务：core 层不依赖 observability | core 层 Cargo.toml 无 observability 依赖 |
| 生产级 SLO：SLI/SLO/错误预算/告警 | ≥7 个核心 SLO，预算耗尽自动告警 |
| OpenTelemetry 兼容：OTLP 输出 | 无需改代码切换 Prometheus/Jaeger/Loki |

### 1.2 设计原则

1. **Foundation 唯一入口**：tracing/otel/metrics 封装在 foundation 内，业务不直接依赖
2. **结构化优先**：所有日志 key-value，禁止自由文本
3. **采样可控**：错误 100%，正常按比例
4. **维度统一**：标准标签 domain/crate/layer/env/version
5. **性能零 overhead**：Release 禁用级别编译期消除，指标 overhead <1%

## §2 三支柱架构

### 2.1 整体架构

```
业务代码(54+ crate) → mox-platform-observability(foundation)
  ├── Logs API(tracing)
  ├── Metrics API(metrics)
  ├── Traces API(opentelemetry)
  └── 统一 Exporter: OTLP/stdout/file(feature flag)
       → Loki(Logs) + Prometheus(Metrics) + Jaeger(Traces) → Grafana
```

### 2.2 日志（Logs）

**选型**：`tracing` + `tracing-subscriber` + `tracing-appender`

| 级别 | 场景 | 生产默认 |
|------|------|:--------:|
| ERROR | 系统级错误，需人工介入 | 100% |
| WARN | 异常但可自动恢复 | 100% |
| INFO | 关键业务事件 | 100% |
| DEBUG | 调试信息 | 采样1% |
| TRACE | 最细粒度 | 禁用 |

```rust
// ✅ 结构化
info!(domain="kg", crate_name="mox-kg-hub-svc", operation="query_graph",
      node_count=1500, duration_ms=42, status="success", "图谱查询完成");
```

自动注入：timestamp, level, trace_id, span_id, env, version

### 2.3 指标（Metrics）

**选型**：`metrics` + `metrics-exporter-prometheus`

| 指标名 | 类型 | 标签 | SLO |
|--------|------|------|-----|
| http_requests_total | Counter | domain,route,method,status | — |
| http_request_duration_seconds | Histogram | domain,route,method | P99<500ms |
| graph_query_duration_seconds | Histogram | query_type,node_count | P95<200ms |
| workflow_execution_total | Counter | workflow_type,status | — |
| workflow_duration_seconds | Histogram | workflow_type | P95<5s |
| ai_inference_duration_seconds | Histogram | model,operation | P95<2s |
| errors_total | Counter | domain,crate,error_type | 错误率<0.1% |
| active_connections | Gauge | service | — |
| queue_depth | Gauge | queue_name | <1000 |

### 2.4 链路（Traces）

**选型**：`opentelemetry` + `tracing-opentelemetry`

- Span 命名：`<domain>.<operation>`（如 `kg.query_graph`）
- 埋点：HTTP(axum middleware自动)、DB(sqlx middleware)、图谱/AI(`#[instrument]`)、工作流(引擎自动)
- 采样：dev 100% / staging 50%+错误100% / prod 10%+错误100%+慢请求100%

## §3 `mox-platform-observability` Crate 设计

### 3.1 定位

- 层级：foundation
- 路径：`platform/foundation/mox-platform-observability/`
- 职责：封装 tracing/otel/metrics，提供统一初始化、宏、中间件

### 3.2 模块结构

```
src/
├── lib.rs, config.rs, init.rs
├── logs/{layer.rs, format.rs}
├── metrics/{registry.rs, macros.rs, middleware.rs}
├── traces/{propagator.rs, middleware.rs}
└── exporter/{otlp.rs, stdout.rs, file.rs}
```

### 3.3 核心 API

```rust
// 初始化
let config = ObservabilityConfig::from_env()?;
let _guard = init_observability(config)?;

// axum 中间件（一行注入日志+指标+链路）
let app = Router::new().route("/...", get(h)).layer(observability_layer());

// 指标宏
counter!("graph_queries_total", "domain"=>"kg");
histogram!("query_duration_seconds", dur.as_secs_f64(), "domain"=>"kg");
```

### 3.4 环境变量

| 变量 | 默认 | 描述 |
|------|------|------|
| OBSERVABILITY_ENV | dev | 运行环境 |
| OBSERVABILITY_LOG_LEVEL | info | 日志级别 |
| OBSERVABILITY_LOG_FORMAT | json | 日志格式 |
| OTEL_EXPORTER_OTLP_ENDPOINT | — | OTLP 收集器 |
| OTEL_TRACES_SAMPLER | parentbased_always_on | 采样器 |
| OTEL_SERVICE_NAME | infotopograph | 服务名 |
| METRICS_EXPORTER | prometheus | 指标导出 |

### 3.5 Feature Flags

| Feature | 默认 | 描述 |
|---------|:----:|------|
| stdout | ✅ | stdout 导出 |
| file | ❌ | 文件滚动 |
| otlp | ❌ | OTLP(生产) |
| prometheus | ✅ | Prometheus 指标 |
| json-log | ✅ | JSON 日志 |
| max_level_debug | ❌ | 编译期 DEBUG |

## §4 SLO / 错误预算 / 告警

### 4.1 核心 SLO

| ID | 服务 | SLI | 目标 | 错误预算(30天) |
|----|------|-----|------|----------------|
| SLO-01 | HTTP API | 可用性 | 99.9% | 43.2min |
| SLO-02 | HTTP API | 延迟P99 | <500ms | — |
| SLO-03 | 图谱查询 | 延迟P95 | <200ms | — |
| SLO-04 | 工作流 | 成功率 | 99.5% | 21.6min |
| SLO-05 | AI推理 | 延迟P95 | <2s | — |
| SLO-06 | 数据导入 | 完整性 | 100% | 0 |

### 4.2 错误预算策略

- >50%：正常发布
- 20%~50%：谨慎发布，额外 review
- <20%：冻结新功能，仅 bugfix
- 耗尽：强制冻结，全员修稳定性

### 4.3 告警路由

| 级别 | 触发 | 通知 | 响应 |
|------|------|------|------|
| P0 | 预算1h耗尽/系统不可用 | 电话+短信+飞书@all | 5min |
| P1 | 错误率>1%/P99超2倍 | 飞书@oncall | 15min |
| P2 | 错误率>0.1%/队列超阈值 | 飞书群 | 1h |
| P3 | 趋势异常/容量预警 | 邮件+机器人 | 下工作日 |

## §7 开源对标

| 维度 | 本方案 | 业界最佳 | 差距 |
|------|--------|---------|------|
| 日志 | tracing | tracing(Rust标准) | ✅对齐 |
| 指标 | metrics+prometheus | metrics/otel | ✅对齐 |
| 链路 | opentelemetry+tracing桥接 | opentelemetry(CNCF) | ✅对齐 |
| 导出 | OTLP | OTLP | ✅对齐 |
| 采样 | 尾部+错误100% | 尾部采样 | ✅对齐 |
| SLO | 自定义+Prometheus | Sloth/OpenSLO | ⚠️需引入OpenSLO |
| 告警 | 飞书+电话 | PagerDuty/Opsgenie | ⚠️国内飞书更合适 |
| 面板 | Grafana | Grafana | ✅对齐 |

**结论**：技术选型与业界100%对齐，差距在SLO管理工具链（建议引入OpenSLO）。
