## §2 V-04：Operator 抽象下沉（P0，最高优先级）

### 2.1 根因分析

`ai-agent-svc` 在 7 个文件中依赖 `flow-operator-core`，使用其 Operator trait、StateVector、ExecutionContext 等核心抽象。这些抽象是**跨域通用的算子模型**，不应属于 flow 域。

### 2.2 修复策略

**将 Operator 核心抽象从 `flow-operator-core` 下沉到 `mox-platform-operator-core`（platform 域）**

下沉内容（纯抽象，无 I/O）：
- `Operator` trait
- `StateVector` 类型
- `ExecutionContext` / `ExecutionResult`
- `OperatorMetadata`
- `OperatorError` 错误类型
- `SystemConfig`
- `TypeIdentifier` / `TypeCheck` trait
- `ResourceCost` / `ResourceUsage`
- `kernel` 模块（纯数学守恒律）

保留在 flow 域（flow 特定实现）：
- `engine.rs`（flow 引擎实现）
- `registry.rs`（flow 算子注册中心）
- `resource.rs`（flow 资源管理实现）
- `conservation.rs`（flow 守恒律实现）
- `category.rs`（flow 算子分类）
- `monad.rs`（flow 单子组合子）

### 2.3 执行步骤

1. **创建 `mox-platform-operator-core` crate**（platform/core/ 下）
2. 将上述纯抽象类型迁移到新 crate
3. `flow-operator-core` 依赖并重新导出 `mox-platform-operator-core`（向后兼容）
4. `ai-agent-svc` 改为依赖 `mox-platform-operator-core`（替代 flow-operator-core）
5. 验证编译通过 + 测试通过
6. arch test 验证 V-04 消除

### 2.4 验收标准

- [x] `mox-platform-operator-core` crate 创建并编译通过
- [x] kernel.rs 迁移（970行：TypeIdentifier/TypeCheck/ResourceCost/守恒律/Op单子）
- [x] kernel_ext.rs 迁移（750行：serde/nalgebra 扩展）
- [x] monad.rs 迁移（From<Result> 实现）
- [x] `flow-operator-core` 的 kernel/kernel_ext/monad 重新导出 platform-operator-core（向后兼容，编译通过）
- [ ] StateVector 迁移（state.rs，285行）
- [ ] Operator trait 迁移（operator.rs，272行）
- [ ] ExecutionContext / ExecutionResult / OperatorMetadata 迁移
- [ ] `ai-agent-svc` 的 Cargo.toml 中移除 `mox-flow-operator-core`
- [ ] `cargo check --workspace` 通过
- [ ] arch test 中 V-04 消除

### 2.5 迁移进度（2026-08-27 更新）

**已完成**：crate 骨架创建 + kernel/kernel_ext/monad 三个模块迁移（约 1800 行代码），flow-operator-core 向后兼容验证通过。

**待完成**：StateVector + Operator trait + ExecutionContext 迁移（约 800 行），然后修改 ai-agent-svc 依赖。

- 难度：中等（类型迁移，需处理模块路径）

## §5 V-01：kg-hub-svc → flow-fusion-svc（P0+P1，最复杂）

### 5.1 根因分析

`kg-hub-svc` 在 9 个文件中依赖 `flow-fusion-svc`。kg→flow 方向错误（kg 不应依赖 flow）。需要深入分析具体使用了 flow-fusion-svc 的什么功能。

可能的根因：
- (a) 图谱融合功能错误地放在了 flow 域，应迁移到 kg 域
- (b) kg-hub-svc 需要调用工作流融合功能，应通过事件驱动或 sdk（但方向应为 flow→kg，不是 kg→flow）
- (c) 循环依赖：flow-fusion-svc 也可能依赖 kg-hub-svc

### 5.2 修复策略（需先深入分析代码）

**第一步：分析 kg-hub-svc 中 flow-fusion-svc 的具体使用**
- 列出所有使用的符号（struct、trait、function）
- 判断这些功能的本质归属（kg 还是 flow）

**第二步：根据分析结果选择修复策略**

策略 A（功能迁移）：如果融合功能本质是图谱融合，将其从 flow-fusion-svc 迁移到 kg 域（新建 `mox-kg-fusion-svc` 或合并到 kg-hub-svc）

策略 B（依赖反转）：如果 kg-hub-svc 只是调用 flow 的融合服务，通过事件驱动解耦（kg 发布事件，flow 订阅处理）

策略 C（sdk + 方向修正）：如果确实需要 kg 调用 flow，创建 flow-sdk 并在依赖矩阵中允许 kg→flow（但这违反 DAG，不推荐）

### 5.3 执行步骤

1. 深入分析 kg-hub-svc 中 flow-fusion-svc 的使用（1 人天）
2. 根据分析结果选择策略 A/B/C
3. 执行修复
4. 验证编译 + 测试
5. arch test 验证 V-01 消除

### 5.4 验收标准

- [ ] kg-hub-svc 的 Cargo.toml 中移除 `mox-flow-fusion-svc`
- [ ] 功能不丢失（融合功能仍可正常工作）
- [ ] `cargo check --workspace` 通过
- [ ] arch test 中 V-01 消除

### 5.5 预估工作量

- 难度：高（需深入分析，可能涉及功能迁移）
- 工时：3-5 人天
- 风险：高（功能迁移可能影响其他依赖方）
