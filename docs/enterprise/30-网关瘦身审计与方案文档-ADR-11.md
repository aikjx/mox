# 网关瘦身审计与方案文档（GATEWAY THINNESS · ADR-11）

> **文档身份**：`mox-platform-gateway-svc` 的职责审计与瘦身方案。基于 arch test 基线（7 项 P0 违规：gateway 直接依赖业务 svc/core），定义网关的合法职责边界、违规依赖清单、分阶段瘦身路线图。
> **版本**：v1.0 ENT（2026-08-26 · 开发专家联盟）
> **权威链**：`18` TOP-MASTER > `02` 架构七视图 > `29` 跨域依赖规则(ADR-09) > **本文件(ADR-11)**
> **关联 ADR**：ADR-08(架构迁移)、ADR-09(跨域依赖规则4)、ADR-12(可观测性)

---

## §1 网关职责定义（WHAT GATEWAY SHOULD DO）

### 1.1 合法职责（白名单）

| 职责 | 描述 | 实现方式 |
|------|------|----------|
| **路由转发** | 将 HTTP 请求按路径/方法转发到对应域的 api/svc 层 | axum Router + 内部 HTTP 调用或直接函数调用 |
| **鉴权认证** | JWT 验证、OAuth2 令牌校验、API Key 验证 | tower middleware + `mox-platform-iam-core` |
| **限流熔断** | 令牌桶限流、熔断器、并发控制 | tower::limit + 自定义 middleware |
| **CORS** | 跨域资源共享配置 | tower-http cors |
| **请求日志** | 结构化访问日志（method/path/status/duration） | `mox-platform-observability` middleware |
| **请求ID注入** | 为每个请求生成/传播 X-Request-ID | axum extension |
| **健康检查** | `/health`、`/ready` 端点 | 简单 handler，聚合各域健康状态（经 SDK） |
| **OpenAPI 聚合** | 聚合各域的 OpenAPI 规范到统一文档 | 启动时拉取各域 api 层的 schema |

### 1.2 禁止职责（黑名单）

| 禁止项 | 原因 | 正确归属 |
|--------|------|----------|
| ❌ 业务逻辑处理 | 网关是流量入口，不是业务层 | 对应域的 svc 层 |
| ❌ 直接访问数据库 | 网关不应持有数据库连接 | 对应域的 svc 层 |
| ❌ 调用算法 crate | 图谱算法/AI 推理/优化器 | kg/ai/flow 域的 svc 层 |
| ❌ 依赖其他域的 svc/core | 违反跨域依赖规则4 | 经各域 sdk 或 api 层间接调用 |
| ❌ 工作流编排 | 工作流是业务能力 | flow 域 svc 层 |
| ❌ 数据转换/映射 | 请求/响应 DTO 转换 | 对应域的 api 层 |

### 1.3 代码量约束

- gateway crate 代码量 ≤ 总代码量的 **5%**
- gateway 的 `Cargo.toml [dependencies]` 中：
  - ✅ 允许：foundation、framework、iam-core、各域 sdk、observability
  - ❌ 禁止：任何域的 svc（除自身）、任何域的 core（除 platform 系统 core）、数据库驱动、算法 crate

## §2 当前状态审计（AS-IS AUDIT）

### 2.1 arch test 基线违规（7 项 P0）

基于 `tools/arch_test.py` 2026-08-26 基线，gateway 存在以下违规依赖：

| # | 违规依赖 | 违规类型 | 严重度 | 分析 |
|---|----------|----------|--------|------|
| 1 | `mox-cloud-volume-svc` | R4: gateway依赖业务svc | P0 | 云存储卷管理，应经 cloud-sdk 或独立 api |
| 2 | `mox-data-compliance-svc` | R4: gateway依赖业务svc | P0 | 数据合规检查，应经 data-sdk |
| 3 | `mox-data-etl-svc` | R4: gateway依赖业务svc | P0 | ETL 任务管理，应经 data-sdk |
| 4 | `mox-data-plane-svc` | R4: gateway依赖业务svc | P0 | 数据平面，应经 data-sdk |
| 5 | `mox-data-standards-core` | R4: gateway依赖业务core | P0 | 数据标准类型，应下沉到 foundation 或经 sdk |
| 6 | `mox-kg-fusion-svc` | R4: gateway依赖业务svc | P0 | 图谱融合服务，应经 kg-sdk |
| 7 | `mox-kg-service-svc` | R4: gateway依赖业务svc | P0 | 图谱服务，应经 kg-sdk |

### 2.2 违规根因分析

**根因 1：网关承担了"业务聚合层"角色**
- 当前 gateway 不仅做路由，还直接调用各域 svc 完成业务聚合
- 这是典型的"胖网关"反模式（Fat Gateway Anti-Pattern）
- 正确做法：网关只做路由，业务聚合由 BFF（Backend for Frontend）或各域 api 层完成

**根因 2：缺少各域 sdk 层**
- 目前多数域只有 core/svc 层，缺少 sdk 层
- 网关无法通过 sdk 调用，只能直接依赖 svc
- 修复路径：Phase 3 为每个域创建 sdk 层 crate

**根因 3：api 层未填充**
- 8 个域的 api 层目录已创建但 0 crate
- 路由注册、DTO 转换、OpenAPI 生成等职责暂由 gateway 承担
- 修复路径：Phase 3 填充各域 api 层

### 2.3 网关当前依赖分类

| 依赖类型 | 数量 | 合法性 | 处理方式 |
|----------|:----:|:------:|----------|
| foundation/framework | — | ✅ 合法 | 保留 |
| platform iam-core/system-core | — | ✅ 合法 | 保留 |
| observability | — | ✅ 合法 | 保留（Phase 2.1 引入） |
| 各域 svc（7个） | 7 | ❌ 违规 | 迁移到 sdk 或 api 层 |
| 各域 core（1个） | 1 | ❌ 违规 | 类型下沉到 foundation 或经 sdk |
| 数据库驱动 | ? | ❌ 违规（如有） | 移除，网关不连库 |

## §3 瘦身方案（TO-BE PLAN）

### 3.1 目标架构

```
                    ┌─────────────────────┐
                    │  mox-platform-gateway │
                    │  (Thin Gateway, <5%) │
                    │  路由·鉴权·限流·CORS  │
                    │  日志·RequestID·健康  │
                    └──────────┬──────────┘
                               │ HTTP 路由
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │  kg-api     │      │  ai-api     │      │  flow-api   │
   │  (REST DTO) │      │  (REST DTO) │      │  (REST DTO) │
   └──────┬──────┘      └──────┬──────┘      └──────┬──────┘
          │                     │                     │
          ▼                     ▼                     ▼
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │ kg-svc      │      │ ai-svc      │      │ flow-svc    │
```

### 3.3 路由分发实现方案

**方案 A：进程内函数调用（推荐，模块化单体阶段）**
- 各域 api 层提供 `Router` 实例
- 网关通过 `nest()` 或 `merge()` 组合所有域的 Router
- 零网络开销，类型安全
- 适合当前模块化单体架构

```rust
// 网关 main.rs
use mox_kg_api::router as kg_router;
use mox_ai_api::router as ai_router;
use mox_flow_api::router as flow_router;

let app = Router::new()
    .nest("/api/v1/kg", kg_router())
    .nest("/api/v1/ai", ai_router())
    .nest("/api/v1/flow", flow_router())
    // ... 其他域
    .layer(auth_layer())
    .layer(rate_limit_layer())
    .layer(cors_layer())
    .layer(observability_layer());
```

**方案 B：内部 HTTP 调用（微服务阶段，Phase 3 后）**
- 各域 api 层独立部署为 HTTP 服务
- 网关通过 reqwest 反向代理
- 需要服务发现、负载均衡
- 适合微服务拆分后

## §4 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|:----:|----------|
| sdk 层提取导致接口变更 | 下游调用方需修改 | 中 | sdk 层 first do no harm，保持 svc 原有接口签名 |
| api 层填充工作量大 | 延期 | 高 | 优先填充 kg/ai/flow 核心域，data/cloud 可延后 |
| 路由迁移期间接口不稳定 | 前端受影响 | 中 | 灰度发布，新旧路由并行，通过 feature flag 切换 |
| 网关性能退化 | 请求延迟增加 | 低 | 性能基准测试，nest() 组合 overhead <1ms |
| 鉴权逻辑分散到各域 api | 安全风险 | 中 | 鉴权仍由网关统一 middleware 完成，api 层不重复鉴权 |

## §5 验收标准（DoD）

## §6 开源对标

| 维度 | 本方案 | 业界最佳实践 | 差距 |
|------|--------|-------------|------|
| 网关定位 | 薄网关（路由+鉴权+限流） | API Gateway 模式（Kong/Apigee） | ✅ 对齐 |
| 业务聚合 | BFF 层（各域 api） | Backend for Frontend 模式 | ✅ 对齐 |
| 路由实现 | axum nest() 进程内 | 模块化单体推荐进程内 | ✅ 对齐 |
| 鉴权 | 网关统一 JWT/OAuth | API Gateway 统一鉴权 | ✅ 对齐 |
| 限流 | tower::limit 令牌桶 | Redis 令牌桶/滑动窗口 | ⚠️ 分布式限流需引入 Redis |
| 可观测性 | observability middleware | 网关级 metrics/tracing | ✅ 对齐（Phase 2.1） |
| 服务发现 | 进程内（无需） | Consul/Nacos（微服务阶段） | — 模块化单体阶段不需要 |

**结论**：网关瘦身方案与业界 API Gateway + BFF 模式 100% 对齐。当前差距在分布式限流（微服务阶段才需要），模块化单体阶段 tower::limit 足够。
