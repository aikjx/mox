## 1. 目的与适用范围

### 1.1 目的

本规范定义璇玑 RelGraph（OUS 算子统一系统）从需求立项到交付运维的**全链路企业级处理流程**，确保：

- 需求↔架构↔业务↔文档四方同步不漂移（四归三连铁律 All-03）；
- 每阶段有明确的输入、输出、责任人、质量门禁；
- 三联盟（产品/算法/开发）职责清晰、交接可追溯；
- 代码、配置、文档、数据全生命周期可审计。

### 1.2 适用范围

- 本仓库 `infotopograph`（璇玑 RelGraph / OUS）所有模块的开发、变更、发布；
- 涵盖 Rust 后端（`platform/` 73+crate workspace）、Vue3 前端（`frontend-ui/`）、Python 工具链（`tools/`、`scripts/`）、WASM 插件（`plugins/`）；
- 适用于三联盟所有成员及外部贡献者。

## 3. 各阶段详细流程

### EP-1 需求立项（产品联盟主责）

**输入**：业务诉求 / 客户需求 / 技术债 / 缺陷报告

**处理步骤**：

1. **需求登记**：在 `docs/graph/requests/` 下创建 `REQ-YYYY-NNN-<主题>.json`，包含需求标题、描述、提出人、优先级、预期收益。
2. **P9 判重（铁律 All-02）**：运行 `tools/info-graph dedup`，Match Score ≥ 0.85 必须复用已有模块，零匹配才允许立项。
3. **全维需求明确书**：按 `docs/enterprise/07-全维需求明确书.md` 模板编写，包含四闸门（业务闸门/技术闸门/资源闸门/风险闸门）、双收口（范围收口/验收收口）。
4. **验收断言**：每条需求必须附带可测试的验收断言（Given-When-Then 格式），无断言退回产品联盟补全。
5. **三联盟评审**：产品联盟（要不要做）、算法联盟（做不做得对）、开发联盟（做不做得稳）三方签字。

**输出**：
- `REQ-YYYY-NNN.json`（机读需求卡）
- 全维需求明确书（人读）
- P9 判重报告
- 三联盟评审记录

**门禁 G1**：需求明确书 + 验收断言 + P9 判重通过 + 三联盟签字

---

### EP-2 架构设计（算法联盟主责）

**输入**：通过 G1 的需求包

**处理步骤**：

1. **架构决策记录（ADR）**：在 `docs/enterprise/` 下创建 `ADR-NN-<决策主题>.md`，记录上下文、决策、后果、替代方案。
2. **图建模合规检查**：新节点/边必须符合 `docs/enterprise/02-architecture.md` 定义的 14 节点族 × 19 边族本体，新增族需算法联盟审批。
3. **算法选型与 Δ对账**：涉及算法的模块必须从八大算法家族（A1~A8）选型，输出 `Δ≤1e-6` 对账报告（8 算法 × 7 数据集）。
4. **接口契约设计**：跨域依赖必须经 L2 API 层（`platform/domains/*/api/`），定义 trait 契约 + 输入输出 Schema + SLA。
5. **数据架构设计**：遵循架构-数据分离铁律（`docs/standards/architecture-data-separation.md`），运行时数据放 `data/`，配置放 `config/`，代码放 `platform/`。
6. **三联盟架构评审**：算法联盟（复杂度/正确性）、开发联盟（可实现性/性能）、产品联盟（范围对齐）三方会签。

**输出**：
- ADR 决策记录
- 架构设计文档（更新 `02-architecture.md` 对应章节）
- 算法对账报告
- 接口契约（trait + Schema）
- 数据架构设计

**门禁 G2**：ADR + Δ对账报告 + 接口契约 + 三联盟会签

---

### EP-3 开发实现（开发联盟主责）

**输入**：通过 G2 的架构设计包

**处理步骤**：

1. **分支策略**：
   - 主分支 `main`（保护分支，仅通过 PR 合并）
   - 功能分支 `feature/REQ-NNN-<主题>`
   - 修复分支 `fix/REQ-NNN-<主题>`
   - 发布分支 `release/vX.Y.Z`
2. **Crate 路径规范**：新 crate 必须位于 `platform/domains/{域}/{层}/` 或 `platform/{foundation,gateway,framework}/`，禁止使用已废弃路径。
3. **编码规范**：
   - Rust：`cargo fmt` + `cargo clippy --all-targets --all-features -- -D warnings`（0 告警）
   - 前端：ESLint + Prettier，提交前自动格式化
   - Python：`black` + `ruff`，类型注解完整
4. **单元测试**：
   - Rust：每个 pub fn 必须有单测，覆盖率 ≥ 80%（核心模块 ≥ 90%）
   - 测试命名：`test_<被测函数>_<场景>_<预期>`
5. **文档注释**：
   - Rust：每个 pub item 必须有 `///` 文档注释，含示例
   - 模块级 `//!` 注释说明模块职责
6. **版权头**：每个源码文件顶部必须包含版权声明（见 §7）。
7. **代码评审（PR Review）**：
   - 至少 1 名开发联盟成员 + 1 名相关域负责人 Approve
   - 涉及算法的 PR 需算法联盟成员 Approve
   - CI 全绿（fmt + clippy + test + 架构测试）才能合并

**输出**：
- 功能分支代码
- 单元测试
- 文档注释
- PR 评审记录

**门禁 G3**：clippy 0 告警 + 单测全绿 + 覆盖率达标 + PR 双 Approve + CI 全绿

---

### EP-4 测试验证（开发联盟主责）

**输入**：通过 G3 的代码

**处理步骤**：

1. **集成测试**：`tests/` 目录下编写跨 crate 集成测试，覆盖核心业务流程。
2. **端到端测试**：前端 + 后端联调测试，覆盖用户主路径。
3. **性能基准测试**：
   - `benches/` 下编写 Criterion 基准
   - 图算法：PageRank / 介数中心性 / 社区检测 在 10万节点图上的耗时基准
   - API 网关：P50/P95/P99 延迟基准
4. **安全扫描**：
   - `cargo audit`（依赖漏洞扫描）
   - `cargo deny check`（许可证/漏洞/重复依赖检查，配置见 `deny.toml`）
   - 前端 `npm audit`
5. **架构合规测试**：`cargo test -p mox-arch-test`（8 项架构不变量：分层规则/跨域依赖/环检测/API纯度/架构-数据分离等）。
6. **数学自洽性验证**：`python3 scripts/manage.py verify`（6 大公理验证）。
7. **测试报告归档**：测试结果存入 `docs/enterprise/_data/test-report-YYYYMMDD/`。

**输出**：
- 集成测试报告
- 性能基准报告
- 安全扫描报告
- 架构合规测试报告
- 数学自洽性验证报告

**门禁 G4**：集成测试全绿 + 性能基准达标（无回归 >10%）+ 安全扫描无高危 + 架构测试全绿 + 数学验证全绿

---

### EP-5 构建发布（开发联盟主责）

**输入**：通过 G4 的测试包

**处理步骤**：

1. **版本号规范**：语义化版本 `MAJOR.MINOR.PATCH`
   - MAJOR：不兼容的 API 变更
   - MINOR：向下兼容的功能性新增
   - PATCH：向下兼容的问题修正
2. **更新版本号**：
   - `Cargo.toml` workspace version
   - `frontend-ui/package.json` version
   - `README.md` 版本徽章
   - `docs/enterprise/05-iteration-roadmap.md` 里程碑状态
3. **构建可复现性验证**：
   - `cargo build --release` 两次构建产物 SHA256 一致
   - `Cargo.lock` 已提交
4. **产物签名**：Release 产物用 GPG 签名，公钥存入 `docs/`。
5. **Release Notes**：按 `Added / Changed / Deprecated / Removed / Fixed / Security` 分类编写，关联对应 REQ/ADR。
6. **Git Tag**：`git tag -a vX.Y.Z -m "Release vX.Y.Z"`，推送至双仓库（gitcode + github）。
7. **GitHub/GitCode Release**：上传二进制产物 + 校验和 + Release Notes。

**输出**：
- 版本号更新的提交
- Git Tag
- Release 产物（二进制 + 校验和 + 签名）
- Release Notes

**门禁 G5**：构建可复现 + 签名校验通过 + Release Notes 完整 + Tag 推送双仓库

---

### EP-6 部署运维（开发联盟/运维主责）

**输入**：通过 G5 的 Release 包

**处理步骤**：

1. **部署清单**：编写部署清单（服务列表、端口、配置、依赖、环境变量），存入 `deploy/`。
2. **环境变量配置**：遵循 12-Factor，所有配置通过环境变量注入：
   - `MOX_DATA_DIR` / `MOX_PLUGINS_DIR` / `MOX_CONFIG_DIR` 等
   - 数据库后端：`MOX_BACKEND`（sqlite/postgres/mysql）+ `MOX_DB_URL`
3. **数据库迁移**：
   - 迁移脚本存放 `platform/domains/platform/core/mox-platform-datastore-core/migrations/`
   - 升级前备份，升级后验证
4. **回滚预案**：每个发布必须附带回滚步骤（上一版本二进制 + 数据库回滚脚本）。
5. **监控告警**：
   - 指标端点：`GET /ai/engine/metrics`（成功率/降级率/P50/P95/P99 延迟）
   - 日志：结构化 JSON 日志，级别可配置
   - 告警阈值：P99 延迟 > 5s / 错误率 > 1% / 服务不可达
6. **健康检查**：`GET /api/health`，部署后自动探活，失败触发回滚。
7. **灰度发布**：重大变更先灰度 10% 流量，观察 24h 无异常再全量。

**输出**：
- 部署清单
- 配置文件（`config/` 模板）
- 回滚预案
- 监控告警配置
- 部署验证报告

**门禁 G6**：部署清单 + 回滚预案 + 监控配置 + 健康检查通过 + 灰度观察无异常

---

### EP-7 交付归档（三联盟会签）

**输入**：通过 G6 的部署包

**处理步骤**：

1. **交付清单**：按 `docs/enterprise/10-企业级交付清单.md` 模板，包含：
   - 代码（Tag + Commit SHA）
   - 文档（需求/架构/设计/测试/运维）
   - 配置（模板 + 环境变量清单）
   - 数据（Schema + 迁移脚本 + 示例数据）
   - 第三方依赖（清单 + 许可证）
2. **五签确认**：产品联盟 + 算法联盟 + 开发联盟 + 客户 + 审计 五方签字。
3. **文档归一化**：运行文档归一化检查，确保需求↔架构↔业务↔文档四方一致（四归三连）。
4. **知识库更新**：
   - 更新 `docs/GLOSSARY.md`（新增术语）
   - 更新 `docs/enterprise/00-INDEX.md`（文档索引）
   - 更新关图 `docs/graph/graph.json`（新增节点/边）
5. **经验复盘**：编写复盘报告（成功经验/问题/改进项），存入 `docs/enterprise/_archive/YYYY-MM-DD/`。
6. **归档**：所有交付物打 Tag，存入仓库 `docs/enterprise/` 对应目录，只读归档。

**输出**：

- 文档归一化报告
- 知识库更新
- 复盘报告

**门禁 G7**：交付清单五签 + 文档归一化通过 + 知识库更新 + 复盘完成 + 归档 Tag

## 5. 配置管理与版本控制

### 5.1 Git 分支模型

```
main ────────────────────────────────────────●─── (保护分支，仅PR合并)
  │                                             │
  ├── release/v3.1.0 ─────────────────●─────── (发布分支)
  │                                     │
  ├── feature/REQ-001-ai-gateway ──●──┘        (功能分支)
  │                                     │
  └── fix/REQ-002-pagerank-bug ───●──┘          (修复分支)
```

### 5.2 Commit Message 规范

采用 Conventional Commits：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore` / `ci`
- **scope**：crate 名或模块名（如 `mox-kg-spark-svc`、`gateway`、`frontend`）
- **subject**：简明描述，不超过 72 字符
- **footer**：关联 REQ/ADR，如 `Refs: REQ-2026-001` / `Closes: #123`

示例：
```
feat(kg-spark): 新增 PageRank 并行实现（rayon）

- 使用 rayon 并行化幂迭代，10万节点图耗时降低 60%
- 新增基准测试 benches/pagerank.rs
- 对齐 ADR-007 图算法并行化决策

Refs: REQ-2026-005
```

### 5.3 双仓库同步

主仓 GitCode + 镜像 GitHub，每次推送同步至双仓：

```bash
git remote set-url --add --push origin https://gitcode.com/aikjx/mox.git
git remote set-url --add --push origin https://github.com/aikjx/mox.git
```

## 6. 安全与合规

### 6.1 依赖安全

- `cargo audit` 纳入 CI，高危漏洞阻断合并
- `deny.toml` 配置许可证白名单（MIT/Apache-2.0/BSD 等）
- 第三方二进制/模型放 `third_party/`，记录来源与许可证

### 6.2 代码安全

- 禁止硬编码密钥/密码/Token，使用环境变量或配置文件（`.gitignore`）
- WASM 插件沙箱隔离，禁止直接访问宿主文件系统
- 输入校验：所有外部输入必须校验长度/类型/范围，防止注入

### 6.3 数据安全

- PII（个人身份信息）脱敏：`mox-data-compliance-svc` 负责
- 数据库连接串含密码时，日志中必须脱敏
- 导出数据必须经审批，记录导出日志

### 6.4 合规审计

- 所有 PR 合并记录可追溯（作者/评审者/时间/变更内容）
- 发布产物签名可验证
- 审计日志（操作记录）保留 ≥ 180 天

## 8. 异常处理与变更管理

### 8.1 缺陷处理流程

1. **缺陷登记**：Issue 模板，包含复现步骤/预期/实际/环境/严重程度
2. **严重程度分级**：
   - P0（阻断）：核心功能不可用 → 24h 内修复
   - P1（严重）：主要功能异常 → 3 个工作日内修复
   - P2（一般）：次要功能异常 → 下个迭代修复
   - P3（轻微）：UI/体验问题 → 排期修复
3. **根因分析**：P0/P1 必须做 5-Why 根因分析，输出改进措施
4. **回归测试**：修复后必须添加回归测试用例

### 8.2 变更管理

- **紧急变更**（线上故障修复）：可跳过部分门禁，但必须事后 48h 内补齐文档与评审
- **常规变更**：严格遵循 EP-1~EP-7 七阶段流程
- **架构变更**：必须新增 ADR，经三联盟架构评审会签
