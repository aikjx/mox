## 0 · 大白话：mox 模块化系统架构自动化处理到底是个啥

> **一句话**：你画好一张流程图（业务/算法/权限/资源都画在同一张图里），点一下"提交"，
> 系统自动拉来 14 位专家一起审、自动排好最优执行顺序、自动过四道安全闸门、自动把所有决定记进审计链，
> 最后告诉你"能上线"还是"哪里卡住了，为什么"。**整个过程没人中间插手，也没法插手跳过任何一道关。**

它解决的是"前面说的mox 模块化系统架构需求（`07`）怎么真的跑起来"的问题——把 `07` 里那 8 条需求、4 道闸门，
从"纸面规矩"变成"一段代码自动执行"。

## 1 · 自动化处理跑哪几步（不可拆分、不可跳过）

> 下面每一"步"都是流水线 `mox_optimize` 里**真实存在且顺序固定**的环节。
> 标 ⛔ 的是"卡住就整条停"的强制控制点。

| 步 | 大白话：这一步干啥 | 对应 `07` 需求 | 主责联盟（新增 v1.1） | 代码落点 |
|----|---------------------|----------------|:--:|----------|
| ① 提交 | 前端把流程图（JSON）发到 `/api/optimize` —— 必须带 REQ 根，没有判重通过的 REQ 根会被 BP-9 闸门在应用层直接挡掉（All-02 铁规） | — | 产品联盟 C（REQ 根绑定）+ 开发联盟 R（server） | `server.rs::run()` → `mox_optimize` |
| ② 归一化 | 把图打上维度标签，合成唯一 `FlowGraph`（四图合一）；如果图上有 G0 能检出的孤儿/悬空/非 DAG，直接 Blocked，不进入下一步 | §1.1 有根 / §1.2 归一化强制 | 算法联盟 R（打标签算法）+ 开发联盟 R（ir 实现） | `ir::auto_dimension` + `primiflow_fusion::full_gate` G0 |
| ③ mox 模块化系统架构分析验证 | 14 位专家（业务七维+开发七维）并行会诊，各自挑刺给分；确定性并行（同输入同输出） | §1.3 权限优先 / §1.4 十四维全过 | 算法联盟 R（维度权重 / 专家模型）+ 开发联盟 R（并行骨架 rayon） | `harness::run_experts` + `experts::all_experts()` |
| ④ 裁决 | 按"权限>安全>资源>…"座次拍板，硬约束优先落地；同优先级平手冲突升级为 Risk(Blocking) 交产品联盟签字审批（All-01 铁规） | §1.3 座次 / §1.4 冲突升级 | 算法联盟 R（`DIM_PRIORITY` 裁决逻辑）+ 产品联盟 A（Blocking 签字） | `reconcile()` |
| ⑤ 最优求解 | 用已验证引擎算最快最省的并行顺序 + 出码；产出加速比、剪伪依赖数、算力压缩比可解释报告（BR-15） | §1.5 用验证引擎 | 算法联盟 R（CPM+RCPSP 算法正确性）+ 开发联盟 R（出码稳定性） | `flow_ai::pipeline::optimize` |
| ⑥ ⛨璇玑否决 ⛔ | 5 项数学/语义硬检查：节点没丢、真依赖没断、没阻塞冲突、并行无数据竞争、图与代码对得上。任一不过 → 强制 Blocked（最高权限，任何 RBAC/合规结论都不能覆盖） | §2 G2 | 算法联盟 R（数学不变式设计 & 验证）+ 开发联盟 R（verify 实现） | `verify()` + `govern.rs::GateResult` |
| ⑦ 治理闸门 ⛔ | 审计链+版本状态机+SLA+预算+RBAC 审批五条件全过才准出码。五条件缺一无条件拒，仅 dry-run 允许（空跑不写真实产物）。 | §2 G3 / §1.6 四闸无旁路 | 开发联盟 R（RBAC & SLA & 预算 & 状态机）+ 产品联盟 A（RBAC 审批签字） | `govern()` + `primiflow_fusion::full_gate` G1 |
| ⑧ 审计收尾 | 把"谁、何时、对哪张图、做了啥决定、走了哪条三联盟签字"写进哈希链（prev_hash→hash，不可篡改）；并写入三联盟签字副本供 All-04 追溯 | §1.7 留痕不可篡改 | 开发联盟 · 安全组 R（哈希链 & 落盘）+ 三联盟联合（签字留痕） | `AuditChain::append` + 审计查询端点 |

> **闭环产物**：`GovernanceReport`——一份把上面所有环节结论打包的报告（专家分 + 优化报告 + 璇玑结论 + 闸门结论 + 审计哈希）。
> 前端 `MoxFusionView.vue` 据此高亮关键路径、复用路径、风险点。

## 2 · 它怎么保证"mox 模块化系统架构需求"被真的执行（不糊弄）

| `07` 铁律要求 | 自动化处理里怎么落实（代码级） |
|---------------|-------------------------------|
| 流程图归一化强制 | ② 在 ③ 之前；不经过 `auto_dimension` 的图进不了专家诊断 |
| 十四维全过、不跳过 | ③ `all_experts()` 真实派生 14 位，曾硬编码 7 个已修正；`run_experts` 确定性并行 |
| 权限/安全压过性能 | ④ `reconcile` 按 `DIM_PRIORITY`（权限/安全=100）排序；`Risk(Blocking)` 不可被软约束覆盖 |
| 四道闸门无降级旁路 | ⑥⑦ 任一道 `vetoed/!approved` → `FlowStatus::Blocked`；`govern` 内 `approved=!algorithm_veto ∧ …` 五条件缺一无条件拒 |
| 仅 dry-run 不真出码 | ⑧ 未 `Approved` 版本 `status.can_emit()=false`，闸门拒绝即不产出可执行代码 |
| 无验证扩展一律退回 | 流水线**没有**"跳过某专家/某闸门"的开关；外部无法注入旁路参数 |

## 3 · 铁律重申：自动化处理不做"无用扩展"

> 对齐 `07` §3 禁止项。本文件明确：**mox 模块化系统架构自动化处理只跑"已登记进 `06` 映射、且过 `07` 双收口"的功能**，
> 不为"演示好看"新增未经验证的分析维度或旁路开关。

- ❌ 禁止给流水线加"跳过归一化/跳过某专家/跳过璇玑"参数。
- ❌ 禁止接"未经 `06` 映射登记"的流程图来源（图的来源必须带 REQ 根，可追溯到需求）。
- ❌ 禁止把璇玑的"否决级"降级成"建议级"来换取通过率。
- ✅ 允许：在同一流水线内新增**已通过mox 模块化系统架构分析验证**的优化策略（须经 `07` §3 双收口回归测试）。

## 4 · 调用入口（人怎么用它）

| 方式 | 入口 | 说明 |
|------|------|------|
| 前端界面 | `MoxFusionView.vue` → 「提交优化」 | 画/导入流程图 → `POST /api/optimize` → 看 `GovernanceReport` 高亮 |
| HTTP API | `POST /api/optimize`（body: `OptimizeRequest{flow,tenant,namespace,principal,roles}`） | 服务端 `run()` 透传角色（缺省最低 `viewer`，不硬编码 admin） |
| 实时会话 | `GET /api/live` | 对实时会话图跑同款 `run()`，复用闭环 |
| 一键闭环演示 | `GET /api/closedloop` | 跑完整 optimize + LLM 调用对比（量化收益） |
| 单元/集成 | `pipeline.rs` 测试：`mox_end_to_end_runs` / `mox_double_league_fourteen_dimensions` / 越权拦截 | 证明双收口在自动化下确实生效 |

> **安全要点**：`run()` 不再硬编码 admin/editor（旧版漏洞），而是透传调用方声明的角色；
> 未声明时仅授 `viewer`，从源头堵住"自动化处理绕开 RBAC"的可能（见 `server.rs` 注释）。
