分析 A 现有业务流程系统性分析

现有 xuanji-expert（璇玑）已实现「七位专家并行诊断 + 归一化裁决 + 企业治理」的流程图优化内核，并具备资源级 RBAC 引擎。但其业务流程停留在图/策略优化层面，缺少人与组织维度：

维度现有能力缺失 / 薄弱点
成员抽象 Principal{subject,roles}无真实成员身份、生命周期、专长档案；无法对「人」分派工作
任务仅 flow-graph 优化任务无任务创建/分派/进度/协作；专家工作不可追踪
权限资源级策略（db:prod/* 等）无「成员↔角色↔作用域」绑定管理；不可运营
通信审计追加写（不可篡改）无实时通知、无频道/消息、结果不回流给干系人
事件治理审计事件事件与通信割裂，无 fan-out 到参与者

分析 B 瓶颈与改进点识别

识别到的瓶颈

  • B1 专家是抽象概念，无真实成员，优化结果无人承接 → 价值无法落地。
  • B2 RBAC 是策略级，缺成员/角色运营界面，权限难管理。
  • B3 无实时通信，优化/审批结论靠轮询，协作低效。
  • B4 事件与通知割裂，参与者对进展无感知。
  • B5 重流程（7 专家 + flow-ai）无任务级增量，小改动成本高。
  • B6 内存态存储，无持久化与多实例扩展。

对应改进点

  • I1 成员管理作为一等公民，将 Principal 映射为真实成员（专长/等级/生命周期）。
  • I2 把「流程图优化」封装为一种任务类型，由璇玑分派给专家执行，结果回写任务频道。
  • I3 权限下沉到成员↔角色↔作用域，所有权权限约束专家仅能动自己任务。
  • I4 事件总线 + 反应器 + WebSocket，实现「变更即通知」。
  • I5 任务 FSM 支持增量推进，避免全量重算。
  • I6 Store 接口化，可平滑替换为 SQLite / 分布式 KV。

分析 C 优化方案：璇玑系统与现有内核的协同

本实现（crates/xuanji-system）按 OUS 分层架构补齐四大子系统，并与既有 xuanji-expert 内核归一化协同：

优化方案落地方式收益
成员即身份Member + Xuanji 多租户；默认授予 Expert 角色专家可承接任务，治理与计费可到人
任务化内核Task 可绑定一种「flow-optimize」交付物；完成态回写结论到任务频道重流程变为可追踪、可协作的增量工作
权限运营化RoleBinding（Global/Xuanji/Task）+ *Own 所有权权限，嵌入每次 require()越权在入口被拦截（已测试验证）
通信事件化写操作→DomainEvent→EventBus→Reactor→系统消息+通知→WebSocket干系人实时感知进展，消除信息孤岛
架构对齐接入/运行时/编排/核心域/数据 五层，复用 flow-ai 与 RBAC 哲学可组合、可演进、与 OUS 一致

验证 实现与测试结论

  • cargo build -p xuanji-system 通过；cargo test -p xuanji-system 三项集成测试全部通过。
  • 端到端演示（--demo）验证：引导璇玑 → 邀请/激活专家 → 创建/分派/推进任务 → 评论 → 越权被 RBAC 拦截 → 提升协调员后可推进 → 事件反应器自动生成通知与任务频道系统消息。
  • HTTP 服务冒烟：/api/health 返回 ok；携带令牌 /api/me 正常；缺令牌 /api/tasks 返回 401。
  • 四大核心模块（成员管理 / 任务协作 / 权限分配 / 通信机制）经事件总线闭环协同，符合业务架构设计。
