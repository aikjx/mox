1. 日常巡检

1.1 L1 巡检（每小时）

自动化巡检，告警触发，无需人工介入：

✅ L1 自动巡检项

  • 所有服务 Pod 状态正常（无 CrashLoopBackOff）
  • 所有 Service Endpoints 数量正常
  • API 错误率 < 1%
  • API P99 延迟 < 500ms
  • CPU 使用率 < 80%
  • 内存使用率 < 80%
  • 数据库连接池使用率 < 80%
  • NATS 消息无堆积

1.2 L2 巡检（每日）

值班工程师每日检查：

📅 L2 每日巡检项

  • 查看 Grafana Overview 大盘，确认 24h 趋势正常
  • 检查各服务副本数是否符合预期
  • 检查是否有异常重启的 Pod
  • 检查慢查询（数据库 > 1s 的查询）
  • 检查 Redis 内存使用趋势
  • 检查 NATS JetStream 消费者延迟
  • 检查审计日志是否有异常操作
  • 确认当日备份是否成功
# 快速检查脚本
echo "=== Pod 状态 ==="
kubectl get pods -n expert-alliance -o wide

echo -e "\n=== 资源使用 ==="
kubectl top pods -n expert-alliance --sort-by=cpu

echo -e "\n=== 重启次数 ==="
kubectl get pods -n expert-alliance | awk '$4 > 0 {print $0}'

echo -e "\n=== HPA 状态 ==="
kubectl get hpa -n expert-alliance

echo -e "\n=== 最近告警 ==="
# 假设使用 Prometheus Alertmanager
# amtool alert --alertmanager.url=http://alertmanager:9093

📆 L3 每周巡检项

  • 容量趋势分析：CPU/内存/存储一周增长趋势

1.4 L4 巡检（每月）

🗓️ L4 每月巡检项

  • 全链路压测（按需）
  • 故障演练：模拟单节点故障、单 AZ 故障
  • DR 环境切换演练
  • 安全审计
  • 成本优化分析
  • SLA 达成情况复盘

2. 监控与告警

2.1 核心监控指标

类别指标名说明告警阈值
API 指标 alliance_http_requests_total HTTP 请求总数 —
alliance_http_request_duration_seconds HTTP 请求延迟分布 P99 > 500ms (P2)
alliance_http_error_rate HTTP 错误率 (5xx / 总请求) > 1% (P2) / > 5% (P1)
alliance_rate_limit_blocked_total 被限流拦截的请求数 突增 3 倍 (P3)
任务指标 alliance_active_tasks 当前活跃任务数 接近上限 80% (P2)
alliance_task_queue_depth 待调度任务队列深度 > 100 持续 5min (P2)
alliance_task_failure_rate 任务失败率 > 5% (P1)
系统指标 alliance_circuit_breaker_open_total 熔断器打开次数 > 0 (P2)
alliance_db_connection_pool_usage 数据库连接池使用率 > 85% (P2)
alliance_nats_consumer_lag NATS 消费者延迟 > 1000 持续 5min (P2)

2.2 告警分级

级别定义响应时间通知方式
P1 紧急 核心功能不可用 / 大面积用户影响 / 数据丢失风险 5 分钟内响应 电话 + 短信 + IM @所有人
P2 重要 部分功能异常 / 性能降级 / 单点故障但服务可用 15 分钟内响应 IM @值班 + 短信
P3 一般 非核心功能异常 / 告警阈值触发但服务正常 2 小时内响应 IM 消息
P4 提示 信息类通知，无业务影响 次日处理 邮件 / 工单

2.3 Grafana 大盘

默认提供 4 个核心 Dashboard：

  • Overview — 全局总览：QPS、延迟、错误率、资源使用
  • Service Detail — 单服务详情：RED 指标、JVM/Go 状态
  • Task Pipeline — 任务流水线：各阶段耗时、成功率、积压
  • Infrastructure — 基础设施：节点资源、网络、存储

3. 备份与恢复

3.1 备份策略

数据类型备份方式频率保留周期RPO
PostgreSQL 全量 + WAL 增量 每日全量 + 实时 WAL 30 天 < 5 分钟
Redis RDB + AOF 每小时 RDB + 实时 AOF 7 天 < 1 秒
图数据库 全量快照 每日全量 30 天 < 24 小时
对象存储 版本控制 + 跨区域复制 实时 90 天 0（版本回退）
NATS 消息 JetStream 持久化 实时 7 天 取决于 RPO 配置

3.2 PostgreSQL 备份

# 手动触发全量备份
kubectl exec -it postgres-primary-0 -n expert-alliance -- \
  pg_basebackup -h localhost -U replicator -D /backup/$(date +%Y%m%d) -Ft -z -P

# 查看备份列表
kubectl exec -it postgres-primary-0 -n expert-alliance -- \
  ls -lh /backup/

# 自动备份（CronJob）
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
  namespace: expert-alliance
spec:
  schedule: "0 2 * * *"   # 每天凌晨 2 点
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: postgres:15
              command:
                - /bin/bash
                - -c
                - |
                  pg_dump -h postgres-primary -U expert_alliance expert_alliance \
                    | gzip > /backup/alliance-$(date +%Y%m%d-%H%M).sql.gz
                  # 保留 30 天
                  find /backup -name "alliance-*.sql.gz" -mtime +30 -delete

3.3 PostgreSQL 恢复

恢复操作会覆盖现有数据，操作前务必确认并做好当前数据备份！ 
# 1. 停止应用写入（缩小服务副本数为 0）
kubectl scale deployment -n expert-alliance \
  --replicas=0 -l app.kubernetes.io/part-of=expert-alliance

# 2. 备份当前数据（可选，但建议执行）
kubectl exec -it postgres-primary-0 -- \
  pg_dump -U expert_alliance expert_alliance | gzip > /backup/before-restore-$(date +%Y%m%d-%H%M).sql.gz

# 3. 恢复指定备份
gunzip -c /backup/alliance-YYYYMMDD-HHMM.sql.gz | \
  kubectl exec -i postgres-primary-0 -- psql -U expert_alliance expert_alliance

# 4. 验证数据
kubectl exec -it postgres-primary-0 -- \
  psql -U expert_alliance -c "SELECT count(*) FROM tasks;"

# 5. 恢复应用服务
kubectl scale deployment -n expert-alliance \
  --replicas=3 -l app.kubernetes.io/part-of=expert-alliance

3.4 Redis 恢复

# 从 RDB 文件恢复
# 1. 停止 Redis
kubectl scale statefulset redis-master -n expert-alliance --replicas=0

# 2. 替换 dump.rdb 文件
kubectl cp dump.rdb redis-master-0:/data/dump.rdb -n expert-alliance

# 3. 启动 Redis
kubectl scale statefulset redis-master -n expert-alliance --replicas=1

# 4. 验证数据
kubectl exec -it redis-master-0 -n expert-alliance -- redis-cli DBSIZE

4. 故障处理 Runbook

🚨 RB-001: API 错误率飙升 P1

触发条件：HTTP 5xx 错误率 > 5% 持续 2 分钟

处理步骤：

  1. 确认影响范围：查看哪个服务的错误率上升
  2. 查看该服务最近 5 分钟日志，定位错误类型
  3. 检查下游依赖（数据库、Redis、NATS）是否正常
  4. 如果是单服务问题，尝试重启该服务：kubectl rollout restart deployment <svc>
  5. 如果是近期变更导致，立即回滚：helm rollback expert-alliance
  6. 如果是数据库问题，参见 RB-003
  7. 记录时间线，故障恢复后复盘

🚨 RB-002: 服务响应变慢 P2

触发条件：API P99 延迟 > 1s 持续 3 分钟

处理步骤：

  1. 查看是全链路慢还是特定接口慢
  2. 检查 CPU / 内存使用率，判断是否资源不足
  3. 检查数据库慢查询：是否有锁等待、全表扫描
  4. 检查 Redis 命中率：INFO stats 看 hit_rate
  5. 检查 NATS 消费延迟：是否有消息堆积
  6. 如果是资源不足，手动扩容：kubectl scale deployment <svc> --replicas=N
  7. 如果是慢查询导致，kill 慢查询或临时加索引

🚨 RB-003: 数据库连接池耗尽 P1

触发条件：数据库连接池使用率 > 95% 持续 1 分钟

处理步骤：

  1. 立即查看数据库活跃连接：SELECT * FROM pg_stat_activity WHERE state = 'active';
  2. 识别长时间运行的查询：WHERE now() - query_start > interval '5 minutes'
  3. 终止慢查询：SELECT pg_terminate_backend(pid);
  4. 临时增大连接池：调整服务的 DB_MAX_CONNECTIONS 并重启
  5. 如果是连接泄漏，重启对应服务释放连接
  6. 根本解决：优化慢查询、加索引、引入读写分离

🚨 RB-004: 任务大量堆积 P2

触发条件：待执行任务数 > 1000 持续 5 分钟

处理步骤：

  1. 检查 executor 服务副本数和资源使用率
  2. 查看是否是单任务占用了所有执行槽（大任务阻塞）
  3. 手动扩容 executor：kubectl scale deployment alliance-executor --replicas=N
  4. 检查下游专家服务是否响应变慢导致执行时间变长
  5. 检查 NATS 队列是否有异常消息
  6. 必要时降级非核心任务，优先保证高优先级任务执行

🚨 RB-005: Redis 故障 P2

触发条件：Redis 连接失败持续 30 秒

处理步骤：

  1. 确认 Redis Pod 状态：kubectl get pods -l app=redis
  2. 如果 Pod Crash，查看日志定位原因（OOM / 配置错误 / 磁盘满）
  3. 主节点故障，哨兵模式下自动切换主从，检查切换是否完成
  4. 如果是 OOM，检查是否有大 Key，临时增大内存
  5. Redis 短暂不可用时，服务会走降级逻辑（直查数据库）
  6. 恢复后监控缓存命中率回升情况

🚨 RB-006: 专家批量下线 P2

触发条件：5 分钟内专家下线数 > 10 个

处理步骤：

  1. 查看专家注册中心日志，确认下线原因
  2. 检查是否是网络分区导致心跳失败
  3. 检查专家服务所在基础设施是否有故障
  4. 如果是误报（网络闪断），专家会自动重连
  5. 如果是专家服务故障，通知对应团队排查
  6. 评估对任务成功率的影响，必要时降级

🚨 RB-007: NATS 消息堆积 P2

触发条件：消费者延迟 > 10000 条持续 2 分钟

处理步骤：

  1. 确认是哪个消费者延迟：nats consumer info
  2. 检查对应消费服务是否正常运行
  3. 查看消费服务日志，是否有处理错误导致重试
  4. 如果是消费能力不足，扩容对应服务
  5. 如果是毒消息（处理必失败），跳过该消息：nats consumer msg get --seq=N
  6. 堆积消化后监控延迟是否归零

5. 容量管理

5.1 容量规划公式

资源计算公式说明
API Gateway 实例数 ceil(QPS / 2000) 单实例 2000 QPS，70% 水位
Scheduler 实例数 ceil(任务创建 QPS / 500) 单实例 500 任务/秒
Executor 实例数 ceil(并发任务数 / 500) 单实例 500 并发任务
Agent 实例数 ceil(并发 Agent 数 / 200) 单实例 200 并发 Agent
数据库连接数 服务数 × 每服务连接池大小 建议总连接 < DB max_connections × 70%
Redis 内存 工作记忆 + 会话缓存 + 热点数据 × 2 预留 50% 余量防突增

5.2 扩容触发条件

  • CPU 使用率连续 10 分钟 > 70% → 扩容 50%
  • 内存使用率连续 10 分钟 > 75% → 扩容 50%
  • 任务队列深度 > 100 持续 5 分钟 → executor +2
  • P99 延迟连续 5 分钟 > 1s → 排查后按需扩容
  • 数据库连接池 > 80% → 增大连接池或读写分离

5.3 缩容触发条件

  • CPU 使用率连续 30 分钟 < 30% → 缩容 25%
  • 内存使用率连续 30 分钟 < 40% → 缩容 25%
  • 最低副本数不低于高可用要求（通常 ≥ 2）

6. 变更管理

6.1 变更类型

类型定义审批要求执行窗口
标准变更 版本升级、配置调整、常规扩缩容 值班负责人审批 工作日 10:00-16:00
紧急变更 线上故障修复、安全补丁 SRE Lead 审批（可后补） 随时，执行前通知
重大变更 架构调整、数据库迁移、跨区域切换 架构委员会评审 提前预约窗口，通常凌晨

6.2 变更前检查

变更前检查清单

  • 变更内容和影响范围已明确
  • 回滚方案已准备并验证可行
  • 已通知相关干系人
  • 选择了合适的变更窗口
  • 监控告警已确认可用
  • 备份已完成且验证可用
  • 值班人员已到位

6.3 变更后验证

  1. 服务是否正常启动，所有 Pod Ready
  2. 核心接口冒烟测试通过
  3. 错误率、延迟等核心指标正常
  4. 日志无异常错误
  5. 观察 30 分钟，确认无异常趋势
  6. 记录变更结果到变更管理系统

7. 安全运维

7.1 证书管理

  • TLS 证书有效期：建议 90 天，自动续期
  • JWT 签名密钥：每 90 天轮换一次，支持双密钥过渡
  • 数据库密码：每 90 天轮换，使用 Secret 管理
  • API Key：用户可自主吊销，定期审计活跃度

7.2 审计日志

以下操作强制记录审计日志：

  • 用户登录 / 登出 / Token 刷新
  • 专家注册 / 注销 / 配置变更
  • 任务创建 / 取消 / 结果获取
  • 管理后台操作（配置变更、用户管理）
  • 权限变更 / 角色分配

审计日志保留 180 天，不可删除不可修改，仅授权人员可查询。

7.3 数据脱敏

  • 日志中自动脱敏：手机号、邮箱、身份证号、Token
  • 监控指标不含用户数据
  • 链路追踪对用户输入做摘要处理

8.2 数据库操作

# 连接数据库
kubectl exec -it postgres-primary-0 -n expert-alliance -- psql -U expert_alliance

# 查看活跃连接
SELECT pid, state, query_start, query FROM pg_stat_activity WHERE state = 'active' ORDER BY query_start;

# 终止慢查询
SELECT pg_terminate_backend(pid);

# 查看表大小
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;

# 查看索引命中率
SELECT relname, idx_scan, seq_scan, round(100.0 * idx_scan / (idx_scan + seq_scan), 2) AS idx_hit_rate
FROM pg_stat_user_tables WHERE (idx_scan + seq_scan) > 0 ORDER BY idx_hit_rate ASC;
