1. 概述

1.1 设计目标

专家联盟系统是一个多专家协作求解平台，通过将领域专家以服务化形式接入联盟，由调度引擎根据任务特征智能匹配最优专家组合，协同完成复杂问题求解。本架构设计的核心目标是：

  • 高可扩展性 — 支持专家服务的即插即用接入，联盟规模可从数专家扩展到数千专家
  • 高可用性 — 核心服务无状态化，支持水平扩展，单节点故障不影响整体服务
  • 高性能 — 任务调度延迟 P99 < 200ms，单集群支持 10K 并发任务
  • 高可靠性 — 任务执行状态持久化，支持断点续跑和故障恢复
  • 可观测性 — 全链路 Trace、结构化日志、指标监控三位一体

1.2 设计原则

原则说明
单一职责 每个服务只聚焦一件事，避免服务膨胀。调度、执行、融合三者分离，各自独立扩展。
无状态优先 所有业务服务无状态化，状态外部化到存储层（PostgreSQL / Redis / 图存储），支持水平扩容和优雅迁移。
事件驱动 服务间通过事件总线异步解耦，降低同步调用链深度，提升系统韧性。
减少跳数 需要紧密协作的模块合并部署，匹配与图谱推理合并到调度服务，减少 RPC 开销。
协议分流 对外 HTTP REST，内部 gRPC，网关层做协议转换，兼顾外部兼容性与内部性能。
容错优先 每个服务都设计熔断器、限流、降级策略，故障时自动隔离而非雪崩。

1.3 适用范围

本文档适用于专家联盟系统 v3.0 版本的架构设计、开发实现、部署运维和技术评审。文档描述了从接入层到数据层的完整架构，包括服务拆分、接口协议、数据模型、非功能设计等核心内容。

1.4 术语定义

术语定义
Expert专家，以服务化形式接入联盟的领域能力提供者，可通过工具、Agent、人工等形态存在。
Task任务，用户提交的待求解问题，包含问题描述、约束条件、期望输出。
Plan执行计划，调度器为任务生成的专家组合和执行 DAG 图。
Fusion融合，多个专家结果的整合过程，支持投票、加权、辩论、迭代等多种策略。
Memory记忆，跨任务和会话的知识沉淀，分为工作记忆、会话记忆、长期记忆三层。
Sidecar边车，与主服务同 Pod 部署的辅助进程，本文指 Python AI 推理进程，通过 UDS 与 Rust 主进程通信。

2.2 服务拆分策略

v3.0 将 v2.0 的 5 服务拆分为 7 服务 + 1 Sidecar，拆分依据是职责单一性和扩容独立性：

服务 职责 状态 扩缩依据 v2 对应
gateway-http HTTP 协议接入：REST / JSON-RPC / WebSocket / MCP，认证、限流、审计 无状态 QPS gateway 拆分
gateway-grpc gRPC 协议接入：服务间路由、负载均衡、服务发现 无状态 gRPC QPS gateway 拆分
alliance-scheduler 任务管理、专家匹配（合并图谱推理）、计划生成、案例检索 无状态 任务创建 QPS alliance + registry 合并
alliance-executor DAG 执行引擎、节点调度、状态追踪、进度推送、人工干预 无状态 并发任务数 alliance 拆分
alliance-fusion 结果融合（6 种策略）、质量评估、迭代精炼 无状态 融合任务数 alliance 拆分
expert-registry 专家 CRUD、健康检查、工具自动发现、版本管理 无状态 注册请求量 registry（精简）
expert-agent Agent 运行时：ReAct 循环、工具调用、多轮对话 无状态 Agent 并发数 agent（重构）
expert-memory 统一记忆抽象：工作记忆 / 会话记忆 / 长期记忆 / 案例库 无状态 记忆读写 QPS 新增（统一抽象）
ai-inference Python Sidecar：LLM 推理、Embedding、RAG 检索 无状态 推理请求量 新增（Sidecar）

2.3 核心数据流

用户任务从提交到最终结果返回的完整数据流如下：

用户提交任务 │ ▼ [HTTP Gateway] ── 认证 / 限流 / 审计日志 │ ▼ [alliance-scheduler] ├─ 任务持久化（PostgreSQL） ├─ 意图理解 ──► [ai-inference Sidecar] ├─ 专家匹配 ──► [图存储] 图谱推理 ├─ 案例检索 ──► [expert-memory] └─ 生成 DAG 计划 │ ▼ [alliance-executor] ├─ DAG 拓扑排序 ├─ 节点调度（并行/串行/条件分支） ├─ 调用专家 ──► [expert-registry] 查找端点 │ └─► [expert-agent] 执行 │ └─► [ai-inference] 推理 ├─ 状态更新（PostgreSQL + Redis） └─ 进度事件 ──► [NATS] │ ▼ [alliance-fusion] ├─ 收集多专家结果 ├─ 融合策略执行（投票/加权/辩论/迭代） ├─ 质量评估 └─ 结果写入记忆 ──► [expert-memory] │ ▼ [HTTP Gateway] ──► WebSocket 推送结果 / 回调通知
关键设计：调度与执行分离使得调度服务可以用较少实例处理高 QPS 任务创建，执行服务可以按并发任务数独立扩容。融合服务独立部署，复杂融合计算不阻塞主执行链路。

3. 接入层设计

3.1 HTTP Gateway

HTTP Gateway 是联盟系统对外的统一入口，承载所有客户端流量，包括 REST API、JSON-RPC、WebSocket 和 MCP 协议。

核心职责

  • 协议终结 — 终结外部 HTTP/1.1、HTTP/2、WebSocket 连接，内部转 gRPC 调用
  • 认证鉴权 — JWT Token 验证、API Key 校验、租户隔离
  • 流量控制 — 令牌桶限流、并发数控制、熔断降级
  • 请求路由 — 根据 URL Path 路由到后端服务
  • 协议转换 — REST ↔ gRPC 转码，JSON ↔ Protobuf 序列化
  • 审计日志 — 记录所有出入请求，用于合规审计
  • 统一错误处理 — 标准化错误码和错误信息格式

路由表

路径前缀后端服务协议说明
/api/v1/tasksalliance-schedulerREST任务 CRUD
/api/v1/executionsalliance-executorREST执行控制
/api/v1/expertsexpert-registryREST专家管理
/api/v1/memoryexpert-memoryREST记忆查询
/ws/v1/tasksalliance-executorWebSocket进度推送
/mcp/v1expert-agentMCP工具调用协议
/jsonrpcalliance-schedulerJSON-RPC兼容旧版客户端

3.2 gRPC Gateway

gRPC Gateway 是内部服务间通信的入口，提供服务发现、负载均衡、流量镜像等能力。

核心职责

  • 服务发现 — 基于 etcd / Kubernetes Service 的服务注册发现
  • 负载均衡 — 支持轮询、加权轮询、一致性哈希等策略
  • 流量管理 — 灰度发布、A/B 测试、流量镜像
  • 链路追踪 — gRPC Interceptor 注入 Trace Context

3.3 协议分流策略

v3.0 采用双网关协议分流方案，解决了 v2.0 单端口混合协议带来的 ALPN 协商复杂度问题：

维度HTTP Gateway (:8080)gRPC Gateway (:50051)
使用场景外部客户端、浏览器、第三方集成内部服务间调用
协议HTTP/1.1, HTTP/2, WebSocketgRPC (HTTP/2)
序列化JSONProtobuf
性能中等，适合外部低 QPS高性能，适合内部高吞吐
认证方式JWT / API Key / OAuth2mTLS / Service Account

4. 联盟核心层设计

4.1 调度服务 (alliance-scheduler)

调度服务是联盟系统的"大脑"，负责任务的接收、解析、专家匹配和执行计划生成。

核心模块

模块职责关键技术
Task Manager 任务生命周期管理：创建、查询、取消、优先级调度 PostgreSQL 持久化 + Redis 队列
Intent Analyzer 任务意图理解：领域分类、复杂度评估、约束提取 LLM 分类 + 规则引擎
Expert Matcher 专家匹配：基于能力标签 + 图谱推理 + 历史表现的综合评分 图数据库 + 向量相似度 + 加权评分
Plan Generator 执行计划生成：DAG 拓扑、并行策略、依赖关系 拓扑排序 + 资源约束求解
Case Retriever 案例检索：相似历史任务查询、最佳实践推荐 向量检索 + 记忆服务

专家匹配算法

匹配评分采用四维加权模型：

score = w1 * capability_match    // 能力标签匹配度
      + w2 * graph_proximity     // 图谱邻域关联度
      + w3 * historical_perf     // 历史表现评分
      + w4 * availability        // 当前可用性

权重默认值：w1=0.35, w2=0.25, w3=0.25, w4=0.15
阈值：score >= 0.6 进入候选池，Top-K 返回

4.2 执行服务 (alliance-executor)

执行服务是联盟系统的"肌肉"，负责任务 DAG 的实际执行、节点调度和状态管理。

核心模块

模块职责关键技术
DAG Engine DAG 执行引擎：节点调度、依赖检查、并行控制 petgraph + tokio 异步
Node Executor 节点执行器：调用专家服务、超时控制、重试策略 gRPC 客户端 + 指数退避
State Tracker 状态追踪：执行状态持久化、断点续跑 PostgreSQL + Redis 缓存
Progress Pusher 进度推送：WebSocket 实时推送执行进度 WebSocket + NATS 广播
Human-in-the-loop 人工干预：暂停、恢复、人工审批节点 状态机 + 事件驱动

执行状态机

┌──────────┐ │ Pending │ 等待调度 └────┬─────┘ │ ▼ ┌──────────┐ ┌────►│ Running │ ────┐ │ └────┬─────┘ │ │ │ │ │ ▼ ▼ ┌────┴────┐ ┌────────┐ ┌────────┐ │ Paused │ │ Success│ │ Failed │ └────┬────┘ └────────┘ └───┬────┘ │ │ └──────────────────────┘ 人工恢复 / 自动重试 补充状态： - Scheduled：已入队，等待执行资源 - Skipped：条件分支跳过 - Timeout：执行超时 - Cancelled：用户取消

4.3 融合服务 (alliance-fusion)

融合服务负责多专家结果的整合与质量评估，是联盟系统产出最终答案的"裁判"。

融合策略

策略适用场景说明
Vote 投票 分类、决策类问题 多数票决，可选加权投票
Weighted Avg 加权平均 数值、评分类问题 按专家置信度加权求平均
Debate 辩论 开放性、争议性问题 多轮交叉质疑，逐步收敛
Iterative 迭代精炼 需要深度优化的问题 首轮结果输入下一轮，N 轮后输出
Ensemble 集成 复杂多面问题 各专家负责不同维度，拼接成完整答案
Best-of-N 选优 有客观评价标准的问题 用评估器打分，选最高分
融合策略选择由调度器在计划生成阶段根据任务类型自动指定，用户也可在提交任务时手动指定。

5. 能力服务层设计

5.1 专家注册服务 (expert-registry)

专家注册服务是联盟的"花名册"，管理所有接入联盟的专家元数据。

核心功能

  • 专家注册与注销：支持 HTTP/gRPC 双协议注册
  • 健康检查：心跳探活 + 主动探测，异常自动下线
  • 能力标签管理：专家能力的标签化描述和检索
  • 版本管理：专家多版本并存，灰度发布
  • 工具自动发现：专家启动时自动上报支持的工具列表

专家注册协议

message ExpertRegistration {
  string expert_id = 1;          // 专家唯一标识
  string display_name = 2;       // 显示名称
  string version = 3;            // 版本号
  ExpertType type = 4;           // 类型: AGENT / TOOL / HUMAN
  repeated string capabilities = 5; // 能力标签
  Endpoint endpoint = 6;         // 服务端点
  map<string, string> metadata = 7; // 扩展元数据
  int32 weight = 8;              // 权重 (1-100)
}

message Heartbeat {
  string expert_id = 1;
  int64 timestamp = 2;
  HealthStatus status = 3;       // HEALTHY / DEGRADED / UNHEALTHY
  float load = 4;                // 当前负载 0-1
}

5.2 Agent 运行时服务 (expert-agent)

Agent 运行时服务承载 Agent 形态的专家执行，实现 ReAct 推理循环和工具调用。

核心模块

模块职责
ReAct Engine推理-行动循环：Thought → Action → Observation → Reflection
Tool Router工具路由：根据 Action 名称分发到对应工具执行器
Conversation Manager会话管理：多轮对话上下文维护
Prompt Manager提示词管理：模板化、版本化、A/B 测试

ReAct 循环

┌─────────────────────────────────────────────────────┐ │ ReAct Loop │ │ │ │ User Input ──► Thought ──► Action ──► Observation │ │ ▲ │ │ │ └──── Reflection ◄───┘ │ │ │ │ │ max_iter? ├─► Final Answer │ │ └─► 继续循环 │ └─────────────────────────────────────────────────────┘

5.3 记忆服务 (expert-memory)

记忆服务提供统一的记忆抽象，解决了 v2.0 记忆数据分散存储的问题。

三层记忆模型

层级存储介质生命周期用途
工作记忆 Redis 任务级，任务结束即失效 当前任务上下文、中间结果、执行状态
会话记忆 Redis + PostgreSQL 会话级，可配置 TTL 多轮对话历史、用户偏好、会话上下文
长期记忆 PostgreSQL + 向量库 永久，可被遗忘 案例库、知识沉淀、专家经验

5.4 AI 推理 Sidecar (ai-inference)

AI 推理以 Python Sidecar 形式与 Agent 服务同 Pod 部署，通过 Unix Domain Socket 通信，避免网络开销。

Sidecar 职责

  • LLM 推理：调用大模型生成文本
  • Embedding：文本向量化，用于检索和匹配
  • RAG 检索：向量检索 + 重排
  • 函数调用解析：Tool Call 参数提取和校验
为什么用 Sidecar 而不是独立服务？AI 推理与 Agent 逻辑紧密耦合，每一次 ReAct 循环都需要多次推理调用。Sidecar 模式将网络调用变为本地 IPC，延迟从 ms 级降到 μs 级，且避免了独立服务的服务发现和负载均衡复杂度。

6. 数据架构设计

6.1 存储选型

存储系统用途选型理由
PostgreSQL 任务元数据、专家注册、执行状态、审计日志 强一致、事务支持、成熟稳定，适合结构化数据
图数据库 知识图谱、专家关系网络、案例关联 原生图存储，支持复杂关系查询和图算法
Redis 缓存、会话、限流计数、工作记忆 超低延迟，丰富数据结构，支持过期和持久化
NATS 事件总线、消息队列、进度广播 轻量高性能，支持 Pub/Sub 和 JetStream 持久化
对象存储 (S3/MinIO) 大文件、任务产物、模型文件 无限扩展，低成本，适合非结构化大数据

6.2 核心数据模型

任务表 (tasks)

  description   TEXT,
  status        VARCHAR(32) NOT NULL,  -- pending/running/completed/failed/cancelled
  priority      INT NOT NULL DEFAULT 5, -- 1-10
  plan_id       UUID REFERENCES plans(id),
  fusion_strategy VARCHAR(32) DEFAULT 'vote',
  input_schema  JSONB,
  output_schema JSONB,
  tags          VARCHAR(64)[],
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  completed_at  TIMESTAMPTZ
);

8. 非功能性设计

8.1 高可用设计

无状态服务

所有业务服务均设计为无状态，状态外部化到存储层。支持水平扩展，节点故障时请求自动转移到健康节点。

多副本部署

服务最小副本推荐副本扩缩策略
gateway-http23+CPU > 60% 自动扩容
gateway-grpc23+QPS 阈值扩容
alliance-scheduler23任务队列长度
alliance-executor24+并发任务数
alliance-fusion23融合队列长度
expert-registry22静态，按需扩容
expert-memory23QPS 阈值

熔断与降级

  • 熔断器 — 每个下游依赖独立熔断器，错误率超阈值自动熔断，半开探测恢复
  • 降级策略 — 非核心功能降级：如专家匹配失败时退化为随机分配 + 标签过滤
  • 限流 — 令牌桶算法，按租户和用户维度限流，防止单一用户占满资源
  • 超时控制 — 每层调用设置独立超时，全局超时链防止慢请求堆积

8.3 安全设计

认证与授权

  • 外部调用：JWT Bearer Token + API Key 双模式
  • 内部服务：mTLS + Service Account
  • 租户隔离：所有数据行级租户隔离
  • RBAC + ABAC 混合权限模型

数据安全

  • 传输加密：TLS 1.3，全链路 HTTPS/gRPC-TLS
  • 存储加密：敏感字段 AES-256 加密，支持国密 SM4
  • 数据脱敏：日志和监控中自动脱敏敏感信息
  • 审计日志：所有操作留痕，不可篡改

9. 技术决策记录 (ADR)

编号决策理由与影响
ADR-001 主语言选择 Rust，AI 推理用 Python Sidecar Rust 提供内存安全和高性能，适合核心调度和执行引擎；Python 生态丰富适合 AI 推理。Sidecar 模式兼顾性能和生态。
ADR-002 微服务架构，7 服务拆分 v2.0 5 服务存在职责过重问题，v3.0 按职责单一原则拆分为 7 服务，各自独立扩容。代价是增加了部署复杂度和运维成本。
ADR-003 专家匹配与图谱推理合并到调度服务 匹配需要频繁调用图谱推理，合并部署减少一次 RPC 跳数，降低延迟约 30-50ms。代价是调度服务依赖图数据库。
ADR-004 事件驱动 + NATS 作为消息总线 服务间异步解耦，降低同步调用链深度，提升系统韧性。NATS 轻量高性能，JetStream 提供持久化保证。
ADR-005 双网关协议分流（HTTP + gRPC） 解决 v2.0 单端口混合协议的 ALPN 协商复杂度，外部兼容性与内部性能兼顾。
ADR-006 统一记忆服务，三层记忆抽象 解决 v2.0 记忆数据分散存储的问题，统一抽象降低查询和维护复杂度。
