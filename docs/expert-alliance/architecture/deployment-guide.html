  --docker-server=registry.example.com \
  --docker-username=your-username \
  --docker-password=your-password \
  -n expert-alliance

3. 快速部署（Helm 一键部署）

使用 Helm Chart 一键部署专家联盟系统到 Kubernetes 集群。

1 添加 Helm 仓库
# 添加专家联盟 Helm 仓库
helm repo add expert-alliance https://charts.example.com/expert-alliance
helm repo update

# 查看可用版本
helm search repo expert-alliance --versions
2 准备自定义配置

创建 custom-values.yaml 文件，配置数据库、Redis 等外部依赖连接信息：

# custom-values.yaml
global:
  imageRegistry: registry.example.com
  imagePullSecrets:
    - name: registry-secret

  database:
    host: postgres-primary.db.svc.cluster.local
    port: 5432
    name: expert_alliance
    user: expert_alliance
    existingSecret: db-credentials
    passwordKey: password

  redis:
    host: redis-master.cache.svc.cluster.local
    port: 6379
    existingSecret: redis-credentials
    passwordKey: password

  nats:
    servers:
      - nats://nats-0.nats-headless.mq.svc.cluster.local:4222
      - nats://nats-1.nats-headless.mq.svc.cluster.local:4222

  graphDb:
    endpoint: http://graph-db.graph.svc.cluster.local:7687
    existingSecret: graphdb-credentials

gatewayHttp:
  replicaCount: 2
  service:
    type: LoadBalancer

allianceScheduler:
  replicaCount: 2

allianceExecutor:
  replicaCount: 2

allianceFusion:
  replicaCount: 2
3 执行部署
# 安装（首次部署）
helm install expert-alliance expert-alliance/expert-alliance \
  --namespace expert-alliance \
  --create-namespace \
  --values custom-values.yaml \
  --version 3.0.0

# 等待部署完成
kubectl wait --for=condition=ready pod -l app.kubernetes.io/part-of=expert-alliance -n expert-alliance --timeout=300s

# 查看部署状态
helm status expert-alliance -n expert-alliance
kubectl get pods -n expert-alliance
kubectl get svc -n expert-alliance
首次部署会执行数据库初始化（建表、索引、初始数据），约需 1-2 分钟。初始化 Job 完成后服务才会启动。

4. 分步部署详解

4.1 部署中间件

如果中间件还未部署，可使用以下方式快速部署（开发测试环境）：

# PostgreSQL
helm install postgres oci://registry-1.docker.io/bitnamicharts/postgresql \
  -n expert-alliance --create-namespace \
  --set auth.username=expert_alliance \
  --set auth.password=change-me \
  --set auth.database=expert_alliance

# Redis
helm install redis oci://registry-1.docker.io/bitnamicharts/redis \
  -n expert-alliance \
  --set auth.password=change-me

# NATS
helm install nats nats/nats -n expert-alliance \
  --set nats.jetstream.enabled=true \
  --set cluster.enabled=true \
  --set cluster.replicas=3
生产环境请使用独立部署的高可用中间件集群，不建议使用 Helm 快速部署的单节点实例。

4.2 初始化数据库

# 执行数据库初始化脚本
kubectl run db-init \
  --image=registry.example.com/expert-alliance/db-init:3.0.0 \
  --env="DB_HOST=postgres-primary" \
  --env="DB_USER=expert_alliance" \
  --env="DB_PASSWORD=$(kubectl get secret postgres -o jsonpath='{.data.password}' | base64 -d)" \
  --env="DB_NAME=expert_alliance" \
  -n expert-alliance

# 等待初始化完成
kubectl wait --for=condition=complete job/db-init -n expert-alliance --timeout=120s

# 检查初始化结果
kubectl logs job/db-init -n expert-alliance | tail -20

4.3 部署核心服务

按依赖顺序依次部署各服务：

  1. expert-registry — 专家注册中心（无外部依赖）
  2. expert-memory — 记忆服务（依赖 PostgreSQL + Redis）
  3. alliance-scheduler — 调度服务（依赖注册中心 + 图数据库）
  4. expert-agent — Agent 运行时（依赖调度服务 + Sidecar）
  5. alliance-executor — 执行服务（依赖调度服务 + Agent）
  6. alliance-fusion — 融合服务（依赖执行服务）
  7. gateway-http / gateway-grpc — 网关（依赖所有后端服务）
使用 Helm 伞图部署时会自动处理依赖顺序，无需手动分步。

4.4 配置 Ingress

# 示例：使用 Nginx Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: expert-alliance-gateway
  namespace: expert-alliance
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/enable-cors: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - alliance.example.com
      secretName: alliance-tls
  rules:
    - host: alliance.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: expert-alliance-gateway-http
                port:
                  number: 8080
          - path: /ws
            pathType: Prefix
            backend:
              service:
                name: expert-alliance-gateway-http
                port:
                  number: 8080

5.3 配置热更新

支持运行时动态调整的配置（通过配置中心 API）：

6. 高可用部署

6.1 多可用区部署

生产环境建议跨可用区部署，每个服务的 Pod 分布在不同 AZ：

# Pod 反亲和性配置示例
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: alliance-scheduler
          topologyKey: topology.kubernetes.io/zone

  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: node-role.kubernetes.io/worker
              operator: Exists

6.2 自动扩缩容 (HPA)

# 执行服务 HPA 示例
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

6.3 健康检查

所有服务均配置了启动探针、存活探针和就绪探针：

探针类型端口路径说明
启动探针8080/health/startup服务初始化完成，最长等待 60s
存活探针8080/health/live进程存活检查，失败会重启
就绪探针8080/health/ready服务就绪检查，失败停止流量

6.4 优雅关闭

服务支持优雅关闭，终止信号到达后：

  1. 停止接收新请求（就绪探针失败）
  2. 等待正在执行的任务完成（最长 300s）
  3. 持久化状态到数据库
  4. 关闭连接，退出进程
# terminationGracePeriod 设置
terminationGracePeriodSeconds: 300

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15 && kill -TERM 1"]

7. 升级与回滚

7.1 版本升级流程

使用 Helm 进行灰度升级，分四阶段逐步放量：

1 备份数据
# 备份数据库
kubectl exec -it postgres-primary-0 -- pg_dump -U expert_alliance expert_alliance > backup-$(date +%Y%m%d).sql

# 备份 Redis
kubectl exec -it redis-master-0 -- redis-cli BGSAVE
2 灰度发布（金丝雀）
# 1% 流量到新版本
helm upgrade expert-alliance expert-alliance/expert-alliance \
  --namespace expert-alliance \
  --values custom-values.yaml \
  --version 3.1.0 \
  --set canary.enabled=true \
  --set canary.weight=1

# 观察 10 分钟，无异常则逐步放量
# 10% → 50% → 100%
helm upgrade ... --set canary.weight=10
helm upgrade ... --set canary.weight=50
helm upgrade ... --set canary.weight=100
3 全量发布
# 金丝雀验证通过后，正式全量升级
helm upgrade expert-alliance expert-alliance/expert-alliance \
  --namespace expert-alliance \
  --values custom-values.yaml \
  --version 3.1.0 \
  --set canary.enabled=false

# 确认升级完成
kubectl rollout status deployment/expert-alliance-scheduler -n expert-alliance
helm history expert-alliance -n expert-alliance

7.2 回滚流程

升级过程中如出现严重问题（错误率飙升、核心功能不可用），立即执行回滚。 
# 查看历史版本
helm history expert-alliance -n expert-alliance

# 回滚到上一个版本
helm rollback expert-alliance -n expert-alliance

# 回滚到指定版本
helm rollback expert-alliance <REVISION> -n expert-alliance

# 验证回滚结果
helm status expert-alliance -n expert-alliance
kubectl get pods -n expert-alliance

7.3 数据库迁移回滚

如果升级涉及数据库 Schema 变更，需手动回滚数据：

# 从备份恢复数据库
kubectl exec -i postgres-primary-0 -- psql -U expert_alliance expert_alliance < backup-YYYYMMDD.sql

# 验证数据完整性
kubectl exec -it postgres-primary-0 -- psql -U expert_alliance -c "SELECT count(*) FROM tasks;"

9. 常见问题

9.1 Pod 启动失败

症状：Pod 状态为 CrashLoopBackOff

排查步骤：

  1. 查看 Pod 事件：kubectl describe pod <pod-name>
  2. 查看容器日志：kubectl logs <pod-name> --previous
  3. 检查配置文件是否正确：kubectl get configmap
  4. 检查 Secret 是否存在：kubectl get secret
  5. 检查数据库连接是否可达

9.2 服务间通信失败

症状：日志显示 gRPC 连接错误、超时

常见原因：

  • Service 名称解析失败 — 检查 DNS 和 Service 配置
  • 网络策略拦截 — 检查 NetworkPolicy 是否放行
  • 目标服务未就绪 — 检查对端 Pod 状态
  • mTLS 证书问题 — 检查证书有效期和挂载

9.3 任务一直 pending

症状：任务创建后长时间处于 pending 状态

排查步骤：

  1. 检查 scheduler 服务是否正常
  2. 查看是否有匹配的在线专家
  3. 检查 executor 服务的并发数是否已满
  4. 查看 NATS 消息队列是否有堆积

9.4 数据库连接池耗尽

症状：日志报 "connection pool exhausted" 错误

解决方法：

  • 增大连接池大小：调整 DB_MAX_CONNECTIONS 环境变量
  • 检查是否有连接泄漏：慢查询导致连接未释放
  • 增加数据库 max_connections 配置
  • 考虑引入读写分离，读请求走只读副本

9.5 Redis 连接失败

症状：i/o timeout / connection refused

解决方法：

  • 检查 Redis 服务是否正常运行
  • 验证密码是否正确
  • 检查网络连通性：telnet redis-host 6379
  • 确认 Redis 配置了持久化（否则重启后数据丢失）
