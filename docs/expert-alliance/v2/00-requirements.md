## 一、项目背景与目标

### 1.1 背景

infotopograph 平台已具备知识图谱存储、AI 推理、数据治理、流程自动化等 31 个微服务能力，但这些能力以**工具集合**形式存在，用户需要理解每个工具的用法、手动编排调用流程、自行处理跨服务数据流转。

**专家联盟（Expert Alliance）** 的目标是将工具集合升级为**智能团队**：用户只需描述目标，系统自动识别所需专家、编排协作流程、调用底层能力、融合多方结果，端到端交付复杂任务成果。

### 1.2 核心目标

| 维度 | 目标 | 衡量标准 |
|------|------|----------|
| **智能化** | 自然语言描述目标 → 自动协作交付 | 任务自动完成率 ≥ 80% |
| **专业化** | 10+ 领域专家，覆盖图谱/AI/数据/安全/运维 | 专家覆盖领域 ≥ 10 个 |
| **协作化** | 多专家自动协作（串行/并行/辩论/分层/迭代） | 支持 ≥ 6 种协作模式 |
| **可扩展** | 新专家即插即用，零代码注册 | 新专家上线时间 ≤ 1 小时 |
| **可追溯** | 完整协作链路记录，每个决策可解释 | 100% 任务可追溯 |
| **企业级** | 多租户/安全/合规/高可用/可观测 | SLA 99.95%，等保三级 |

### 1.3 范围界定

**包含**：
- 专家注册/发现/匹配
- 协作任务编排/执行/监控
- 多专家协作（6种模式）
- 结果融合（6种策略）
- 协作记忆与案例库
- 知识图谱关联关系驱动
- 多协议接入（gRPC/JSON-RPC/MCP/REST/WebSocket）
- 多租户隔离
- 企业级安全/可观测/弹性

**不包含**：
- 底层微服务能力开发（复用现有31个服务）
- AI 模型训练（复用 mox-ai-svc + Python sidecar）
- 前端 UI 开发（由前端团队负责，本文档定义 API 契约）

## 三、业务需求

### 3.1 核心业务场景

#### 场景一：智能图谱构建
**用户**：数据工程师
**诉求**："把这一批 CSV 数据构建成知识图谱，并做质量评估和安全审计"
**业务价值**：将原本需要 3 个工具手动操作、耗时 2 小时的工作，压缩为 1 次自然语言请求、5 分钟自动完成

#### 场景二：跨领域智能分析
**用户**：业务分析师
**诉求**："分析客户流失原因，结合历史数据和客户反馈，给出可执行的挽回方案"
**业务价值**：自动协调数据分析/AI推理/搜索推荐三个专家，输出综合分析报告

#### 场景三：自动化数据治理
**用户**：数据治理专员
**诉求**："对新接入的数据源做完整的数据治理流程，输出治理报告"
**业务价值**：自动执行数据标准检查/质量评估/敏感数据识别/元数据提取/血缘分析

#### 场景四：AI 辅助开发
**用户**：开发者
**诉求**："根据需求描述，生成流程图、代码、测试用例，并验证可运行性"
**业务价值**：协调流程设计/代码生成/测试验证专家，实现需求到可运行代码的自动化

#### 场景五：安全合规审计
**用户**：安全合规官
**诉求**："对整个平台做一次全面的安全合规审计，输出风险清单和整改建议"
**业务价值**：自动协调权限审计/数据脱敏检查/合规规则校验/漏洞扫描专家

## 四、功能需求

### 4.1 专家注册中心

**FR-REG-001**：系统支持通过 JSON/YAML/Proto 定义专家，包含名称/描述/角色/领域/能力/工具/性格/记忆配置
**FR-REG-002**：注册时自动验证工具存在性（对应微服务+gRPC方法是否存在）
**FR-REG-003**：注册时自动验证能力完整性（每个能力是否绑定了至少一个工具）
**FR-REG-004**：支持专家版本管理（semver），支持灰度发布新版本
**FR-REG-005**：支持专家状态管理（active/inactive/maintenance/deprecated）
**FR-REG-006**：支持专家健康检查（心跳/成功率/延迟/错误率）
**FR-REG-007**：支持按领域/能力/名称/状态搜索专家
**FR-REG-008**：支持按任务描述自动匹配专家（图谱推理+评分排序）
**FR-REG-009**：系统内置 10 个专家，租户可创建自定义专家
**FR-REG-010**：专家注册事件发布（NATS），联盟调度器自动更新缓存（此处"调度器"指专家匹配与任务调度组件，对应 `TaskScheduler`）

### 4.2 协作任务管理

**FR-TASK-001**：支持通过自然语言描述创建协作任务
**FR-TASK-002**：支持指定协作模式（auto/serial/parallel/debate/hierarchical/iterative/dynamic）
**FR-TASK-003**：支持指定/排除特定专家
**FR-TASK-004**：支持设置任务约束（超时/预算/质量要求/最大专家数）
**FR-TASK-005**：支持任务取消（正在执行的节点优雅终止）
**FR-TASK-006**：支持任务查询（状态/进度/执行详情/结果）
**FR-TASK-007**：支持任务列表（按状态/时间/租户/用户分页筛选）
**FR-TASK-008**：支持任务进度实时推送（WebSocket/SSE）
**FR-TASK-009**：支持失败节点重试（指定节点/全部失败节点）
**FR-TASK-010**：支持人工干预（暂停/修改计划/指定专家/跳过节点）
**FR-TASK-011**：支持任务结果导出（JSON/PDF/Markdown）
**FR-TASK-012**：支持任务模板保存与复用

### 4.3 协作编排引擎

**FR-ORCH-001**：支持自动专家识别（任务解析→领域提取→能力匹配→图谱推理→评分排序）
**FR-ORCH-002**：支持自动协作计划生成（DAG：节点=专家调用，边=数据依赖）
**FR-ORCH-003**：支持串行模式（Pipeline：A→B→C）
**FR-ORCH-004**：支持并行模式（Fan-out/Fan-in：多专家同时执行→结果汇总）
**FR-ORCH-005**：支持辩论模式（多专家对同一问题给出观点→互相质询→仲裁）
**FR-ORCH-006**：支持分层模式（协调专家分解任务→子专家执行→协调专家汇总）
**FR-ORCH-007**：支持迭代模式（专家A生成→专家B审核→不通过返回A重做）
**FR-ORCH-008**：支持动态模式（根据中间结果动态决定下一步调用哪个专家）
**FR-ORCH-009**：支持条件节点（if/else 分支，根据上游结果选择路径）
**FR-ORCH-010**：支持循环节点（for/while，批量处理或迭代直到满足条件）
**FR-ORCH-011**：支持人工审核节点（HITL：暂停等待人工确认后继续）
**FR-ORCH-012**：支持 DAG 拓扑排序与并行调度
**FR-ORCH-013**：支持依赖检查（上游完成才启动下游）
**FR-ORCH-014**：支持动态重编排（节点失败后自动选择替代专家或调整计划）
**FR-ORCH-015**：支持协作计划可视化（前端展示 DAG 图+实时状态）

### 4.4 专家 Agent 运行时

**FR-AGENT-001**：每个专家 Agent 遵循 ReAct 循环（理解→规划→执行→观察→审核）
**FR-AGENT-002**：支持工具调用（通过 gRPC 调用底层微服务，带超时/重试/熔断）
**FR-AGENT-003**：支持 AI 推理调用（通过 mox-ai-svc，支持流式生成）
**FR-AGENT-004**：支持知识检索（通过 mox-graph-svc/mox-search-svc）
**FR-AGENT-005**：支持工作记忆（当前任务上下文/中间结果/推理过程）
**FR-AGENT-006**：支持专家思考过程记录（可解释性，每步推理可追溯）
**FR-AGENT-007**：支持流式输出（AI生成过程实时推送给前端）
**FR-AGENT-008**：支持工具调用结果观察与反思（失败后自动调整策略）
**FR-AGENT-009**：支持专家性格配置（推理风格/详细程度/保守程度）
**FR-AGENT-010**：支持专家实例池化（复用 Agent 实例，减少初始化开销）

### 4.5 结果融合

**FR-FUSION-001**：支持多数投票策略（分类/判断类任务，取多数专家结果）
**FR-FUSION-002**：支持加权投票策略（按专家置信度/历史成功率加权）
**FR-FUSION-003**：支持拼接合并策略（各专家负责不同部分，拼接为完整输出）
**FR-FUSION-004**：支持择优选择策略（按评分选择最优结果）
**FR-FUSION-005**：支持辩论仲裁策略（专家互相质询，协调专家仲裁）
**FR-FUSION-006**：支持迭代精炼策略（一个专家生成，另一个审核修改）
**FR-FUSION-007**：支持融合结果质量自动评估（完整性/一致性/准确性）
**FR-FUSION-008**：支持融合过程可追溯（记录每个专家的贡献度和原始结果）

### 4.6 协作记忆与案例库

**FR-MEM-001**：工作记忆：存储当前任务的上下文/中间结果/推理过程，任务结束后归档
**FR-MEM-002**：会话记忆：存储用户的历史任务/偏好/常用专家，TTL 24小时
**FR-MEM-003**：长期记忆：存储历史任务/案例/专家协作统计，永久保存
**FR-MEM-004**：案例自动提升：任务评分 ≥ 4.0 自动提升为案例，写入知识图谱
**FR-MEM-005**：案例检索：输入新任务，通过图谱相似度匹配找到最相关的历史案例
**FR-MEM-006**：案例复用：参考历史案例的专家组合/协作模式/融合策略
**FR-MEM-007**：专家协作统计：每次任务更新专家间的 collaborates_with 边（频率/成功率/平均时长）
**FR-MEM-008**：专家能力统计：每次任务更新 has_capability 边的使用次数/成功率
**FR-MEM-009**：用户偏好学习：记录用户常用专家/协作模式/输出格式，自动推荐
**FR-MEM-010**：记忆清理：工作记忆任务结束归档，会话记忆 TTL 过期，长期记忆支持归档

### 4.7 知识图谱关联关系

**FR-KG-001**：维护六元关联图谱（Expert/Capability/Domain/Tool/Data/Case 七种顶点）
**FR-KG-002**：维护 12 种关联边（has_capability/operates_in/requires_tool/operates_on/contains_data/solved_by/used_capability/similar_to/collaborates_with/depends_on/subdomain_of/executed_by）
**FR-KG-003**：所有关联边带权重属性（熟练度/成功率/频率/贡献度/相似度）
**FR-KG-004**：图谱驱动专家匹配（多跳遍历+综合评分）
**FR-KG-005**：图谱驱动协作编排（通过 collaborates_with/depends_on 推荐专家组合）
**FR-KG-006**：图谱驱动结果融合（通过 solved_by/used_capability 评估专家贡献）
**FR-KG-007**：图谱持续学习（每次任务完成自动更新边权重）
**FR-KG-008**：图谱初始化（系统启动时创建领域树/能力定义/工具注册/内置专家）
**FR-KG-009**：图谱工具自动注册（从 gRPC 服务反射自动发现工具，创建 Tool 节点）
**FR-KG-010**：图谱多租户隔离（系统专家共享，自定义专家/案例按租户隔离）

### 4.8 多协议接入

**FR-PROTO-001**：REST API（/api/v1/expert/*），兼容现有前端
**FR-PROTO-002**：gRPC（内部服务间通信，高性能强类型）
**FR-PROTO-003**：JSON-RPC 2.0（/rpc，支持 HTTP + WebSocket）
**FR-PROTO-004**：JSON-RPC → gRPC 自动转码（基于 .proto 反射）
**FR-PROTO-005**：MCP 协议（/mcp，AI 模型工具调用标准，基于 JSON-RPC）
**FR-PROTO-006**：MCP tools/list 自动从 gRPC 服务发现工具
**FR-PROTO-007**：MCP tools/call 通过 JSON-RPC→gRPC 转码调用后端
**FR-PROTO-008**：WebSocket（/ws，实时进度推送/流式输出）
**FR-PROTO-009**：单端口多协议共存（Content-Type/Path 路由分发）
**FR-PROTO-010**：协议错误码统一映射（gRPC Status ↔ JSON-RPC Error ↔ HTTP Status）

## 五、非功能需求

### 5.1 性能

| 指标 | 目标 | 说明 |
|------|------|------|
| 任务创建响应时间 | < 500ms | 从请求到返回 task_id |
| 专家匹配时间 | < 200ms | 图谱推理+评分排序 |
| 协作计划生成时间 | < 300ms | DAG 生成 |
| 单节点执行延迟 | P99 < 2s | 不含 AI 推理时间 |
| AI 流式首包延迟 | < 500ms | 从调用到第一个 token |
| 任务进度推送延迟 | < 1s | 从状态变更到前端收到 |
| 系统并发任务数 | ≥ 100 | 单集群同时执行的任务数 |
| 单任务最大专家数 | ≤ 20 | 防止过度编排 |

### 5.2 可用性

| 指标 | 目标 |
|------|------|
| 服务可用性 | 99.95%（月停机 < 22 分钟） |
| 故障恢复时间（RTO） | < 15 分钟 |
| 数据恢复点（RPO） | < 1 分钟 |
| 单服务故障影响 | 不影响其他服务（故障隔离） |
| 专家故障自动切换 | 自动选择替代专家或降级 |

### 5.3 可扩展性

| 维度 | 目标 |
|------|------|
| 专家数量 | 支持 100+ 专家（内置+自定义） |
| 租户数量 | 支持 1000+ 租户 |
| 单租户用户数 | 支持 10000+ 用户 |
| 水平扩展 | 所有服务无状态，可水平扩缩 |
| 新专家上线 | ≤ 1 小时（零代码注册） |
| 新协议接入 | 插件化，不影响现有协议 |

### 5.4 安全合规

| 维度 | 要求 |
|------|------|
| 认证 | JWT + OIDC/SSO + MFA |
| 授权 | RBAC + ABAC + 数据权限 |
| 传输加密 | TLS 1.3（外部）+ mTLS（服务间） |
| 存储加密 | 敏感字段加密（AES-256/国密SM4） |
| 密码存储 | Argon2id 哈希 |
| 审计日志 | 不可篡改，全操作记录 |
| 多租户隔离 | L1 逻辑（默认）/ L2 Schema / L3 集群 |
| 数据脱敏 | 敏感字段自动脱敏（手机号/身份证/邮箱） |
| 合规标准 | 等保三级 / GDPR / 个人信息保护法 |
| 密钥管理 | KMS（密钥轮换/审计/备份） |

### 5.5 可观测性

| 维度 | 要求 |
|------|------|
| 日志 | 结构化 JSON，聚合到 Loki，可检索 |
| 指标 | Prometheus 采集，Grafana 仪表盘，RED+USE+业务指标 |
| 链路追踪 | OpenTelemetry + Jaeger，全链路 Trace |
| 告警 | P0-P3 四级，多渠道通知（飞书/短信/邮件/PagerDuty） |
| 任务级可观测 | 每个任务的 DAG 执行图/节点状态/耗时/错误/专家思考 |
| 专家级可观测 | 每个专家的调用次数/成功率/平均延迟/错误分布 |

### 5.6 弹性容错

| 机制 | 要求 |
|------|------|
| 限流 | 网关层（租户/用户/接口）+ 服务层（并发控制） |
| 熔断 | gRPC 客户端三态熔断器（Closed/Open/HalfOpen） |
| 降级 | 默认值/缓存/简化功能/排队/限流 五种降级策略 |
| 重试 | 指数退避+抖动，最多3次，幂等性保证 |
| 超时 | 多层级超时（网关/服务间/数据库/缓存/第三方） |
| 舱壁 | 资源隔离（线程池/连接池/信号量） |
| 死信队列 | 消息重试超限转入 DLQ，人工处理+告警 |
| 专家故障切换 | 节点失败自动选择替代专家或降级策略 |

## 六、用户故事

### 6.1 终端用户

**US-001**：作为数据工程师，我希望用自然语言描述"把 CSV 构建成知识图谱"，系统自动完成，这样我不需要学习多个工具的用法。

**US-002**：作为业务分析师，我希望系统能自动协调多个领域专家分析复杂问题，这样我不需要手动切换工具和整合结果。
**验收标准**：输入分析需求 → 系统自动识别所需专家 → 并行/串行执行 → 输出综合报告

**US-003**：作为用户，我希望能实时看到协作过程（哪个专家在做什么/进度如何/中间结果），这样我能了解系统在做什么并及时干预。
**验收标准**：WebSocket 实时推送 DAG 执行状态/专家思考/中间结果

### 6.2 领域专家

**US-004**：作为领域专家，我希望能通过配置文件注册我的专业能力，这样我不需要写代码就能加入联盟。
**验收标准**：编写 YAML 专家定义 → 调用注册 API → 5分钟内可被任务匹配到

**US-005**：作为专家，我希望我的贡献能被量化和记录，这样我能了解我的能力在哪些场景下效果最好。
**验收标准**：专家仪表盘展示调用次数/成功率/平均延迟/贡献度/历史案例

### 6.3 平台管理员

**US-006**：作为平台管理员，我希望能管理所有专家的生命周期（注册/更新/下线/灰度），这样我能控制平台能力。
**验收标准**：专家管理 CRUD + 版本管理 + 灰度发布 + 状态管理

**US-007**：作为管理员，我希望系统出问题时能快速定位（哪个服务/哪个专家/哪个节点），这样 MTTR 能降到最低。

### 6.4 开发者

**US-008**：作为开发者，我希望通过 MCP 协议将专家联盟能力接入我的 AI 客户端（Claude/Cursor），这样我能在 IDE 里直接调用。
**验收标准**：配置 MCP Server URL → Claude Desktop 能看到工具列表 → 调用工具返回结果

**US-009**：作为开发者，我希望通过 gRPC/JSON-RPC/REST 多种协议接入，这样我能根据场景选择最合适的协议。
**验收标准**：四种协议都能调用相同的后端能力，结果一致

## 七、约束与假设

### 7.1 约束

| 约束 | 说明 |
|------|------|
| **全维 Rust** | 后端核心代码必须用 Rust 开发（AI 推理 sidecar 除外，用 Python） |
| **核心自研** | 核心功能（图存储/协作引擎/专家运行时）必须自研，不依赖第三方成品 |
| **复用现有服务** | 底层能力复用现有31个微服务，不重复开发 |
| **gRPC 主干** | 内部服务间通信必须用 gRPC（tonic + Protobuf） |
| **多租户** | 必须支持多租户，L1 逻辑隔离为默认 |
| **图存储零修改** | 自研图存储引擎代码不修改，仅增加 gRPC 薄包装层 |

### 7.2 假设

| 假设 | 说明 |
|------|------|
| 微服务架构按计划实施 | 假设 docs/microservices/ 中的架构优化按路线图推进 |
| gRPC 服务间通信就绪 | 假设所有底层服务已 gRPC 化（或在专家联盟上线前完成） |
| K8s 集群就绪 | 假设生产环境有 K8s 集群，支持 HPA/PDB/拓扑分布 |
| NATS JetStream 就绪 | 假设事件总线 NATS JetStream 已部署 |
| PostgreSQL/Redis/MinIO 就绪 | 假设基础数据存储已部署 |
| AI 推理服务就绪 | 假设 mox-ai-svc + Python sidecar 已可用 |
