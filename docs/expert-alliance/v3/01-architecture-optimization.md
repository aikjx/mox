# 01 - 架构优化分析

> 版本：v3.0 | 日期：2026-08-26 | 状态：优化定稿
>
> 基于：v2.0 企业级全维版

## 一、v2 架构复盘与问题识别

### 1.1 v2 架构回顾

v2 采用 5 服务拆分：
- `mox-gateway-svc`：多协议接入
- `mox-expert-alliance-svc`：联盟核心（调度/编排/执行/融合/记忆）
- `mox-expert-registry-svc`：专家注册/匹配/健康检查
- `mox-expert-agent-svc`：Agent 运行时（ReAct 循环）
- `mox-expert-kg-svc`：知识图谱/关联推理/案例库

### 1.2 问题识别（全维审计）

| # | 问题 | 严重度 | 影响 | 根因 |
|---|------|--------|------|------|
| P1 | alliance-svc 职责过重（5大能力耦合） | 高 | 单点瓶颈/部署不灵活/扩容粒度粗 | 把调度/编排/执行/融合/记忆全放一个服务 |
| P2 | agent-svc 有状态（Agent实例/会话），但用 Deployment | 中 | Pod 重启丢失会话/无法优雅迁移 | Agent 实例存在内存中，未外部化 |
| P3 | kg-svc 与 graph-storage 双层图谱查询 | 中 | 延迟增加/缓存不一致 | kg-svc 做一层封装再调 graph-storage，多一跳 |
| P4 | 协作记忆三层（工作/会话/长期）分散在 alliance + Redis + 图谱 | 中 | 一致性难保证/查询复杂 | 记忆数据分散存储，无统一抽象 |
| P5 | 专家匹配在 registry-svc，但图谱推理在 kg-svc | 中 | 两次 RPC 调用/匹配延迟高 | 匹配需要图谱推理，但两个服务分离 |
| P6 | DAG 执行引擎与节点执行器耦合在 alliance-svc | 中 | 执行引擎扩容影响调度/反之亦然 | 调度和执行在同一进程 |
| P7 | 结果融合器无独立扩展能力 | 低 | 复杂融合（辩论/迭代）阻塞主流程 | 融合在 alliance-svc 内同步执行 |
| P8 | 多协议单端口混合 HTTP/1.1+HTTP/2 | 低 | ALPN 协商复杂/边缘 case | 同端口跑两种协议版本 |

## 二、v3 优化架构

### 2.1 优化原则

| 原则 | 说明 |
|------|------|
| **职责单一化** | 每个服务只做一件事，拆分过重的服务 |
| **无状态化** | 所有服务无状态，状态外部化（Redis/PostgreSQL/图谱） |
| **减少跳数** | 合并需要紧密协作的服务，减少 RPC 调用 |
| **独立扩缩** | 高负载组件独立部署，按需扩容 |
| **统一抽象** | 记忆/匹配/执行等核心概念统一抽象，减少分散 |
| **协议分流** | 内部 gRPC 独立端口，对外 HTTP 独立端口 |

### 2.3 服务职责定义（v3）

| 服务 | 职责 | 状态 | 扩缩依据 | 修复问题 |
|------|------|------|----------|----------|
| **gateway-http** | HTTP协议接入(REST/JSON-RPC/MCP/WS) + 认证/限流/转码 | 无状态 | QPS | P8 |
| **gateway-grpc** | gRPC协议接入 + 服务间路由/负载均衡 | 无状态 | gRPC QPS | P8 |

| **alliance-fusion** | 结果融合(6种策略)/质量评估/迭代精炼 | 无状态 | 融合任务数 | P1/P7 |

| **expert-memory** | 统一记忆抽象(工作/会话/长期)/案例库/图谱学习/边权重更新 | 无状态 | 记忆操作QPS | P4 |
| **ai-inference** | Python AI推理(sidecar，UDS通信) | 有状态(模型) | 推理并发 | - |

### 2.4 关键优化点详解

#### 优化1：alliance-svc 拆分为 3 个服务（P1/P6/P7 修复）

```
v2: alliance-svc（5大能力耦合）
     ├── 任务调度/计划生成
     ├── DAG执行/节点调度
     ├── 结果融合
     ├── 协作记忆
     └── 专家匹配调用

v3: 拆分为 3 个独立服务
     ├── alliance-scheduler：任务调度 + 专家匹配 + 计划生成（CPU密集，低延迟）
     ├── alliance-executor：DAG执行 + 节点调度 + 进度推送（IO密集，高并发）
     └── alliance-fusion：结果融合 + 质量评估（计算密集，可异步）

收益：
  - 独立扩缩：执行器高峰期扩容不影响调度器
  - 故障隔离：融合服务挂了不影响任务执行（降级为择优选择）
  - 部署灵活：调度器可用少副本高规格，执行器用多副本低规格
  - 迭代独立：融合策略迭代不影响核心执行链路
```

#### 优化2：专家匹配合并到 scheduler（P5 修复）

```
v2: 匹配流程（2次RPC）
  scheduler → registry.match_experts() → kg.graph_query() → registry → scheduler
  延迟：~200ms（2次RPC + 图谱查询）

v3: 匹配流程（1次RPC，scheduler内嵌图谱查询）
  scheduler → 直接查询图存储（gRPC）→ 本地评分排序
  延迟：~80ms（1次RPC + 图谱查询 + 本地计算）

收益：
  - 匹配延迟降低 60%
  - 减少 registry 服务压力
  - 匹配算法迭代更灵活（不依赖 registry 接口）
  - registry 精简为纯注册中心（CRUD + 健康检查 + 工具发现）
```

#### 优化3：统一记忆服务（P4 修复）

```
v2: 记忆分散
  - 工作记忆：alliance-svc 内存 + Redis
  - 会话记忆：Redis
  - 长期记忆/案例：alliance-svc → kg-svc → graph-storage
  - 图谱学习：alliance-svc 内异步更新

v3: 统一记忆服务 expert-memory
  - 统一 API：MemoryService（Get/Put/Delete/Search/Learn）
  - 内部路由：工作记忆→Redis，会话记忆→Redis，长期记忆→PostgreSQL，案例→图存储
  - 图谱学习：独立异步 worker，批量更新边权重
  - 对上层透明：scheduler/executor/fusion 都通过统一 API 访问记忆

收益：
  - 一致性保证：记忆操作有统一事务边界
  - 查询简化：上层不需要知道记忆存在哪里
  - 学习异步化：图谱学习不阻塞主流程
  - 可独立优化：记忆层可加缓存/预取/批量
```

#### 优化4：全服务无状态化（P2 修复）

```
v2: agent-svc 有状态
  - Agent 实例存在内存中
  - 会话状态存在内存中
  - Pod 重启 → 丢失所有进行中的 Agent

v3: 全服务无状态
  - Agent 实例状态 → Redis（会话存储）
  - 执行上下文 → PostgreSQL（task_nodes 表）
  - 工作记忆 → Redis（统一记忆服务）
  - Agent 实例池 → 无状态，每次请求创建/复用无状态执行器

收益：
  - Pod 可随时重启/迁移（K8s 滚动更新无忧）
  - HPA 可自由缩容（不丢失会话）
  - 故障恢复快（新 Pod 从 Redis/PG 恢复状态）
```

#### 优化5：协议分流（P8 修复）

```
v2: 单端口混合 HTTP/1.1 + HTTP/2
  - :8080 同时承载 REST/JSON-RPC/MCP(HTTP/1.1) 和 gRPC(HTTP/2)
  - 需要 ALPN 协商/Content-Type 路由
  - 边缘 case：某些客户端不支持 ALPN，gRPC 握手失败

v3: 双端口分流
  - :8080 = 纯 HTTP/1.1（REST/JSON-RPC/MCP/WebSocket），对外
  - :50051 = 纯 HTTP/2 gRPC，内部服务间
  - 内部服务调用直接走 :50051，零路由开销
  - 对外调用走 :8080，按需转码到内部 gRPC

收益：
  - 内部 gRPC 性能最优（零协议判断开销）
  - 消除 ALPN 协商兼容性问题
  - 安全隔离：gRPC 端口不对外暴露（内网防火墙）
  - 独立监控：HTTP 和 gRPC 流量分别统计
```

## 三、v2 vs v3 对比

| 维度 | v2 | v3 | 改进 |
|------|----|----|------|
| 服务数 | 5 + 1 sidecar | 7 + 1 sidecar | +2（拆分过重服务） |
| 最大服务职责数 | 5（alliance-svc） | 3（alliance-scheduler） | 职责更单一 |
| 有状态服务 | 1（agent-svc） | 0（全无状态） | 全无状态化 |
| 专家匹配跳数 | 2次RPC | 1次RPC | 延迟降60% |
| 记忆访问方式 | 分散3处 | 统一API | 一致性提升 |
| 协议端口 | 1个（混合） | 2个（分流） | 内部性能最优 |
| 融合扩展 | 同步阻塞 | 独立服务可异步 | 不阻塞主流程 |
| 部署粒度 | 5个Deployment | 7个Deployment | 更精细扩缩 |
| 故障爆炸半径 | 大（alliance挂=全挂） | 小（单服务挂=降级） | 故障隔离提升 |

## 四、优化后的性能预估

| 指标 | v2 预估 | v3 预估 | 提升 |
|------|---------|---------|------|
| 任务创建→计划生成 | ~300ms | ~150ms | 50% |
| 专家匹配延迟 | ~200ms | ~80ms | 60% |
| 节点调度延迟 | ~50ms | ~20ms | 60% |
| 内部gRPC调用 | ~1ms(含路由) | ~0.5ms | 50% |
| 并发任务数(单集群) | 100 | 200 | 100% |
| 故障恢复时间 | ~5min(有状态恢复) | ~30s(无状态) | 90% |
| 滚动更新零中断 | 需优雅迁移会话 | 天然支持 | - |
