## 一、规划总纲

### 1.1 输入摘要

**来自 10 号成熟度评审（40 项）**

- 总体分级：✅ 企业级可用 **22 项（55%）**、🟡 需增强 **14 项（35%）**、🔴 不达标 **4 项（10%）**。
- 4 个 🔴 硬缺口：#11 图谱节点级无 CRUD（N4，只能全量 rebuild）、#15 DAG 并行无信号量上限（N8）、#23 SQLite 无 schema 版本迁移（N3）、#25 WebSocket 文档幻觉（代码无、文档宣称有）。
- **P0 阻断项（企业级定性红线，必须前置）**：
  - **D1 / N3**：SQLite 无 schema 版本迁移——任何一次表结构演进都可能让生产库起不来；
  - **D2 / N2 + G3**：审计 Actor 硬编码 system、前端控制台无角色按钮级权限——合规审计无法定责、破坏性写面对所有登录用户开放；
  - **D3 / #25**：WS 文档幻觉未修订——运维按 06 配 WS 必踩坑（代码侧无需实现，实时性已由 SSE 满足，只改文档）。
- 其余 P1 差距：D4 进程内三项（favorites/plans/history）重启即失、D5 / N8 并行护栏、D6 / N7 指标三进程格式不统一、D8 / N5 探活默认关、D9 / G5+G6 SSE 未统一 + store 无测试。

**来自 11 号竞品对标**

- **我们强 5 条（差异化卖点，须放大）**：①专家关系知识图谱 + 最优组队（主流竞品均为向量 RAG，不建模专家关系）；②国密 SM4-GCM 全链路一键开关；③零外部依赖的气隙内网可部署（嵌入式 SQLite）；④开箱即用的 7 协作模式 + 6 融合策略；⑤面向大规模专家注册的 10:1:1 分级心跳聚合 + HA 选主。
- **我们弱 8 条（需追赶）**：①无可视化拖拽编排画布；②无可观测/tracing/eval 控制台；③企业治理三件套缺失（SSO / 多租户 / 真实用户审计）；④无插件/技能市场与分发生态；⑤无 HITL 人工审批节点；⑥无中心化凭证托管与每用户记忆隔离；⑦DAG 工程化不足（无并行信号量、无补数/重放、无 schema 迁移）；⑧开放协议滞后（尚无 MCP/A2A，而 MAF/Copilot/飞书/钉钉已支持）。

### 1.2 规划原则

1. **先补企业级底线，再做差异化创新。** 10 评审的 P0 项（N3 schema 迁移、N2 审计身份 + G3 前端权限、N1 下游鉴权、#25 文档修订）不是创新点，但它们是一切创新的前置地基——不补则创新建在流沙上。本文把这组底线项列为「阶段一前置」，不占创新卡片篇幅，但在 §六依赖图中显式标注为 P0 阻塞节点。
2. **放大强项而非追平弱项。** 不与 Dify/Coze 比「通用低代码 + 插件市场规模」，而把「专家知识图谱 + 国密气隙 + 多专家协作融合」做深（图 RAG、图数据库、图谱可视化、私有化交付）；可视化画布、多租户、MCP 等是「补到可用即可」的受众扩大项，不求全面超越。
3. **每条创新必须有依据。** 所有创新卡片均标注来自 10 评审的缺口编号（N/G/D/#）或 11 对标的「我们弱 / 借鉴点」条目；无依据的想法不进路线图。
4. **与 08 §十 对齐。** 08 §十 已列的 P2 项（fusion 独立、memory 独立、MCP=P3 等）在本文升级为带成本/依赖的完整卡片，并按 11 对标结论调整优先级（如 MCP 从 P3 提前）。
5. **成本给相对量级，不编造绝对数字。** 「成本：中，约 1–2 人·月」这类相对估算用于排期，不作为商务报价依据。

## 二、新技术升级

### 2.1 T1　DAG 并行度信号量与重试/重放

- **价值**：当前 DAG 靠 tokio 自然调度、无并发护栏（10 评审 #15 🔴/N8），LLM 配额可能被并行节点打爆、成本失控；补信号量 + 每专家限流后，并发可观测、可配置、可兜底。在此基础上叠加「跨任务重试/补跑/重放」语义（节点已有超时 300s + 重试 3 + 指数退避，缺的是任务级重放与失败补跑），对齐 Airflow 的成熟调度工程。
- **成本**：中。dag_engine 加 Semaphore + 配置入口约 1–2 人·月；任务级重放/断点续跑约 2–3 人·月（依赖 A3 事件溯源的状态持久化，可分两步走）。
- **优先级**：**P1**（10 评审 D5 已列 P1；11 对标弱⑦直接命中）。
- **依赖**：P0 的 N3 schema 迁移（重放要落任务节点表）；与 A3 事件溯源部分重叠，可先做信号量（独立、快赢），重放随 A3 一起做。
- **落地路径**：① dag_engine 引入 `tokio::sync::Semaphore`，全局并行上限 + 每专家/每 Provider 配额两级信号量，env 可配（`MOX_DAG_MAX_PARALLEL`）；② 前端编排视图暴露并发上限滑块与当前并发指标；③ 节点级状态落 `ea_task_node` 表（08 §六目标态），支持失败节点单独重跑与整任务 backfill。
- **依据**：10-D5/N8/#15；11-我们弱⑦；08 §九 N8；Airflow 借鉴点①（Semaphore 限流、任务重放、补数）。

### 2.2 T2　图 RAG（知识图谱增强检索）

- **价值**：这是我们与所有竞品的本质差异——Dify/Coze 的知识库是文档向量 RAG，CrewAI/LangGraph 是代码状态机，均不建模「专家/能力/领域」关系。把现有专家关系图谱（graph_nodes/edges/meta + optimal-team）从「只读快照」升级为「图检索增强」：检索时不只返回语义相似的文档/专家，而是沿边多跳扩展相关专家、能力域、历史协作链路，给 planner 提供「该找谁、为什么、怎么组队」的结构化上下文。放大 11-强①。
- **成本**：中偏高。增量图写入（N4）是前置；图查询语言/多跳检索约 2–3 人·月；与向量检索（#27 语义搜索）做 hybrid 融合约 1–2 人·月。
- **优先级**：**P1**（差异化护城河，越早建壁垒越高）。
- **依赖**：P0 之后先补 N4 图谱节点/边增量写（10-#11🔴/D7）；向量检索目标态（08 §十 P1，pgvector）可并行评估；A4 图数据库是其远期承载，初期可在 SQLite 图表上用递归 CTE 做多跳。
- **落地路径**：① 先补专家 CRUD 联动维护图谱边（不再全量 rebuild）；② 在语义搜索端点叠加「图谱邻域」返回（一跳邻居专家 + 关系类型 + 权重）；③ planner 生成计划时消费 optimal-team 结果作为组队证据链；④ 远期随 A4 迁入图库后启用多跳/路径查询。
- **依据**：11-我们强①、11-弱④生态；10-#10/#11/N4/D7、#27；08 §十「图谱节点级 CRUD P2」。
- **落地状态（2026-10-01）**：✅ **图谱纯检索已落地**——`POST /api/expert-graph/rag/expand` 上线，输入 seeds/max_depth(1-4)/top_k/node_types/min_weight，沿无向边 BFS 多跳扩展，聚合分=路径边权重乘积，返回 node+depth+path+first_hops（首跳边供解释「为什么组队」）；11 个后端单测 + 前端 650 vitest 全绿。实现选择由规划期「SQLite 递归 CTE」改为**内存态加权多跳**（state.graph 无 SQLite 连接句柄，与 get_graph 同源、与 SQLite 双向同步等价，A4 图库迁入时换查询实现）。⏳ **向量融合留待**：`hybrid_rerank` 为扩展点（当前透传），pgvector 召回落地前不冒充向量分数，响应 `rerank` 字段如实标注「graph_only（向量融合待 #27）」。

### 2.3 T3　MCP 协议接入（从 P3 提前）

- **价值**：08 §十 把 MCP 列在 P3，但 11 对标显示 MAF（AutoGen 合并后）、Microsoft Copilot Studio、飞书 aily、钉钉生态均已支持或认证 MCP，开放协议已成主流互操作语言。滞后意味着我们的专家既不能被外部 Agent 生态调用，也无法复用外部 MCP 工具。提前到 P1 可获得与外部 Agent/工具链的双向互操作入口，是 11-弱⑧ 的直接补课。
- **成本**：中。MCP Server 侧（把我们的专家/图谱/任务能力暴露为 MCP tools）约 1–2 人·月；MCP Client 侧（让我们的 DAG 能调用外部 MCP Server）约 1–2 人·月。
- **优先级**：**P1（由 P3 上调）**。
- **依赖**：P0 的 N1 下游鉴权 + N2 审计身份（MCP 调用必须有可审计的调用方身份）；与 M2 生态开放卡片共用 SDK 与认证骨架。
- **落地路径**：① 先做 MCP Server：把「专家检索 / optimal-team / 发起协作任务」封装为标准 MCP tools，鉴权走网关 JWT + 审计注入真实 Actor；② 再做 MCP Client：scheduler 工具层支持注册外部 MCP Server，DAG 节点可调用；③ 凭证托管对齐飞书 aily 借鉴（中心化凭证，Agent 不持密钥）。
- **依据**：11-我们弱⑧、MAF 借鉴点①（优先落地 MCP）；08 §十「协议扩展 REST+SSE → +JSON-RPC+MCP，原列 P3」。
- **落地状态（2026-10-01）**：①已完成——独立 crate `platform/domains/alliance/mcp/mox-alliance-mcp-server`，自实现 JSON-RPC 2.0 over stdio（Content-Length 帧），3 个真实工具 `expert_search/optimal_team/graph_expand` 薄适配网关读面端点，真实验证返回真实专家/组队/邻域；②③留待——MCP Client（DAG 调用外部 MCP Server）与中心化凭证托管未做。

### 2.4 T4　事件驱动架构（任务状态变更事件流）

- **价值**：当前 SSE（#24）是单向「日志流」（日志行推送），任务状态变更（pending→running→completed/failed、节点启停）没有结构化事件流，外部系统/前端/多副本只能靠轮询。引入任务状态事件流后：① 前端无需 4s 轮询回退即可感知状态；② 外部企业系统（政务办事系统、监控）可订阅任务生命周期事件做联动；③ 为可观测/tracing 控制台（11-弱②）提供数据骨干。对齐 Airflow 3.0 的事件驱动方向与 LangGraph 的状态机事件。
- **成本**：中。事件 schema 定义 + 内嵌事件总线（初期可复用 SQLite/SSE，不必引 Kafka）约 1–2 人·月；前端事件消费适配约 1 人·月。
- **优先级**：**P1**（是 U1 画布、U2 透明化、A1 多租户审计的公共依赖）。
- **依赖**：P0 的 N3（事件要落库才能回放）；与 T5 流式编排、A3 事件溯源共用事件模型，建议同一套事件 schema。
- **落地路径**：① 定义 TaskLifecycleEvent / NodeLifecycleEvent 结构化事件（type、timestamp、task_id、node_id、actor、payload）；② 网关侧发布，SSE 升级为「日志帧 + 事件帧」双通道；③ 提供事件订阅端点（webhook 或 SSE）供外部系统消费；④ 事件落库（与 A3 共用），支持按 task 回放。
- **依据**：10-#24（SSE 单向日志流）、D9/G5；11-我们弱②（可观测/tracing 短板）；LangGraph 借鉴点①（run 级结构化事件 + 时间线）、Airflow 3.0 事件驱动。

### 2.5 T5　流式编排（边执行边交付）

- **价值**：当前是「全量 DAG 跑完 → 融合 → 一次性返回」（#9 融合结果仅保留 `__fusion_output__` 行），长任务用户长时间无中间产出。流式编排让已完成节点的结果、辩论中间轮次、融合中间增量边执行边推送给前端与调用方，显著提升长任务体验，也为 HITL 人工审批节点（11-弱⑤）提供「人在环中」的交互基础。
- **成本**：中偏高。executor 节点结果流式回传 + fusion 中间态透出约 2–3 人·月；前端逐节点渲染约 1 人·月。
- **优先级**：P2（体验增强，依赖 T4 事件流先建）。
- **依赖**：T4 事件驱动（事件帧是流式载体）；U1 画布（流式结果要在画布上逐节点点亮，二者联动）。
- **落地路径**：① executor 每完成一个节点即发 NodeCompletedEvent（带部分结果）；② 融合策略支持增量/流式聚合（map_reduce 天然适合）；③ 前端画布逐节点从 running→success 实时点亮，辩论轮次逐轮推送；④ 远期叠加 HITL 节点（审批暂停/继续）。
- **依据**：10-#6（辩论无轮次回看）、#9（融合无可解释明细）；11-弱①（HITL）、LangGraph streaming 借鉴。

## 三、新UI升级

### 3.1 U1　画布式可视化编排（拖拽 DAG）

- **价值**：这是面向业务人员最大的体验差距（11-弱①）。当前是固定步骤表 + Kahn 拓扑（#7/#13），业务人员无法画 DAG。补拖拽节点-边画布，让业务方自行编排「专家节点 + 协作模式 + 融合策略」并导出为我们的 DAG，是把产品从「技术团队自建后端」推向「业务人员自助平台」的关键一跃。
- **成本**：高。画布引擎（节点拖拽、连线、校验、 minimap）约 3–5 人·月；与现有 planner/DAG 模型双向转换约 1–2 人·月。建议基于成熟图编辑库（如现有 echarts 力导向栈统一后）而非从零造 SVG。
- **优先级**：**P1**（11 弱①，受众扩大的第一杠杆）。
- **依赖**：T4 事件流（画布要实时点亮节点状态）；T5 流式结果（节点结果回显）；G9 三套可视化栈归一化（10-D10）先收口，避免画布成为第四套栈。

## 四、新架构升级

### 4.1 A1　多租户隔离（数据 / 配额 / 密钥）

- **价值**：11-弱③ 企业治理三件套之一。当前无 SSO、无工作区/租户概念，所有数据平铺。政务/企业场景下一套系统常需服务多个处室/业务单元，租户隔离（专家数据、会话、任务、配额、密钥按租户分域）是「平台化」而非「单项目」的前提。对标 Dify 多租户、n8n 组织策略、Airflow 多团队隔离。
- **成本**：高。数据模型加 tenant_id 全表改造 + 行级隔离 + 配额计量 + 密钥按租户托管约 3–5 人·月。
- **优先级**：**P1**（企业治理红线，与 P0 的 N2/G3 同源，是其规模化延伸）。
- **依赖**：P0 的 N2 审计身份 + G3 角色权限（多租户 = 在用户/角色之上加一层租户维度）；P0 N1 下游鉴权（下游 svc 要能识别 tenant）；中心化凭证（飞书 aily 借鉴：Agent 不持密钥，系统统一托管）。
- **落地路径**：① 数据模型引入 tenant_id（P0 schema 迁移框架内一并加）；② 所有查询按租户过滤，行级权限；③ 配额：每租户专家数、并发数（接 T1 信号量）、LLM 调用量计量；④ 密钥按租户隔离托管（对齐飞书 aily 中心化凭证）；⑤ SSO/SAML 对接（n8n/Dify 借鉴）作为租户入口。
- **依据**：11-我们弱③、Dify/n8n/Airflow 多团队借鉴；10-D2/N2/G3；08 §十（SSO/多租户原属目标态未列项）。

### 4.2 A2　模块化微服务深化（fusion 独立 / memory 独立）

- **价值**：08 §十 已列两项 P2：fusion 目前是 executor-core 适配层（#9）、memory/session 目前网关内联（#26）。把两者独立为 fusion-svc / memory-svc：① fusion 可独立扩缩（融合是 CPU 密集纯算法，独立部署不拖累执行器）；② memory 独立后网关可无状态化（解决 N11 会话单进程恢复、网关多副本需 sticky 的问题），并为飞书 aily 借鉴的「每用户/每群记忆隔离」提供承载。
- **成本**：中偏高。fusion 独立约 1–2 人·月（trait 已存在，主要是拆进程 + proto）；memory 独立 + 网关无状态化约 2–3 人·月。
- **优先级**：P2（08 §十 原列 P2，维持）。
- **依赖**：P0 N1 下游鉴权（新 svc 同样要挂 internal token）；A1 多租户（memory 隔离要按租户/用户）；N3 schema 迁移（memory 表结构演进）。
- **落地路径**：① fusion：现有 fusion/strategies trait 抽离为独立 svc，executor 通过契约调用，落 08 §十 P2；② memory：sessions/session_messages 从网关 SQLite 迁到独立 memory-svc，网关会话改为远程调用，解决 N11 sticky；③ 记忆按用户/租户隔离（飞书 aily 借鉴）。
- **依据**：08 §十「fusion 独立 P2 / memory 独立 P2」；10-#9/#26、N11；11-弱⑥（记忆隔离）。

### 4.3 A3　事件溯源（任务 / 审计可重放）

- **价值**：当前审计是 SHA-256 哈希链 NDJSON 文件追加（#19），任务状态在 SQLite 但无事件序列，plans/history 进程内（#28/#29）。事件溯源把「状态变更」当作不可变事件流持久化，当前状态由事件折叠得到——天然支持：① 任务任意重放/回溯（对齐 LangGraph durable execution、Airflow 补数）；② 审计从 NDJSON 文件升级为可查询、可关联到任务节点的事件流（n8n 审计送 SIEM）；③ 与 T4 事件流、T1 重放共用同一套事件存储，不重复造。
- **成本**：高。事件存储 + 快照 + 重放引擎约 3–5 人·月；审计链兼容（保留防篡改）约 1 人·月。
- **优先级**：P2（企业级可运维性增强，依赖 T4 先定义事件模型）。
- **依赖**：P0 N3 schema 迁移（事件表要版本化）；T4 事件 schema（同源）；T1 任务重放是其直接受益者。
- **落地路径**：① T4 定义的 Task/Node 事件落事件表（append-only）；② 定期快照当前状态（避免全量重放）；③ 提供任务重放 API（从某事件点重建状态）；④ 审计事件接入 SIEM 输出（n8n 借鉴），保留 HMAC 防篡改链。
- **依据**：10-#19（审计 NDJSON）、#28/#29（进程内）、D4；11-弱⑦（持久执行/重放）、LangGraph durable execution 借鉴、n8n 审计送 SIEM 借鉴。

### 4.4 A4　图数据库引入（关系层从 SQLite 升级）

- **价值**：当前图谱是 SQLite 三张表（graph_nodes/edges/meta），且只能全量 rebuild（#11/N4🔴）。图数据库（NebulaGraph/Neo4j 或自研轻量图库）引入后：① 多跳/路径/邻域查询不再靠递归 CTE，支撑 T2 图 RAG；② 专家 CRUD 增量维护边成为一等操作（彻底解决 N4）；③ 图谱规模从百级节点迈向千/万级。这是把「专家关系图谱」这个差异化强项从 demo 级推向生产级的承载升级。
- **成本**：高。选型调研 + 图库接入 + 迁移 + 增量写约 3–5 人·月；注意这与 11-强③「零外部依赖气隙」存在张力——必须保证图库可嵌入式/可气隙部署，否则削弱卖点。
- **优先级**：P2（差异化纵深，但气隙约束下选型要谨慎，初期先用 SQLite 递归 CTE 顶住 T2）。
- **依赖**：P0 N3；N4 增量写先在 SQLite 上落地（数据模型先行）；T2 图 RAG 是其应用方。**关键约束**：必须选支持私有化/嵌入式的图库，或自研轻量图库，避免引入必须联网的云图库而破坏气隙卖点。
- **落地路径**：① 先在 SQLite 上用递归 CTE 实现多跳（T2 先行，不依赖图库）；② 调研可气隙部署的图库（嵌入式/单机版），评估 Rust 客户端成熟度；③ 迁移 graph_nodes/edges 到图库，专家 CRUD 联动增量写边；④ 图谱查询 API 切换到底层图库，前端 U3 无感。
- **依据**：10-#11/N4、D7；11-强①（图谱差异化）；11-Dify 对标注（Dify 原生 RAG 不接图数据库，恰是我们差异点）；08 §六 graph 表现状。

## 五、新模式升级

### 5.1 M1　私有化交付产品化（信创 / 气隙离线部署包）

- **价值**：这是我们最强模式卖点（11-强②③）的产品化。当前嵌入式 SQLite 零依赖 + SM4 国密已具备气隙能力（09 生产模板、4 容器 compose），但还不是「开箱可交付的产品」。把它产品化为：① 信创适配清单（国产 CPU/OS/数据库兼容认证路径）；② 离线安装包（含全部依赖、模型、向量库的镜像包，无外网可装）；③ 一键自检脚本（09 §6 已有 200/401/加密自检，扩为交付前自检套件）。这是政务等保/信创场景的成交关键。
- **成本**：中。离线打包脚本 + 自检套件 + 信创适配测试约 2–3 人·月（认证周期另计）。
- **优先级**：**P1**（已有能力产品化，投入产出比最高）。
- **依赖**：P0 N3 schema 迁移（离线包升级要带迁移）；MCP/图库选型必须气隙友好（否则破坏交付前提）；等保三级申报路径（钉钉对标为既有资质，我们在申报路上）。
- **落地路径**：① 出离线交付包（docker save 全量镜像 + 离线 compose + 初始化脚本）；② 交付前自检套件（09 §6 自检扩为一键 `mox doctor`）；③ 信创适配矩阵（CPU/x86 vs  ARM、OS、国产数据库）；④ 国密 SM4 状态在前端/自检中可见（10-#21 前端无加密状态可见性，顺带补）。
- **依据**：11-我们强②③、Copilot/钉钉/飞书云 SaaS 对比；10-#21（SM4 6 挂载点）、09 生产模板；11-弱（等保资质在申报路径）。

### 5.2 M2　生态开放（MCP Server / 插件 SDK / 开放 API）

- **价值**：与 T3 MCP 联动，从「能被外部调用」走向「开放生态」。提供：① MCP Server（专家/图谱/任务能力对外开放，T3 已做）；② 插件 SDK（第三方把自有专家/工具按契约注册进我们的 registry，对标 CrewAI Tool Repository、Dify 插件）；③ 开放 API + webhook（外部政务系统编排我们的多专家协作）。这是把 registry-svc（10:1:1 聚合，11-强⑤）从「内部注册中心」推向「开放注册生态」的模式升级。
- **成本**：中偏高。SDK 设计 + 文档 + 注册-白名单治理约 2–3 人·月。
- **优先级**：P2（T3 MCP 落地后顺势开放）。
- **依赖**：T3 MCP Server；A1 多租户（插件按租户隔离）；中心化凭证（插件调用密钥托管）；插件准入治理（Dify 2026-08 插件信任治理借鉴：包准入、可达范围、版本审查）。
- **落地路径**：① T3 完成 MCP Server 后，公开其 API 文档；② 定义插件/专家注册契约（proto 已有 Expert 契约基础）；③ 插件白名单治理（对标 Coze「仅允许企业插件」、Dify 准入治理）；④ webhook 对外发任务事件（T4 事件流的外向出口）。
- **依据**：11-我们弱④、CrewAI Tool Repository 借鉴、Dify Marketplace/插件治理借鉴、Coze 企业插件商店借鉴；11-强⑤（registry 10:1:1 聚合打底）。

### 5.3 M3　专家市场（技能上架 / 订阅 / 分成）

- **价值**：对标 Coze 商店、Dify Creator Center + Template Marketplace。把「专家」从内置种子 + 本地 CRUD 变成可上架、可订阅、可分成的资产：领域专家把自己的能力声明、提示词、协作模板发布到市场，其他组织/用户一键订阅组队。这是生态（M2）之上的商业层，但在政务内网定位下，市场更可能是「企业内部市场 / 行业模板库」而非公开 C 端商店。
- **成本**：高。上架-审核-订阅-计量-分成体系约 3–5 人·月；政务场景下以「内部模板库」起步可大幅降本。
- **优先级**：P2（依赖 M2 生态 SDK 成熟后）。
- **依赖**：M2 插件/专家注册 SDK；A1 多租户（市场按租户/组织可见）；U2 匹配透明化（市场专家要有可信画像）。
- **落地路径**：① 先做「组织内专家/工作流模板共享」（对标 Coze 企业商店、仅本组织可见），不做公开市场；② 模板一键采用（Dify Template Marketplace 借鉴）；③ 版本治理与白名单；④ 远期再评估公开订阅/分成。
- **依据**：11-我们弱④、Coze 商店/Dify Creator Center 借鉴；10-#34/#35（内置两套专家种子）。

### 5.4 M4　SaaS 订阅

- **价值**：历史 39 号文档有 SaaS 化讨论。与气隙私有化（M1）是互补模式：对无力自托管的中小团队提供云托管 SaaS 订阅，对政务/大客户坚持私有化。但我们的核心壁垒（国密气隙、信创）在 SaaS 形态下不成立，因此 SaaS 是「获客入口」而非「利润核心」。
- **成本**：高。多租户云平台 + 计费 + 运维约 5+ 人·月（基础设施另计）。
- **优先级**：P2/P3（在 A1 多租户成熟后才有成本基础；当前气隙/政务优先，SaaS 排后）。
- **依赖**：A1 多租户（SaaS 是多租户的直接商业化）；M1 私有化是主航道；数据驻留与合规（Dify BYOK/数据驻留借鉴）。
- **落地路径**：① 不急于自建公有云；② 先以「私有化交付 + 远程运维」覆盖中小企业；③ 待 A1 多租户与 M2 生态成熟后，评估托管 SaaS；④ 政务客户永远走 M1 气隙，不进 SaaS 多租户池。
- **依据**：历史 39 号 SaaS 讨论（已退役快照，仅作方向参考）；11-强③（气隙是壁垒，SaaS 弱化它）；Dify 三态部署（云/VPC/自有）借鉴。

## 六、依赖关系与里程碑

### 6.1 依赖关系（P0 必须前置）

```
[P0 企业级底线（10 评审，非创新卡片，但是所有创新的地基）]
  N3 schema 迁移 ──────┬─→ T1 重放 / A3 事件溯源 / A4 图库迁移 / M1 离线包
  N2 审计身份+G3 权限 ─┼─→ A1 多租户 / T3 MCP 身份 / U4 实时协作 / M2 插件治理
  N1 下游鉴权 ─────────┼─→ T3 MCP Client / A2 新 svc / A1 租户识别
  #25 WS 文档修订 ─────┘─→（纯文档，解除运维踩坑）

[T4 事件驱动] ──公共骨干──→ T5 流式编排 / U1 画布回显 / U4 多人围观 / A3 事件溯源 / M2 webhook

[T2 图 RAG] ←── N4 增量写（先在 SQLite）←── A4 图库（远期承载）
   ↑
```

**关键阻塞说明**：
- T1 的「信号量」部分可独立快赢；T1 的「重放」部分被 A3 阻塞，分两步走。

- U1 画布被 G9 三栈归一阻塞，避免画布成为第四套渲染栈。
- 所有外向能力（T3/M2/M3/M4）都被 P0 身份与 A1 租户阻塞，不可越级。

### 6.2 三阶段里程碑

**阶段一：P0 企业级底线 + 快赢差异化（1–2 个季度）**

- 前置底线（10 评审 P0，强制前置）：N3 schema 迁移、N2 审计身份 + G3 前端角色权限、N1 下游双值令牌、#25 WS 文档修订；顺手补 D4 进程内三项落盘、D8 探活默认开。
- 快赢创新：
  - **T1a** DAG 并行信号量（不含重放）；
  - **U2** 专家画像与匹配透明化（低成本高信任）；
  - **M1** 私有化交付产品化（离线包 + 一键自检）；
  - **T4** 任务状态事件流（公共骨干，先建）。
- 出口标准：按 09 生产档 + 上述底线后，可对政务客户做气隙交付；并发可控、审计可定责、匹配可解释。

**阶段二：P1 差异化与受众扩大（2–3 个季度）**

- **T2** 图 RAG（基于 N4 增量写 + SQLite 多跳）；
- **T3** MCP 协议接入（Server 先行、Client 跟进）；
- **U1** 画布式编排（只读呈现 → 拖拽编辑 → 流式回显）；
- **A1** 多租户隔离（数据/配额/密钥 + SSO 入口）；
- **T5** 流式编排（在 T4 之上）；
- 出口标准：业务人员可自助画 DAG、多专家组队可图检索增强、外部 Agent 可经 MCP 互操作、一套系统可隔离服务多组织。

**阶段三：P2 纵深与生态（3+ 个季度）**

- **A2** fusion / memory 微服务独立（网关无状态化）；
- **A3** 事件溯源（任务重放 + 审计送 SIEM，含 T1b 重放）；
- **U3** 图谱可视化增强、**U4** 实时协作；
- **A4** 图数据库引入（气隙约束下选型）；
- **M2** 生态开放 SDK / **M3** 企业内部专家市场；
- **M4** SaaS 订阅（仅在多租户成熟后评估，不碰政务气隙客户）。
- 出口标准：从「技术团队自建后端」演进为「业务人员自助、企业 IT 可治理、专家可生态化流通」的平台，同时守住国密气隙的政务护城河。

## 七、结论

**一句话定位**：专家联盟的差异化护城河是「专家知识图谱 + 国密气隙部署 + 多专家协作融合」，必须先补齐的企业级底线是「schema 迁移、真实用户审计与角色权限、下游鉴权」。

- **护城河要做深**：图 RAG（T2）、图数据库（A4）、图谱可视化（U3）、匹配透明化（U2）、私有化交付（M1）——这些把「别人没有的专家关系图谱与气隙国密」从 demo 做成生产壁垒，不与 Dify/Coze 拼通用低代码规模。
- **底线要先补**：10 评审的 P0 项（N3/N2/G3/N1/#25）不是创新，但决定了创新能否落地——身份、权限、schema、审计不立，多租户、MCP、生态全是空中楼阁，故强制列为阶段一前置。
- **受众要扩大但不越界**：画布编排（U1）、多租户（A1）、MCP（T3）补到「业务人员可用、企业 IT 可治理」即可，不求全面超越；SaaS（M4）与公开专家市场（M3）是远期评估项，政务气隙客户永远走 M1 私有化，不进多租户云池。

> 本规划为 2026-09-29 基于 10 评审与 11 对标的创新路径排期。所有创新项均可回溯依据编号；成本为相对量级估算，排期前应按团队实际产能校准。
