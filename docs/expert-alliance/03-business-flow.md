# 专家联盟业务处理流程

## 1. 端到端主流程

```
用户提交任务
    ↓
[1] 任务接收与解析
    - 输入：任务描述 + 偏好模式 + 约束
    - 输出：TaskID + 任务上下文
    ↓
[2] 专家智能匹配
    - 输入：任务描述 + 领域 + 能力需求
    - 处理：5维评分（领域30% + 能力30% + 健康15% + 优先级15% + 表现10%）
    - 输出：排序后的专家列表 + 匹配理由
    ↓
[3] 协作计划生成（DAG）
    - 输入：匹配的专家 + 偏好模式
    - 处理：按模式生成拓扑 + 节点依赖 + 融合策略 + 权重
    - 输出：CollaborationPlan（DAG）
    ↓
[4] DAG 执行
    - 输入：CollaborationPlan
    - 处理：拓扑排序 → 调度循环 → 节点执行 → 依赖更新 → 进度推送
    - 输出：节点执行结果列表
    ↓
[5] 结果融合
    - 输入：各节点输出 + 融合策略 + 专家权重
    - 处理：按策略融合（投票/加权/择优/辩论仲裁/迭代精炼）
    - 输出：最终结果
    ↓
[6] 记忆沉淀与交付
    - 输入：完整协作记录
    - 处理：归档案例 + 更新图谱边权重 + 会话记忆
    - 输出：任务完成 + 结果返回用户
```

## 2. 专家匹配流程

```
任务描述输入
    ↓
┌─────────────────────────────────┐
│ 第1步：候选过滤                  │
│   - 租户隔离：tenant_id 匹配     │
│   - 状态过滤：仅 Active 专家     │
│   - 优先级过滤：≥ min_priority   │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│ 第2步：5维评分                   │
│   - 领域匹配分 = 匹配领域数/总需求领域数（权重30%） │
│   - 能力匹配分 = 70%能力覆盖度 + 30%描述文本相似度（权重30%） │
│   - 健康分 = is_healthy ? 1.0 : 0.3（权重15%） │
│   - 优先级分 = priority / 10.0（权重15%） │
│   - 表现分 = health.success_rate（权重10%） │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│ 第3步：阈值过滤                  │
│   - 总分 < 0.2 → 淘汰            │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│ 第4步：排序与截断                │
│   - 按总分降序排序                │
│   - 截取 max_results 个           │
└─────────────────────────────────┘
    ↓
输出：MatchedExpert[]（含分数明细 + 匹配理由）
```

**对应代码：** `scheduler-core/matcher.rs → RuleBasedExpertMatcher::match_experts()`

## 3. 协作计划生成流程

### 3.1 模式选择

```
用户指定模式？
    ├─ 是 → 用指定模式
    └─ 否 → 默认 Parallel
```

### 3.2 七种模式的 DAG 拓扑

| 模式 | 拓扑结构 | 节点依赖 | 适用场景 |
|------|---------|---------|---------|
| **Parallel 并行** | 所有节点无依赖，同时执行 | 无 | 任务可分解为独立子问题 |
| **Sequential 串行** | 节点按分数排序，链式依赖 | node-n 依赖 node-(n-1) | 需要逐步递进的任务 |
| **Voting 投票** | 所有专家对同一问题独立作答 | 无 | 需要多方案对比 |
| **Hierarchical 分层** | 按领域分组，组内并行，组间串行 | 后层依赖前层全部节点 | 跨领域复杂任务 |
| **Debate 辩论** | 正方 + 反方 + 裁判 | 裁判依赖正反方 | 需要权衡利弊的决策 |
| **Iterative 迭代** | 多轮循环，逐步精炼 | 每轮依赖上一轮 | 需要反复优化的任务 |
| **Dynamic 动态** | 决策节点 + 主路径 + 兜底分支 | 主路径/兜底都依赖决策节点 | 任务特征不确定，需智能选型 |

### 3.3 Dynamic 模式决策流程

```
任务描述输入
    ↓
[1] 关键词意图识别
    ├─ 含"迭代/优化/refine" → Iterative
    ├─ 含"评审/审核/review" → Sequential
    └─ 无明确意图 → 进入下一步
    ↓
[2] 专家数量判断
    ├─ ≤1 位专家 → Sequential（单链）
    └─ ≥2 位专家 → 进入下一步
    ↓
[3] 领域广度判断
    ├─ 领域去重数 ≥ 3 → Hierarchical（分层协同）
    └─ 领域数 < 3 → 进入下一步
    ↓
[4] 分数分布判断
    ├─ 极差 ≥ 0.25 → Hierarchical（强弱分明，高分领衔）
    ├─ 极差 < 0.10 且 ≥3人 → Voting（实力接近，投票裁决）
    └─ 其他 → Debate（存在分歧，辩论仲裁）
    ↓
输出：决策理由留痕 + 主路径拓扑 + 兜底分支
```

**对应代码：** `scheduler-core/planner.rs → decide_dynamic_mode()`

## 4. DAG 执行流程

```
CollaborationPlan 输入
    ↓
[1] 初始化
    - 所有节点状态 = Pending
    - 构建邻接表 + 入度表
    ↓
[2] 调度循环
    ┌─────────────────────────────────┐
    │ 找出所有入度=0 且 Pending 的节点 │
    │   - 无 → 检查是否还有 Failed 节点 │
    │     - 有 → 任务失败              │
    │     - 无 → 全部完成，退出循环     │
    │   - 有 → 取一个可执行节点        │
    ↓                                  │
    │ [3] 节点执行                      │
    │   - 状态 → Running               │
    │   - 调用专家 Agent 执行           │
    │   - 成功 → 状态 → Completed       │
    │   - 失败 → 状态 → Failed          │
    │     - retry_count < 3 → 重试     │
    │     - 否则 → 标记 Skipped         │
    ↓                                  │
    │ [4] 依赖更新                      │
    │   - 遍历该节点的后继节点          │
    │   - 入度 -1                       │
    │   - 记录输出到 output_ref          │
    ↓                                  │
    │ [5] 进度推送                      │
    │   - WebSocket/SSE 推送节点状态   │
    └─────────────────────────────────┘
    ↓
输出：全部节点执行结果
```

**对应代码：** `executor-core/` + 网关 `experts_orchestration.rs → topological_sort()`

## 5. 结果融合流程

```
多专家输出输入
    ↓
[1] 融合策略路由
    ├─ MajorityVote（多数投票）→ 取出现次数最多的结果
    ├─ WeightedVote（加权投票）→ 按匹配分加权投票
    ├─ Concatenation（拼接合并）→ 按专家顺序拼接
    ├─ BestOf（择优选择）→ 取分数最高的专家结果
    ├─ DebateArbitration（辩论仲裁）→ 裁判专家裁决
    └─ IterativeRefinement（迭代精炼）→ 多轮迭代优化
    ↓
[2] 质量评估
    - 检查结果完整性
    - 检查各专家结果一致性
    - 不一致 → 触发迭代精炼
    ↓
[3] 输出最终结果
    - 融合后的最终答案
    - 各专家贡献说明
    - 融合策略说明
```

**对应代码：** `alliance-core/fusion/strategies/`

## 6. 异常处理流程

```
节点执行失败
    ↓
[1] 错误分类
    ├─ 临时错误（网络超时/限流）→ 重试
    ├─ 参数错误 → 标记 Skipped，继续其他节点
    └─ 专家不可用 → 找替代专家
    ↓
[2] 重试机制
    - 最多重试 3 次
    - 指数退避：1s → 2s → 4s
    - 重试耗尽 → 标记 Failed
    ↓
[3] 降级策略
    - 关键节点失败 → 任务失败
    - 非关键节点失败 → 跳过，继续执行
    - 有替代专家 → 切换专家重跑
    ↓
[4] 任务终态
    - 全部关键节点成功 → completed
    - 任一关键节点失败 → failed
    - 用户取消 → cancelled
```

## 7. 专家注册流程

```
专家 Agent 启动
    ↓
[1] 注册请求
    - 发送：专家ID + 名称 + 领域 + 能力 + 工具 + 健康指标
    - 目标：registry-svc:3400
    ↓
[2] 注册中心验证
    - 格式校验
    - 租户隔离检查
    - 重复ID检查
    ↓
[3] 注册成功
    - 状态 = Active
    - 加入专家列表
    - 同步到 scheduler 的匹配器
    ↓
[4] 心跳上报
    - 定期上报健康状态
    - 分级聚合：node → rack → cell（10:1:1）
    - 心跳超时 → 状态 = Offline
```

**对应代码：** `registry-core/` + `registry-svc:3400`
