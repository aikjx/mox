🔍 一、全维代码分析发现

扫描三联盟核心模块（alliance/ 全部 crate + mox-ai-expert-svc/），识别出以下性能瓶颈、架构冗余和未完成功能：

1.1 性能瓶颈

  • 匹配器重复分词 O(N×M)：description_overlap() 每次匹配都对每个专家重新执行 tokenize(&expert_text(expert))，N 专家 × M 次匹配产生大量重复分词。
    scheduler-core/src/matching.rs:273 → 已优化（ExpertTokenCache）
  • LLM 客户端无连接池：OpenAiChatClient::complete() 每次调用都新建 reqwest::blocking::Client，每次都重建 TCP 连接 + TLS 握手。
    mox-ai-expert-svc/src/llm/chat.rs:205 → 已优化（Client 复用 + pool_max_idle_per_host=10）
  • 文件存储全量快照写入：FileTaskRepository::save() 每次写入都执行全量 JSON 序列化 + 磁盘写，高频写入场景下严重拖慢。
    scheduler-core/src/storage.rs:153 → 已优化（BatchedFileTaskRepository 延迟持久化）
  • DAG 调度轮询间隔：调度循环基于 poll_interval_ms 轮询，就绪节点检测有最小延迟约束（默认配置下约 100ms+ 调度周期）。
    executor-core/src/dag_engine.rs:134 → 基准测试中已量化（1ms 间隔下 ~108ms E2E）

1.2 架构冗余

  • Fusion 引擎三重复制：scheduler-core/fusion.rs（685行）、executor-core/fusion.rs（640行）、alliance-core/fusion/（7策略 1900+行）三套实现并存，逻辑高度重叠。
    建议后续统一为 alliance-core/fusion 单一实现
  • DAG 引擎双重复制：scheduler-core/dag_engine.rs（813行）与 executor-core/dag_engine.rs（570行）功能重叠。
    建议后续 scheduler 端仅保留规划，执行统一到 executor-core
  • 匹配器三套实现：matcher.rs（223行，RuleBased）、matching.rs（546行，分词+领域推断）、modular_matcher.rs（519行，模块化）。
    matching.rs 已作为核心算法层，matcher.rs 作为门面，modular_matcher.rs 可评估是否废弃

1.3 未完成功能

  • Scheduler 缺少代理端点：Executor（3200端口）有 /tasks/:id/nodes 和 /tasks/:id/result，但 Scheduler（3100端口）无法代理这些请求，用户必须直连 executor。 已补全
    scheduler-svc/src/routes.rs → 新增 proxy_task_nodes / proxy_task_result
  • 无统一 Metrics 可观测性：匹配耗时、LLM 调用统计、融合耗时、DAG 执行统计均无聚合指标，仅散落在 debug log 中。 已补全
    scheduler-core/src/metrics.rs → 新建 AllianceMetrics（14个 AtomicU64）
  • LLM Router 与实际 LLM 调用未打通：scheduler-core/llm_router.rs（560行，含熔断/降级/路由策略）与 mox-ai-expert-svc/llm/chat.rs（实际 LLM 调用）之间无集成，路由策略未真正生效。 待后续轮次
  • Executor 节点重试/超时/熔断：expert_executor.rs 已有重试逻辑（execute_node_retries_on_failure 测试通过），但超时控制和熔断器未与 LLM Router 集成。 部分完成

⚡ 二、三项性能优化实现

优化 1：匹配器专家 Token 缓存

维度BeforeAfter
分词次数N×M（每次匹配重算）N（一次计算+缓存命中）
核心结构无ExpertTokenCache（RwLock+HashMap）
缓存失效-invalidate(expert_id) / 注册时自动失效
向后兼容-cache: Option<&ExpertTokenCache>，None 保持原行为

修改文件：matching.rs、matcher.rs、modular_matcher.rs

优化 2：LLM 客户端连接池复用

维度BeforeAfter
Client 生命周期每次 complete() 新建new() 时一次性构建，持有复用
TCP 连接每次重建+TLS握手连接池复用（pool_max_idle_per_host=10）
连接超时仅请求超时connect_timeout=10s + 请求超时
Trait 兼容-ChatClient trait 不变，MockChatClient 不变

修改文件：mox-ai-expert-svc/src/llm/chat.rs

优化 3：存储批量写入（BatchedFileTaskRepository）

维度FileTaskRepository（原）BatchedFileTaskRepository（新）
save() 行为内存写入 + 立即全量持久化内存写入 + 标记 dirty，不落盘
持久化触发每次写操作flush() 显式调用 / maybe_flush(interval) 节流
高频写入开销O(N) 序列化 × 每次写入O(1) 内存写 + 周期性 1 次持久化
原子性临时文件+重命名同左（flush 时复用 persist 逻辑）

修改文件：scheduler-core/src/storage.rs（新增结构体，原 FileTaskRepository 不变）

🧩 三、两项模块补全

补全 1：Scheduler 代理端点

  • GET /tasks/:task_id/nodes → 代理到 executor /tasks/:task_id/nodes
  • GET /tasks/:task_id/result → 代理到 executor /tasks/:task_id/result
  • 转发 X-Tenant-Id header，10秒超时
  • executor 不可达 → 503 Service Unavailable
  • executor 错误 → 透传状态码 + body

修改：scheduler-svc/Cargo.toml（+reqwest）、app_state.rs、routes.rs、server.rs

补全 2：Metrics 可观测性模块

  • AllianceMetrics：14 个 AtomicU64 计数器
  • 匹配维度：requests / errors / latency_us（sum+count）
  • LLM 维度：calls / errors / latency_ms（sum+count）
  • 融合维度：calls / latency_ms（sum+count）
  • DAG 维度：executions / node_executions
  • MetricsSnapshot：Serialize，含 avg latency 计算
  • 10 线程并发无竞争验证通过

新建：scheduler-core/src/metrics.rs（+lib.rs 导出）

🚀 七、后续优化方向（第八轮建议）

高优先级

  • LLM Router 与 chat.rs 打通：将 scheduler-core/llm_router.rs 的熔断/降级/路由策略真正接入 mox-ai-expert-svc/llm/chat.rs，实现多 Provider 自动切换
  • Fusion 引擎统一：消除 scheduler-core/fusion.rs 和 executor-core/fusion.rs 的重复实现，统一使用 alliance-core/fusion/
  • DAG 事件驱动调度：替换轮询模式为事件驱动（节点完成时立即触发下游就绪检测），消除 ~100ms 调度基线延迟

中优先级

  • 匹配器 Aho-Corasick 词典匹配：将 DOMAIN_KEYWORDS 的线性扫描替换为 AC 自动机，领域推断从 O(K×T) 降至 O(T+K)
  • Metrics HTTP 端点：在 scheduler-svc 新增 /metrics 端点，输出 AllianceMetrics 的 JSON 快照，对接 Prometheus
  • LLM 响应缓存：对相同 prompt 的 LLM 调用做短时缓存（TTL 60s），减少重复 API 调用和成本
  • 匹配器结果缓存：对相同 task_description 的匹配结果做短时缓存，高并发场景下显著降低匹配延迟
