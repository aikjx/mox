## 1 概述与核心定位

### 1.1 为什么要有关图规范

软件项目在演进中持续产生**隐性依赖**与**信息孤岛**：一段代码偷偷读了一张表，一个定时任务依赖某个外部 API，一份文档描述的接口早已下线，却无人知晓。传统文档滞后于代码，架构图只在立项时画一次。关图规范把"图"从一次性交付物升级为**项目的唯一事实基准（Single Source of Truth）**，所有信息实体及其关系可机读、可校验、可自动同步。

### 1.2 核心定位（一句话）

**一切皆是信息。** 项目内所有可命名、可引用的产物都是"信息节点"；节点之间所有可观测的依赖与交互都是"关联边"。

### 1.3 与业务系统解耦

本规范**不绑定"业务系统"这一狭小范围**。后端服务、前端页面、数据库表、运维脚本、定时任务、配置文件、依赖库、第三方服务、项目文档、代码仓库——全部纳入同一张信息关联关系图。图既是设计图，也是依赖地图，也是知识库。

### 1.4 第一性步骤

> **项目启动第一步骤：搭建本项目信息关联关系图骨架。**
> 后续所有开发、对接、迭代、重构都以这张图作为唯一基准；任何变更（新增/删除/改名/改依赖）必须同步更新关系图，从源头消灭隐性依赖与信息孤岛。

## 2 适用范围与边界

### 2.1 适用

- 软件项目全生命周期：立项、设计、开发、联调、测试、上线、运维、重构。
- 全栈对象：代码文件、数据库、接口、配置、任务、文档、第三方依赖。
- 任意规模：单人项目到跨团队大型工程（图可按子系统分片，再聚合）。

### 2.2 不适用

- 底层硬件/芯片架构（信息图谱不描述物理电路）。
- 非结构化且不可引用的纯媒体资产（视频/图片二进制本身不建模，其元数据可建模）。

## 3 核心概念模型

### 3.1 图模型定义

```
G = (N, E)
N = { n | n 是信息节点 }
E = { e = (n_from, r, n_to) | r 是关联类型 }
```

每个节点 `n` 具备：`(id, kind, name, path, summary, source, created_at, updated_at)`。
每条边 `e` 具备：`(id, from, to, kind, label, evidence)`。

- `id`：全局唯一，建议 `kind:hash(path|name)`。
- `path`：节点对应的物理/逻辑位置（文件路径、表名、服务地址、文档锚点）。
- `evidence`：边的出处（如 "main.rs:42 use operator_core"），保证关系可溯源、可复核。

### 3.2 信息节点分类（12 类，强制覆盖）

| 编号 | kind | 含义 | 典型来源 |
|---|---|---|---|
| N1 | Business | 业务信息/业务能力域 | 业务目录、需求文档、领域术语 |
| N2 | Data | 数据信息/数据结构 | 数据库表、视图、消息 schema、缓存 key |
| N3 | Function | 功能信息/函数方法 | 函数、方法、过程、存储过程 |
| N4 | Interface | 接口信息/契约 | REST/GraphQL/RPC 路由、API 契约 |
| N5 | CodeFile | 代码文件信息 | 源文件（.rs/.py/.ts/.go/.java…） |
| N6 | Script | 脚本信息 | 运维/构建/迁移脚本（.sh/.sql/.py 工具） |
| N7 | ScheduleTask | 定时任务信息 | cron、调度器、周期性 job |
| N8 | Config | 配置信息 | 配置文件（.toml/.yaml/.env）及其键值 |
| N9 | Dependency | 依赖库信息 | 内部/外部依赖（crate/npm/包） |
| N10 | ThirdParty | 第三方服务信息 | 外部 SaaS/API/消息队列/云资源 |
| N11 | Doc | 文档信息 | 设计文档、README、规范、Wiki |
| N12 | Runtime | 运行时信息 | 进程/服务实例/容器/端口（可选扩展类） |

> 注：N12 为可选扩展类，用于把"正在运行的服务实例"纳入图，实现设计态与运行态对齐。

### 3.3 关联边分类（7 类，强制标注）

| 编号 | kind | 含义 | 示例 |
|---|---|---|---|
| E1 | Call | 调用 | 函数调用接口、服务调用服务 |
| E2 | ReadWrite | 读写 | 服务读写数据表、读配置 |
| E3 | Reference | 引用 | 代码 import/use/require、文档引用文档 |
| E4 | Dependency | 依赖 | 模块依赖库、任务依赖上游任务 |
| E5 | Inheritance | 继承/实现 | 类继承、trait 实现、接口实现 |
| E6 | ConfigRef | 配置引用 | 代码读取配置项、任务读取环境变量 |
| E7 | Deploy | 部署/承载 | 服务部署到容器、代码生成产物 |

每条边必须带 `evidence`（可定位出处），无出处的关系视为**未证实关系**，校验阶段须标红。

## 4 图的建立与维护流程（生命周期）

### 4.1 立项：搭建骨架（第一性步骤）

1. 初始化图存储（默认 `graph.json`，或纳入仓库受版本管理）。
2. 扫描现有代码/配置/文档，自动抽取初始节点与边（见第 8 节工具要求）。
3. 人工补录工具无法识别的节点（业务域 N1、第三方 N10、运行时 N12）。
4. 产出首版《信息关联关系图骨架》，作为项目基线交付物准入评审。

### 4.2 日常：变更即同步

- **强制规则 GR‑R1**：任何 PR/提交若新增、删除、改名、改依赖，必须同步更新图（新增节点/边或删除孤儿）。
- 推荐：CI 中挂 `info-graph sync` 比对基线，`drift > 0` 则阻断合并（见 9.4）。
- 人工无法判定的关系，标注 `evidence="manual"`，但不得缺省。

### 4.3 迭代/重构：以图驱动

- 重构前：先在图上模拟删除/移动节点，预览受影响边（影响面分析）。
- 重构后：重新扫描，校验图与代码一致（闭环验证）。

### 4.4 审计

- 图的每次变更保留历史（节点 `updated_at` + 变更日志），支持回溯"某依赖何时引入"。

## 5 建模规则与命名规范

- **GR‑N1** 节点 `id` 全局唯一，同 `path` 不允许重复节点。
- **GR‑N2** `name` 用人类可读原名（函数名、表名、文件名），不得改写。
- **GR‑N3** 跨语言引用统一归一：Rust `use operator_core::X`、Python `from x import Y`、JS `import Y from 'x'` 均解析为对 `X`/`Y` 的 Reference 边，`evidence` 记录原始语句与行号。
- **GR‑N4** 外部不可解析的依赖（如公网 crate）建模为 `Dependency→ThirdParty` 边，标记为 `external=true`。
- **GR‑N5** 文档（N11）必须至少被一个其他节点引用或被引用，否则判为信息孤岛（见 9.2）。

## 6 工具与代码实现要求

关图规范**必须**有可执行的工具支撑，禁止仅停留在文档。工具最低能力集：

1. **扫描器 Scanner**：递归扫描项目目录，按扩展名/语法抽取节点与边（N5/N6/N8/N9/N10/N11、以及 E1~E7 中可静态识别者）。
2. **图存储 Store**：节点/边持久化（默认 JSON，可选 SQLite），支持版本历史。
3. **校验器 Validator**：执行第 9 节全部规则，输出问题清单（退出码非零=不通过）。
4. **导出器 Exporter**：导出 Mermaid/PlantUML/JSON，供文档与画布渲染。
5. **同步比对 Sync**：对比两次快照（old/new），输出新增/删除/改名漂移，供 CI 门禁。
6. **查询器 Query**：按 kind/name/path 检索子图，支撑影响面分析。

> 本规范配套提供参考实现 `tools/info-graph`（纯 Rust std，零外部依赖，可离线编译），可直接扫描本工程生成骨架并接入 CI。

## 7 与 PT‑Primi 规范的关系（兼容与承载）

关图规范与 PT‑Primi（PT‑STD‑V1.0）不冲突，而是**物理底座与上层范式**的关系：

- PT‑Primi 的"六维绑定"（需求‑功能‑业务‑算法‑任务‑代码）在关图规范中即为六类节点（N1/N3/N7/N5 等）与其间绑定边，**关图是六维绑定的可机读载体**。
- PT‑Primi 的 κ‑τ 守恒残差 `ε` 可映射为"图中孤儿节点数 + 悬空边数 + 未证实关系数"的归一化指标，作为图健康度。
- 五代范式（Prompt/Context/Harness/Loop/Graph）资产作为既有节点/边导入关图，无需重构。

## 9 校验规则、约束与强制合规项

### 9.1 结构校验

- **孤儿节点**：除 Doc/Config/Business 允许弱连接外，核心代码/数据/接口节点入度+出度=0 判孤儿（GR‑E1）。
- **悬空边**：边的 `from`/`to` 指向不存在的节点 id（GR‑E2，致命）。
- **未证实关系**：边缺 `evidence`（GR‑E3，标红）。
- **重复 id**：同 `id` 多定义（GR‑E4，致命）。

### 9.2 孤岛与隐性依赖校验

- **信息孤岛**：连通分量规模 ≤ 2 且含 Doc/Config（GR‑E5）。
- **隐性依赖**：边指向图外文件/地址且未建模为 ThirdParty/Dependency（GR‑E6，重点消灭项）。
- **失效引用**：Doc 引用的接口/表在图中已不存在（GR‑E7）。

### 9.3 一致性校验

- **同步漂移**：`sync` 比对 old/new，删除未声明的节点/边超阈值即不合格（GR‑E8）。

### 9.4 强制合规清单（CI 门禁 8 项）

1. 图文件纳入版本管理且非空。
2. 无悬空边（GR‑E2）。
3. 无重复 id（GR‑E4）。
4. 所有边带 evidence（GR‑E3）。
5. 核心节点无孤儿（GR‑E1）。
6. 无未建模的隐性依赖（GR‑E6）。
7. 文档引用全部有效（GR‑E7）。
8. 新变更 sync 漂移 = 0（GR‑E8）。

## 10 风险、边界与缓解

| 风险 | 边界 | 缓解 |
|---|---|---|
| 图随代码腐化 | 人不更新图 | CI sync 门禁 + 提交即同步规则 |
| 扫描误判 | 静态分析有漏/误 | 人工补录 + evidence 复核，允许 `manual` |
| 大项目图爆炸 | 节点过多 | 按子系统分片，按需聚合；查询限深 |
| 过度建模 | 把不该建模的也建 | 仅建模"可引用、可依赖"的信息 |
| 与运行态脱节 | 只建设计态 | P2 接入 N12 运行时节点 |

## 11 术语词典

- **信息节点（InfoNode）**：图中表示一条信息的顶点。
- **关联边（RelationEdge）**：节点间依赖/交互的有向边。
- **隐性依赖（Hidden Dependency）**：存在于代码/配置但未在图中建模的依赖。
- **信息孤岛（Info Silo）**：与其他节点几乎无关联的孤立信息。
- **同步漂移（Sync Drift）**：两次图快照间的未授权差异。
- **证据（Evidence）**：关系边的可定位出处，保证可溯源。
- **关图（InfoGraph）**：本规范定义的信息关联关系图实例。

## 12 附录：参考实现命令速查

```bash
# 扫描工程，生成骨架 graph.json
info-graph build --root . --out graph.json

# 校验（CI 门禁，非零即失败）
info-graph validate --graph graph.json

# 导出 Mermaid 供文档/画布
info-graph export --graph graph.json --format mermaid > graph.mmd

# 影响面：查某节点关联子图
info-graph query --graph graph.json --name operator_core

# CI 同步比对：阻断未同步的提交
info-graph sync --old baseline.json --new graph.json
```
