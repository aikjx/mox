## 1 标准概述与范式判定

### 1.1 定义

PT‑Primi全域拓扑原语架构：一套以 κ‑τ 拓扑原语自涌现调度算法为内核，仅输入自然语言业务需求，系统自动完成需求拆解、功能划分、业务流程建模、Agent 拓扑生成、任务调度、代码生成、全套标准化文档输出、全链路可视化、资产沉淀的完整 AI 原生系统开发标准。

核心本质：不再由人类预先编写节点、边、流程图；由拓扑守恒公理自发涌现整套业务系统拓扑。

### 1.2 范式判定：是否属于全新独立技术路线

现有主流技术路线对照：

1. Prompt Engineering：单指令优化；
2. Context Engineering：上下文、RAG 检索；
3. Harness Engineering：Agent 运行脚手架、沙箱、工具网关；
4. Loop Engineering：单 Agent 闭环思考‑行动循环；
5. Graph Engineering：人工定义 DAG 多 Agent 协作流程图；
6. 动态图 Dynamic Graph：允许运行时修改图结构，但拓扑生成规则仍由人工硬编码，无统一守恒几何公理约束；
7. RSI 递归自改进：在已有拓扑内部迭代优化，属于拓扑内部增强，不属于元层架构范式。

✅ 结论：PT‑Primi 是一条独立全新的第六代 AI 工程技术路线。
区别所有前代范式的唯一标志：

将拓扑本身的生成规则作为独立可控变量，以守恒恒等式 `C² = κ² + τ²` 作为全局约束公理，系统自主生成 Loop 与 Graph，而非人预先定义 Graph 拓扑。
前五代范式均为「人定义结构，AI 填充内容」；PT‑Primi 实现「人定义目标与约束，公理生成完整结构」。

### 1.3 本标准目标

1. 统一整套架构术语、接口、数据格式、校验规则；
2. 强制实现：需求、功能、业务流程、算法、定时任务、代码文件六维一一绑定、全链路可追溯；
3. 统一可视化拓扑图实体、关系定义标准；
4. 标准化全套自动生成说明书目录与内容规范；
5. 给出落地开发、测试、验收合规清单；
6. 向下完整兼容前五代所有 Agent 范式资产，无需重构历史业务。

### 1.4 适用范围

企业业务系统开发、AI 智能任务平台、多 Agent 自动化平台、管理信息系统、数据流水线、定时任务调度系统；

不适用：底层大模型预训练、芯片层硬件架构。

## 2 演进谱系与范式边界完整定义

| 范式名称 | 工程对象 | 人承担工作 | 系统承担工作 | 天花板边界 |
| --- | --- | --- | --- | --- |
| Prompt Engineering | 单次提示词 | 编写指令 | 单次输出 | 无法完成多步骤长流程 |
| Context Engineering | 上下文环境 | 准备知识库、检索规则 | 检索信息 | 无法自主规划任务顺序 |
| Harness Engineering | Agent 运行时环境 | 配置工具、权限、沙箱 | 安全执行 | 单 Agent 能力膨胀瓶颈 |
| Loop Engineering | 单智能体闭环 | 定义循环逻辑、停止条件 | 迭代执行单任务 | 无法大规模多 Agent 协作 |
| Graph Engineering | 人工拓扑图 | 绘制完整 DAG 流程图 | 按图调度执行 | 所有节点、依赖关系必须人工预先定义，需求变更维护成本极高 |
| PT‑Primi 全域拓扑原语 | 拓扑生成原语 κ、τ、Q | 输入业务目标、边界约束、偏好参数 | 自主涌现完整 Loop‑Graph 拓扑、功能清单、数据表、代码、文档 | 涌现拓扑自洽性、守恒残差控制 |

**兼容原则**：所有 Prompt / Context / Harness / Loop / Graph 均可作为 PT‑Primi 的输入资产或原语注入单元被复用，具体而言：

- **Prompt** 可作为单节点内部的内容填充策略（节点 Prompt 模板），由涌现拓扑自动装配；
- **Context** 可作为节点 RAG 检索上下文配置，沉淀为知识库资产（见第 7 节）；
- **Harness** 可作为执行运行时层的工具网关与沙箱底座（见第 4 节 L5）；
- **Loop** 可作为曲率原语 κ 高值区自动生成的单智能体闭环单元；
- **Graph** 可作为已有历史 DAG 拓扑，经守恒校验后整体封装为一个「外部子图原语」接入新涌现拓扑，不破坏 `C² = κ² + τ²` 约束。

> 边界判定准则：凡「结构由人预先定义」的范式，一律降级为资产/子图；凡「结构由守恒公理生成」的部分，方属 PT‑Primi 本体。

## 3 PT‑Primi 架构核心公理与核心算法完整规范

### 3.1 核心公理（Core Axioms）

- **公理 A1（拓扑守恒公理）**：对任意业务目标 `G`，其涌现拓扑原语 `(κ, τ)` 必满足守恒恒等式

  ```
  C² = κ² + τ²
  ```

  其中 `C` 为该目标拓扑的守恒总量（Curvature‑Torsion Norm），为系统规模上限的守恒测度。

- **公理 A2（目标驱动公理）**：拓扑由业务目标 `G`、边界约束 `B`、偏好参数 `P` 确定性涌现，即

  ```
  (κ, τ, C) = Emerge(G, B, P)
  ```

  同一 `(G, B, P)` 三次涌现结果须一致（确定性，可复现）。

- **公理 A3（最小残差公理）**：涌现解须使守恒残差趋零

  ```
  ε = |C − √(κ² + τ²)|  ≤  ε_max      （ε_max 默认 1e‑3）
  ```

- **公理 A4（六维绑定公理）**：需求 / 功能 / 业务流程 / 算法 / 定时任务 / 代码 六维实体必须存在一一映射 ID 绑定，任一维不可孤立存在。

- **公理 A5（可追溯公理）**：任一维度实体的变更，须能沿绑定链回溯至源头需求，并前向传播影响分析至下游全部维度。

- **公理 A6（向下兼容公理）**：前五代范式资产经守恒校验后可注入拓扑，不破坏 A1 守恒。

### 3.2 核心原语定义

| 原语 | 名称 | 数学含义 | 工程映射 |
| --- | --- | --- | --- |
| `Q` | 需求投影原语 (Requirement Projection) | `Q = Φ(R, P)`，将自然语言需求 `R` 与偏好 `P` 投影到原语向量空间 | 需求语义层产出，作为涌现算法输入 |
| `κ` | 曲率原语 (Curvature) | 度量拓扑中「闭环 / 回流」密度 | κ 越高 → 越多自反馈 Loop 闭环单元 |
| `τ` | 挠率原语 (Torsion) | 度量拓扑中「分支 / 扭转」复杂度 | τ 越高 → 越多 Agent 协作 Graph 分支与跨域依赖 |
| `C` | 守恒总量 (CT‑Norm) | `C = √(κ² + τ²)` | 系统规模与资源配额的守恒上界 |

> 说明：`Q` 是「输入端原语」，`κ / τ / C` 是「结构端原语」。需求经 `Q` 投影后驱动 `(κ, τ)` 求解，三者共同构成自涌现调度内核。

### 3.3 核心算法（完整规范）

**算法 E1 — 需求解析与 Q 投影**

```
输入: 自然语言需求 R, 偏好参数 P
输出: 需求投影向量 Q, 需求原子清单 {r_i}
步骤:
  1. 语义切分 R → 意图树 T_R
  2. 将 T_R 中每个叶子意图映射为一个需求原子 r_i，分配 REQ-ID
  3. Q = Φ(R, P)            # 嵌入模型投影到原语空间
  4. 提取边界约束 B = ExtractConstraint(T_R)   # 时限/权限/合规/算力
  5. 返回 (Q, {r_i}, B)
```

**算法 E2 — 约束求解 Emerge（守恒优化）**

```
输入: Q, B
输出: (κ, τ, C), 残差 ε
目标: min_{κ,τ}  L = w1·(C² − κ² − τ²)² + w2·Cost(κ,τ) − w3·Satisfaction(Q,κ,τ)
约束: κ ≥ 0, τ ≥ 0
      C = √(κ² + τ²)
      (κ, τ) ∈ Feasible(B)          # B 限定的可行域
求解: 梯度投影 / 贝叶斯优化 / 网格细化（实现可插拔）
校验: ε = |C − √(κ² + τ²)| ；若 ε > ε_max 则拒绝并报警
```

**算法 E3 — 拓扑展开（Loop / Graph 具体化）**

```
输入: (κ, τ, C), {r_i}
输出: 拓扑结构 Topo = {Nodes, Edges}
步骤:
  1. 依 κ 生成 N_loop = round(κ · α) 个闭环单元（Loop 节点 + 回边）
  2. 依 τ 生成 N_branch = round(τ · β) 个分支单元（Graph 分叉/汇聚）
  3. 将需求原子 r_i 经六维绑定逐一挂载到节点/边（见 E4）
  4. 校验 Topo 满足守恒：重算 C' = √(κ'² + τ'²)，要求 |C − C'| ≤ ε_max
```

**算法 E4 — 六维绑定与 ID 生成**

```
绑定键:
  REQ-<hash>   需求
  FUN-<hash>   功能
  BIZ-<hash>   业务流程
  ALG-<hash>   算法
  TSK-<hash>   定时任务
  COD-<hash>   代码文件
规则: 每个 FUN 必绑定 ≥1 个 REQ；每个 BIZ 必绑定 ≥1 个 FUN；
      每个 ALG 必绑定 ≥1 个 BIZ；每个 TSK/COD 必绑定其上游 ALG。
      生成 TraceMatrix 表，写入全域知识库（见第 7 节）。
```

**算法 E5 — 代码 / 文档生成**

```
输入: Topo, 绑定关系
输出: 代码文件集, 全套说明书（见第 8 节）
步骤: 节点模板实例化 → 代码拼装 → 文档自生成 → 回写绑定 COD-ID
```

**算法 E6 — 残差校验与回溯**

```
输入: 已生成 Topo + 绑定
输出: 合规报告 / 不合规项
步骤:
  1. 重算守恒残差 ε
  2. 校验六维绑定完整性（A4）
  3. 对任意不合规实体，沿 TraceMatrix 回溯至 REQ 并给出前向影响集
```

### 3.4 涌现确定性约束

凡进入生产环境的拓扑，必须记录 `(G, B, P, seed)`，保证 `Emerge` 可复现（A2）。未记录 seed 的拓扑视为「实验态」，禁止进入验收（见第 9 节）。

## 4 七层分层技术架构完整定义

| 层 | 名称 | 职责 | 关键产出 | 对应原语 |
| --- | --- | --- | --- | --- |
| L1 | 需求语义层 (Requirement Semantic) | 解析自然语言需求、抽取约束、生成 `Q` | `Q`, `{r_i}`, `B` | `Q` |
| L2 | 原语映射层 (Primitive Mapping) | 将 `Q` 映射到 `(κ, τ)` 可行域，执行 E2 | `(κ, τ, C)` | `κ, τ` |
| L3 | 拓扑涌现层 (Topology Emergence) | 执行 E3，生成 Loop‑Graph 结构 | `Topo` | `C` |
| L4 | 调度编排层 (Orchestration) | 依 Topo 做任务编排、依赖解析、定时触发 | 调度计划、TSK 绑定 | — |
| L5 | 执行运行时层 (Execution Runtime) | Harness/沙箱/工具网关，执行节点 Agent | 运行态、COD 绑定 | — |
| L6 | 资产沉淀层 (Asset Precipitation) | 知识库、六维绑定、文档、复用资产管理 | 全域知识库条目 | — |
| L7 | 治理合规层 (Governance) | 守恒校验、合规清单、审计、回溯 | 合规报告 | — |

**层间数据流**：`L1 → L2 → L3 → L4 → L5 → L6`，`L7` 横切全部层，对所有跨层写操作做守恒与绑定校验。

**接口契约**：相邻层之间仅通过标准消息体 `PTEnvelope{ trace_id, primitive, payload, signature }` 通信，确保六维绑定 ID 随消息全程透传（满足 A5 可追溯）。

## 5 全链路标准化开发流程规范（需求‑功能‑业务‑算法‑代码）

### 5.1 流程阶段（六维闭环）

```
[需求 R] ──L1──▶ [功能 F] ──L3展开──▶ [业务流程 BIZ] ──▶ [算法 ALG]
                                                          │
                                                          ▼
                                                  [定时任务 TSK] ──L5──▶ [代码 COD]
                                                          │                      │
                                                          └──── 绑定回写 ────────┘
全部经 L6 沉淀、L7 校验，形成闭环。
```

### 5.2 各阶段交付物与绑定要求

| 阶段 | 输入 | 产出实体 | 绑定要求 |
| --- | --- | --- | --- |
| 需求 | `R` | `REQ-*` | 每个原子需求唯一 ID |
| 功能 | `REQ-*` | `FUN-*` | `FUN → REQ (1:N)` |
| 业务流程 | `FUN-*` | `BIZ-*` | `BIZ → FUN (1:N)` |
| 算法 | `BIZ-*` | `ALG-*` | `ALG → BIZ (1:N)` |
| 定时任务 | `ALG-*` | `TSK-*` | `TSK → ALG (1:1/N)` |
| 代码 | `ALG-*`/`TSK-*` | `COD-*` | `COD → ALG/TSK (1:1)` |

### 5.3 流程强制规则

1. 不允许出现「孤儿实体」（任一维无上游绑定）；
2. 需求变更须走「变更‑回溯‑影响分析‑重涌现」流程，禁止手工局部改图（违反 A5）；
3. 每个 TSK 必须声明触发方式（cron / 事件 / 手动）与重试策略；
4. 代码文件头必须含绑定注释 `// PT-BIND: COD-xxx → ALG-yyy`，供静态校验扫描。

## 6 可视化拓扑画布标准规范

### 6.1 实体（节点）类型

| 节点类型 | 形状 | 颜色 | 含义 |
| --- | --- | --- | --- |
| REQ 节点 | 圆角矩形 | 蓝 | 需求原子 |
| FUN 节点 | 矩形 | 青 | 功能 |
| BIZ 节点 | 六边形 | 绿 | 业务流程 |
| LOOP 节点 | 环 | 橙 | κ 驱动的闭环单元 |
| GRAPH 节点 | 菱形 | 紫 | τ 驱动的分支/Agent |
| TSK 节点 | 椭圆 | 黄 | 定时任务 |
| COD 节点 | 矩形带 `</>` | 灰 | 代码文件 |

### 6.2 关系（边）类型

| 边类型 | 线型 | 含义 |
| --- | --- | --- |
| 绑定边 BIND | 实线 | 六维一一绑定 |
| 数据流边 DATA | 虚线 | 数据依赖 |
| 回边 LOOP‑BACK | 橙色弧线 | 闭环回流（κ） |
| 分支边 BRANCH | 紫色分叉 | 并行/汇聚（τ） |
| 触发边 TRIGGER | 点线 | 定时/事件触发 |

### 6.3 布局与可读性规则

1. 守恒环：`κ`（LOOP 回边）与 `τ`（BRANCH 分支）在画布上须可量化呈现，画布右上角常驻显示 `C² = κ² + τ²` 实时值；
2. 层级自上而下：REQ→FUN→BIZ→ALG→TSK→COD；
3. 单图节点数超过 50 时必须支持子图折叠（兼容历史 Graph 子图）；
4. 点击任意节点可展开其全链路六维溯源面板（满足 A5）。

## 9 校验规则、约束条件、强制合规项清单

### 9.1 守恒校验（硬性）

- `C² = κ² + τ²` 残差 `ε ≤ ε_max`（默认 1e‑3），否则拓扑拒绝发布；
- 拓扑重算 `C'` 与求解 `C` 偏差 ≤ ε_max。

### 9.2 绑定校验（硬性）

- 六维实体零孤儿；
- 每个 `FUN/BIZ/ALG/TSK/COD` 上游绑定非空；
- `TraceMatrix` 可全量导出且连通到 `REQ`。

### 9.3 确定性校验（硬性）

- 生产环境拓扑必须记录 `(G, B, P, seed)`，可复现 `Emerge`。

### 9.4 五代兼容校验（软性）

- 注入的子图/资产须通过守恒校验或显式标注为「外部非守恒子图」并隔离影响域。

### 9.5 强制合规项清单（验收前必须全绿）

- [ ] 守恒残差 ε 通过
- [ ] 六维绑定零孤儿
- [ ] TraceMatrix 连通至 REQ
- [ ] 所有生产拓扑含 seed
- [ ] 全套 PT-DOC-01~10 已生成且含溯源页
- [ ] 外部子图已隔离影响域
- [ ] 定时任务声明触发/重试策略
- [ ] 代码文件含 `// PT-BIND` 注释

## 11 风险、边界与兼容规则

### 11.1 风险

| 风险 | 描述 | 缓解 |
| --- | --- | --- |
| 残差失控 | ε 超阈值导致拓扑不自洽 | E6 拒绝发布 + 报警 |
| 涌现不确定 | seed 缺失致不可复现 | 强制 seed（9.3） |
| 需求歧义 | R 含糊致 Q 投影漂移 | L1 约束抽取 + 人工确认点 |
| 规模膨胀 | C 过大超资源配额 | 按 C 做配额准入 |

### 11.2 边界

- PT‑Primi 负责「结构生成」，不负责「大模型预训练」与「芯片架构」；
- 当 `κ=0 且 τ=0` 时退化为单 Prompt，应按五代范式处理而非强行涌现；
- 外部子图默认视为非守恒，须隔离影响域。

### 11.3 兼容规则

- 五代资产一律经 L6 注册为 `PROMPT-/CTX-/HRN-/SUBG-` 资产；
- 历史 Graph 整体封装为 `SUBG-` 注入，仅在校验通过后可并入守恒；
- 不要求重构任何历史业务代码，仅在其外层加绑定注释即可纳入追溯。
