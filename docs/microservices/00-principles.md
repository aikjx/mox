# 00 - 独立部署核心原则

> 独立部署不是简单地把单体拆成多个进程，而是一套完整的架构设计方法论。

## 一、12 条铁律

### 铁律 1：单一职责（Single Responsibility）

每个服务只负责一个业务领域，只做一件事，做好一件事。

- **反模式**：一个服务既管用户认证又管文件存储又管消息推送
- **正模式**：auth-svc 只管认证，storage-svc 只管文件，notification-svc 只管消息

**判断标准**：如果一个服务的描述需要用"和"连接两个以上的业务概念，就应该拆分。

### 铁律 2：独立数据（Database per Service）

每个服务拥有自己的数据库，其他服务不能直接访问本服务的数据库，只能通过 API 访问。

- **反模式**：多个服务共享同一个数据库，直接 JOIN 查询对方的表
- **正模式**：每个服务独立 Schema/DB，服务间通过 gRPC 调用获取数据

**为什么**：数据是服务最核心的私有资产，共享数据库会导致紧耦合、无法独立扩展、 schema 变更互相影响。

### 铁律 3：API 优先（API First）

服务间只通过定义良好的 API（gRPC + Protobuf）通信，API 契约是服务间唯一的耦合点。

- **反模式**：服务 A 直接 import 服务 B 的内部结构体、调用内部函数
- **正模式**：服务 A 通过 gRPC Client 调用服务 B 的公开 API，API 定义在 proto 文件中

**为什么**：API 契约是服务间的边界，明确的契约让服务可以独立演进、独立测试、独立部署。

### 铁律 4：独立部署（Independent Deployment）

每个服务可以独立编译、独立测试、独立发布、独立回滚，不依赖其他服务的发布周期。

- **反模式**：发布服务 A 必须同时发布服务 B 和 C，因为它们有内部依赖
- **正模式**：服务 A 可以在任何时间单独发布，只要保持 API 向后兼容

**为什么**：独立部署是微服务的核心价值，让小团队可以自治、快速迭代、降低发布风险。

### 铁律 5：独立扩展（Independent Scaling）

每个服务可以根据自身负载独立扩缩容，不需要跟着其他服务一起扩容。

- **反模式**：AI 服务高并发时，整个系统一起扩容，图谱存储服务也被迫扩容（浪费资源）
- **正模式**：AI 服务 HPA 自动扩容到 20 副本，图谱存储保持 3 副本不变

**为什么**：不同服务的负载特征完全不同（CPU密集/IO密集/内存密集/GPU密集），独立扩展可以大幅降低资源成本。

### 铁律 6：故障隔离（Fault Isolation）

一个服务的故障不会导致其他服务故障，系统具有优雅降级能力。

- **反模式**：认证服务超时导致所有请求阻塞，整个系统雪崩
- **正模式**：认证服务超时后，网关快速失败并返回降级响应，其他服务正常运行

**为什么**：分布式系统中故障是常态，故障隔离是系统可用性的基础保障。

### 铁律 7：契约兼容（Backward Compatibility）

API 变更必须向后兼容，旧版本客户端可以继续调用新版本服务。

- **反模式**：修改 proto 字段名/类型，导致旧客户端反序列化失败
- **正模式**：只新增字段，不修改/删除已有字段；废弃字段标记 `deprecated = true`，保留至少 2 个版本周期

**为什么**：独立部署意味着服务版本不一致是常态，向后兼容是系统稳定运行的前提。

### 铁律 8：可观测性（Observability）

每个服务必须输出日志、指标、链路追踪，且包含统一的 trace_id 和 tenant_id。

- **反模式**：服务出问题了，不知道哪个环节慢、哪个服务报错、数据流向哪里
- **正模式**：通过 trace_id 可以看到一次请求经过的所有服务、每个环节的耗时和状态

**为什么**：分布式系统排查问题比单体困难 10 倍，没有可观测性就是盲人摸象。

### 铁律 9：配置外部化（Externalized Configuration）

服务配置不硬编码在代码中，通过配置中心管理，支持环境隔离和热更新。

- **反模式**：数据库地址写死在代码里，换环境需要重新编译
- **正模式**：配置从 Nacos/K8s ConfigMap 读取，修改配置不需要重新部署

**为什么**：同一份代码需要在 dev/staging/prod 等不同环境运行，配置外部化是基本要求。

### 铁律 10：无状态服务（Stateless Services）

服务本身不保存状态，所有状态存在数据库/缓存/对象存储中，任何实例都可以处理任何请求。

- **反模式**：用户会话存在服务内存中，用户请求必须路由到特定实例
- **正模式**：会话存在 Redis 中，任何实例都可以处理用户请求，扩容只需加副本

**为什么**：无状态是弹性扩缩容的前提，有状态服务扩容需要数据同步，复杂度极高。

### 铁律 11：自动化一切（Automate Everything）

构建、测试、部署、扩缩容、故障恢复全部自动化，人工操作只用于审批和异常处理。

- **反模式**：每次发布需要 SSH 到服务器手动拉代码、编译、重启
- **正模式**：Git push 触发 CI/CD，自动构建测试、自动部署到 staging、自动灰度到 production

**为什么**：微服务数量多，人工操作不可扩展且容易出错，自动化是运维效率的保障。

### 铁律 12：渐进式拆分（Incremental Decomposition）

不要一步到位拆成几十个微服务，先模块化单体，再按业务价值逐步拆分。

- **反模式**：项目第一天就拆 30 个微服务，结果分布式复杂度把团队拖垮
- **正模式**：先在单体中划清模块边界和内部 API，再优先拆分高变更/高并发的服务

**为什么**：微服务的分布式复杂度（网络延迟、数据一致性、服务发现、可观测性）是有成本的，过早微服务化得不偿失。

## 二、康威定律（Conway's Law）

> "设计系统的组织，其产生的设计等同于组织之内、组织之间的沟通结构。" —— Melvin Conway

**含义**：系统架构反映了团队的沟通结构。如果团队是按职能划分的（前端组、后端组、DBA组），系统就会是分层架构；如果团队是按业务领域划分的（用户组、订单组、支付组），系统就会是微服务架构。

**对 infotopograph 的启示**：

- 如果目标是独立部署的微服务，团队也应该按业务领域组织（AI 团队、图谱团队、平台团队）
- 每个微服务对应一个小团队（2-5 人），团队对服务的全生命周期负责（开发、测试、部署、运维）
- 服务边界应该与团队边界对齐，避免一个服务由多个团队维护（沟通成本高）

## 三、领域驱动设计（DDD）

服务边界的划分应该基于业务领域，而不是技术分层。

### Bounded Context（限界上下文）

每个限界上下文对应一个微服务，上下文内有统一的领域模型和通用语言，上下文间通过 API 通信。

**infotopograph 的限界上下文划分**：

| 限界上下文 | 对应服务 | 核心领域概念 |
|-----------|----------|-------------|
| 身份与访问 | auth-svc, tenant-svc | 用户、角色、权限、租户、令牌 |
| AI 编排 | ai-svc, agent-svc, expert-svc | Prompt、模型、Agent、推理、RAG |
| 知识图谱 | graph-svc, graph-storage-svc, graph-algo-svc | 顶点、边、属性、图谱、算法、本体 |
| 数据存储 | storage-svc, etl-svc, dataplane-svc | 文件、对象、桶、ETL、数据管道 |
| 流程编排 | flow-svc, flow-fusion-svc, operator-svc | 工作流、节点、连线、算子、执行 |
| 业务治理 | compliance-svc, catalog-svc, market-svc | 审计、合规、目录、模板、插件 |
| 平台支撑 | gateway-svc, metering-svc, notification-svc, system-svc | 路由、计量、通知、配置 |

### 上下文映射（Context Mapping）

上下文间的关系类型：

| 关系类型 | 说明 | infotopograph 示例 |
|---------|------|-------------------|
| **Partnership** | 两个上下文协同演进，需要协调发布 | ai-svc ↔ agent-svc |
| **Customer-Supplier** | 上游服务提供 API，下游服务消费，下游可以影响上游 | graph-storage-svc（上游）→ graph-svc（下游） |
| **Conformist** | 下游完全遵循上游的 API 模型，无话语权 | 所有服务 → auth-svc（认证标准） |
| **Anti-Corruption Layer** | 下游创建防腐层，将上游模型转换为自己的模型 | ai-svc 调用外部 LLM API 时的适配层 |
| **Open Host Service** | 上游提供公开的、稳定的 API 协议 | gateway-svc 对外的 REST/gRPC API |
| **Published Language** | 上下文间共享的通用语言/数据格式 | proto 定义的公共消息类型 |

## 四、拆分策略

### 什么时候拆

| 信号 | 说明 |
|------|------|
| **变更频率高** | 某个模块每周都有变更，且变更经常与其他模块冲突 |
| **负载特征不同** | 某个模块是 CPU/GPU 密集型，其他是 IO 密集型，扩容需求不同 |
| **团队规模增长** | 团队超过 8 人，沟通成本指数级上升，需要按领域拆分团队 |
| **故障影响大** | 某个模块的故障会导致整个系统不可用，需要隔离 |
| **技术栈差异** | 某个模块需要不同的技术栈（如 Python for AI），不适合放在 Rust 单体中 |
| **独立发布需求** | 某个模块需要频繁发布（如每天多次），不适合跟着整体版本发布 |

### 什么时候不拆

| 信号 | 说明 |
|------|------|
| **业务边界不清晰** | 领域模型还在快速变化，边界不稳定，拆了还要合并 |
| **团队规模小** | 团队只有 3-5 人，微服务的运维成本超过收益 |
| **分布式经验不足** | 团队没有微服务运维经验，先在单体中练手 |
| **性能要求极高** | 服务间网络延迟不可接受（如亚毫秒级），进程内调用更合适 |
| **数据强一致** | 模块间需要强一致性事务，分布式事务复杂度高 |

### 拆分优先级排序

按以下维度打分（1-5 分），总分高的优先拆分：

| 维度 | 权重 | 说明 |
|------|------|------|
| 变更频率 | 20% | 越频繁越该拆 |
| 负载差异 | 20% | 差异越大越该拆 |
| 故障影响 | 20% | 影响越大越该拆 |
| 边界清晰度 | 15% | 越清晰越容易拆 |
| 团队对齐 | 15% | 有独立团队负责越该拆 |
| 技术栈差异 | 10% | 差异越大越该拆 |

**infotopograph 拆分优先级建议**：

1. **第一梯队（立即拆）**：mox-gateway-svc, mox-ai-svc（含 Python sidecar）, mox-graph-storage-svc
2. **第二梯队（随后拆）**：mox-auth-svc, mox-tenant-svc, mox-graph-svc, mox-agent-svc
3. **第三梯队（逐步拆）**：mox-storage-svc, mox-flow-svc, mox-expert-svc, mox-graph-algo-svc
4. **第四梯队（最后拆）**：其余业务服务，可暂时保留在模块化单体中

## 五、反模式警示

### 反模式 1：分布式单体（Distributed Monolith）

**症状**：拆成了多个服务，但服务间紧耦合，发布必须同时发布多个服务，一个服务挂了全系统挂。

**原因**：没有遵守独立数据和 API 优先原则，服务间共享数据库、直接调用内部函数。

**避免**：严格执行 Database per Service 和 API First，服务间只通过 gRPC 通信。

### 反模式 2：纳米服务（Nanoservices）

**症状**：拆得太细，一个服务只有几个函数，服务间调用链长达 10+ 跳，网络延迟超过计算时间。

**原因**：过度追求单一职责，把一个限界上下文拆成了多个服务。

**避免**：服务粒度以限界上下文为单位，一个上下文一个服务，不要过度拆分。

### 反模式 3：共享数据库（Shared Database）

**症状**：多个服务连同一个数据库，直接查询和修改对方的表。

**原因**：图省事，不想做数据同步和 API 调用。

**避免**：严格执行 Database per Service，跨服务数据通过 API 获取，需要聚合时在 API 网关或 BFF 层做。

### 反模式 4：同步调用链过长（Long Sync Chains）

**症状**：一个请求经过 5+ 个服务的同步调用，任何一个慢都导致整体超时，级联故障。

**原因**：过度使用同步调用，没有引入异步事件驱动。

**避免**：非核心路径用异步消息（NATS），核心路径控制在 3 跳以内，引入熔断降级。

### 反模式 5：忽略可观测性（No Observability）

**症状**：服务出问题了，只能看日志 grep，不知道调用链、不知道指标、不知道哪个服务慢。

**原因**：只关注功能开发，忽视运维能力建设。

**避免**：从第一个微服务开始就接入 OpenTelemetry，日志/指标/链路追踪三位一体。

## 六、总结

独立部署的微服务架构不是银弹，它用分布式复杂度换取了独立部署、独立扩展、故障隔离、团队自治等收益。

**成功的关键**：
1. 渐进式拆分，不要一步到位
2. 清晰的服务边界（基于 DDD 限界上下文）
3. 严格的 API 契约（gRPC + Protobuf，向后兼容）
4. 完善的可观测性（日志+指标+链路追踪）
5. 自动化的 CI/CD（构建+测试+部署+回滚）
6. 足够的分布式系统经验（熔断+降级+限流+数据一致性）

**infotopograph 的路径**：先模块化单体（当前已有较好的模块基础）→ 核心服务优先拆分（网关/AI/图谱存储）→ 逐步全面微服务化。
