## 第1章 总则与适用范围

### 1.1 规范目的

本规范旨在为"开发专家联盟"（Expert Alliance，以下简称"专家联盟"）主题的全部文档建立**可直接执行的归一化工程标准**，确保：

1. **索引声明 = 物理事实**：所有目录声明、文件命名、权威等级标注与仓库物理状态严格一致，杜绝"索引声称存在但物理缺失"或"物理存在但索引未登记"的分裂。
2. **单一事实源（Single Source of Truth）**：同一主题只允许一个 🟢权威文档，其他版本必须标注替代关系或归档，杜绝多版本并存不裁决。
3. **文档-代码对齐**：专家联盟主题文档中所有架构描述、服务端点、专家清单、融合策略必须与 `platform/domains/alliance/` 域真实代码一致，代码是唯一事实源。
4. **引用零断裂**：所有文档间引用统一使用仓根相对路径，新增/移动文件后必须重跑全量引用审计。
5. **术语零漂移**：所有术语以 `docs/GLOSSARY.md` 为唯一事实源，文档中首次出现必须链接，后续使用保持一致。

### 1.2 适用范围

本规范适用于 `infotopograph` 仓库中**所有以"开发专家联盟"为主题的文档**，包括但不限于：

- `docs/expert-alliance/` 目录下全部文档（含子目录 v2/、v3/、architecture/）；
- `docs/standards/` 目录下与专家联盟流程/规范相关的文档（如 `expert-alliance-flow-standard.md`）；
- `docs/working-reports/` 目录下与专家联盟处理模式相关的过程稿；
- `docs/modules/` 目录下 `mox-expert-*` 系列文档；
- 任何其他目录中描述专家联盟架构、服务、专家、融合策略的文档段落。

**不适用范围**：本规范不约束代码本身的编写规范（见 `docs/enterprise/37-企业级处理流程规范-V1.0.md` EP-3），不约束非专家联盟主题的文档（受 `docs/DOC-NORMALIZATION-REPORT.md` 通用规范约束）。

### 1.3 与通用规范 DOC-GOV-V1.0 的关系

| 维度 | DOC-GOV-V1.0（通用） | 本规范 EA-NORM-001（专项） |
|------|----------------------|---------------------------|

## 第2章 目录职责与命名规则

### 2.1 docs/expert-alliance/ 目录职责划分

`docs/expert-alliance/` 是专家联盟主题文档的**唯一权威承载目录**，其内部子目录职责划分如下：

| 子目录 | 职责 | 权威等级 | 允许存放的文档类型 |
|--------|------|:--------:|-------------------|
| `docs/expert-alliance/`（根） | 专家联盟主题的顶层权威文档入口：索引（00-INDEX）、规范总册、架构总纲 | 🟢 | `00-INDEX.md`、本规范引用的顶层权威文档 |
| `docs/expert-alliance/v2/` | 专家联盟 V2 架构版本的设计文档、需求规格、接口契约 | 🟢/🟡 | V2 版本的架构设计、需求规格、API 契约、测试报告 |
| `docs/expert-alliance/v3/` | 专家联盟 V3 架构版本的设计文档、需求规格、接口契约 | 🟢/🟡 | V3 版本的架构设计、需求规格、API 契约、测试报告 |
| `docs/expert-alliance/architecture/` | 专家联盟架构决策记录（ADR）、架构分析报告、跨版本架构对比 | 🟡参考 | ADR 文档、架构分析、技术选型报告、迁移映射表 |

**强制规则**：

1. `docs/expert-alliance/` 根目录**只允许**存放 `00-INDEX.md` 和本规范引用的顶层权威文档，禁止散落过程稿或版本化设计文档。
2. V2/V3 子目录按版本隔离，**禁止**在 v2/ 存放 v3 文档或反之。
3. architecture/ 子目录存放跨版本的架构决策与分析，**不存放**具体版本的需求或设计。
4. 每个子目录必须包含 `00-README.md` 或在父级 `00-INDEX.md` 中登记其内容清单。

### 2.2 与其他目录的边界

| 目录 | 职责边界 | 与专家联盟的关系 |
|------|---------|----------------|
| `docs/enterprise/` | 企业级治理中心：00-INDEX + 编号 01~37 企业级文档 | 专家联盟的组织治理角色（开发联盟 R）定义在 enterprise/ 文档中；专家联盟主题的**专项文档**不放入 enterprise/，除非是企业级编号文档（如 37 号） |
| `docs/modules/` | 模块级设计/参考文档 | `mox-expert-*` 系列模块文档存放于此；若内容升级为专家联盟主题权威文档，应迁移至 `docs/expert-alliance/` 并在 modules/ 保留引用指针 |
| `docs/cosmic-architecture/` | 全域架构专题 | 专家联盟架构若涉及全域架构层面，可在 cosmic-architecture/ 存放跨域分析，但专家联盟**专项文档**以 `docs/expert-alliance/` 为准 |
| `docs/standards/` | 企业级/行业级规范标准 | 专家联盟的流程标准（如 `expert-alliance-flow-standard.md`）存放于此；本规范 EA-NORM-001 也存放于此。standards/ 存放**可复用的规范标准**，expert-alliance/ 存放**主题文档集** |
| `docs/working-reports/` | 过程稿/工作报告 | 专家联盟处理模式的过程稿（如 `mox-expert-alliance-processing-mode.md`）存放于此；过程稿结论沉淀为权威文档后，必须迁移至 `docs/expert-alliance/` 并在 working-reports/ 标注"已被 XX 替代" |

**边界强制规则**：

1. 同一主题文档**不得**同时出现在 `docs/expert-alliance/` 和其他目录中（单一事实源）。若需在其他目录引用，使用仓根相对路径链接。
2. 过程稿从 `docs/working-reports/` 升级为权威文档时，必须执行：迁移至 `docs/expert-alliance/` → 在原位置留下替代声明 → 更新所有引用 → 重跑引用审计。
3. `docs/standards/` 中的规范文档是**可复用标准**，不承载专家联盟主题的具体版本设计；具体版本设计放在 `docs/expert-alliance/v2/` 或 `v3/`。

### 2.3 文件命名规则

#### 2.3.1 命名格式

专家联盟主题文档统一采用以下命名格式：

```
<编号>-<主题>-<版本>.md
```

| 字段 | 规则 | 示例 |
|------|------|------|
| 编号 | 专家联盟文档使用 `EA-` 前缀 + 三位数字，如 `EA-001`；架构决策记录使用 `EA-ADR-NN`；版本化设计文档使用 `EA-V2-001` / `EA-V3-001` | `EA-001`、`EA-ADR-01`、`EA-V2-003` |
| 主题 | 中文或英文短横线连接的主题描述，禁止空格 | `专家联盟架构总纲`、`scheduler-svc接口契约` |
| 版本 | 格式为 `V<主版本>.<次版本>`，如 `V1.0`、`V2.1`；草稿版本加 `-draft` 后缀 | `V1.0`、`V2.0-draft` |

**完整示例**：
- `EA-001-专家联盟架构总纲-V1.0.md`
- `EA-V2-001-scheduler-svc接口契约-V2.0.md`
- `EA-ADR-01-融合策略选型-V1.0.md`

#### 2.3.2 命名强制规则

1. **禁止空格**：文件名中禁止使用空格，使用短横线 `-` 或中文连续字符分隔。
2. **禁止特殊字符**：文件名中禁止使用 `!@#$%^&*()+=[]{}|;:'",.<>?/~` 等特殊字符；允许使用中文、英文字母、数字、短横线 `-`、下划线 `_`、点 `.`。
3. **版本号格式固定**：版本号必须为 `V<数字>.<数字>` 格式，禁止使用 `v1`、`ver1.0`、`最新版`、`final` 等非标准写法。
4. **编号唯一**：每个编号在专家联盟文档全集内唯一，禁止重复使用；废弃编号在 `00-INDEX.md` 中登记为"已废弃"。
5. **可视化产物同位**：`.html` / `.mmd` / `.json` 等可视化产物必须与源 `.md` **同目录存放**，文件名主体一致（仅扩展名不同）。
6. **过程稿后缀**：位于 `docs/_archive/` 的过程稿统一带 `-YYYYMMDD` 后缀。

### 2.4 归档目录规则

#### 2.4.1 docs/_archive/ 的使用

`docs/_archive/YYYY-MM-DD/` 是过程稿、验证快照、被替代文档的**唯一归档目录**。

| 归档类型 | 归档条件 | 归档位置 |
|---------|---------|---------|
| 过程稿 | 结论已沉淀入 🟢权威文档，不再作为独立参考 | `docs/_archive/YYYY-MM-DD/` |
| 被替代文档 | 存在更新版本的 🟢权威文档，旧版本不再维护 | `docs/_archive/YYYY-MM-DD/` |
| 验证快照 | 某次归一化/验证的完整快照，用于追溯 | `docs/_archive/YYYY-MM-DD/` |
| 原始草稿 | 归一化前的原始草稿，保留追溯链 | `docs/_archive/YYYY-MM-DD/` |

#### 2.4.2 归档强制规则

1. **禁止直接删除**：任何已入 git 的文档不得直接删除，必须先归档至 `docs/_archive/YYYY-MM-DD/`，保留 git 历史可回溯。
2. **归档日期目录**：归档按日期组织，日期为归档执行日期（格式 `YYYY-MM-DD`），同一批次归档放入同一日期目录。
3. **替代声明**：被归档的文档必须在其头部添加归档声明块，注明"已被 `<权威文档路径>` 替代，归档日期 `<YYYY-MM-DD>`"。
4. **引用更新**：归档前必须将所有指向该文档的引用更新为指向新的权威文档；归档后原路径引用应全部失效（引用审计验证）。
5. **归档文档权威等级**：归档文档权威等级统一标注为 🟡归档，禁止标注为 🟢权威或 🟡参考。
6. **禁止在归档目录新增权威文档**：`docs/_archive/` 只存放已归档文档，禁止新增未归档的新文档。

## 第3章 文档分层与权威分级

### 3.1 文档分层模型

专家联盟主题文档按职责分为以下 **6 层**，每层有明确的准入条件和权威等级要求：

| 层级 | 名称 | 职责 | 典型文档 | 权威等级 |
|:----:|------|------|---------|:--------:|
| L1 | 权威规范层 | 专家联盟主题的归一化规范、流程标准、治理规则，是所有下游文档的裁决依据 | 本规范 EA-NORM-001、`docs/standards/expert-alliance-flow-standard.md` | 🟢权威 |
| L2 | 架构设计层 | 专家联盟的架构总纲、ADR 决策、跨版本架构分析 | `EA-001-专家联盟架构总纲`、`EA-ADR-*` 系列 | 🟢权威 / 🟡参考 |
| L3 | 需求规格层 | 具体版本的需求规格、接口契约、数据模型 | `EA-V2-001-*`、`EA-V3-001-*` 系列 | 🟢权威 |
| L4 | 流程标准层 | 业务处理流程、操作SOP、验收流程 | 流程标准文档、SOP 文档 | 🟡参考 |
| L5 | 过程稿层 | 正在编写中的草稿、验证报告、工作总结 | 未完成的设计稿、验证报告 | 🟡过程稿 |
| L6 | 归档层 | 已被替代或已沉淀的历史文档 | `docs/_archive/` 下全部文档 | 🟡归档 |

**分层强制规则**：

1. 每篇文档必须明确归属一个层级，在元信息块中声明。
2. L1~L3 层文档必须经过三联盟评审签字才能发布为 🟢权威。
3. L5 过程稿不得被其他文档作为权威依据引用；若需引用，必须先升级为 L1~L3 层文档。
4. L6 归档文档不得被新增引用；已有引用必须在归档时更新。

### 3.2 权威分级体系

本规范复用 DOC-GOV-V1.0 的四级权威分级体系，并针对专家联盟场景细化如下：

| 等级 | 标记 | 含义 | 专家联盟场景细化 | 允许的操作 |
|------|:----:|------|----------------|-----------|
| 权威 | 🟢 | 以该文档为准的单一事实源 | 专家联盟主题的规范、架构总纲、需求规格；同一主题只允许一个 🟢权威 | 可被任意文档引用；修改需 ADR + 三联盟签字 |
| 参考 | 🟡 | 仅供参考，结论已沉淀入 🟢文档 | 流程标准、SOP、架构分析报告；内容可能随权威文档更新而更新 | 可被引用但须注明"参考"；修改需主责联盟审批 |
| 过程稿 | 🟡 | 正在编写中，结论未定型 | 草稿、验证报告、工作总结；不得作为裁决依据 | 不得被其他文档权威引用；可自由修改 |
| 归档 | 🟡 | 已被替代或沉淀，仅供追溯 | 被新版本替代的旧文档、已归档的过程稿 | 不得被新增引用；只读，不得修改 |

### 3.3 文档头部元信息块

**每篇专家联盟主题文档头部必须包含以下元信息块**，格式固定，不得缺项：

```markdown
> **标题**：<文档完整标题>
> **版本**：V<主>.<次>
> **权威等级**：🟢权威 / 🟡参考 / 🟡过程稿 / 🟡归档
> **编号**：<EA-xxx / EA-ADR-NN / EA-Vx-NNN>
> **文档层级**：L1权威规范层 / L2架构设计层 / L3需求规格层 / L4流程标准层 / L5过程稿层 / L6归档层
> **最后更新日期**：YYYY-MM-DD
> **主责联盟**：开发联盟 R / 算法联盟 R / 产品联盟 R
> **单源声明**：本文档是 <主题> 的唯一权威承载。冲突时以 <上级权威文档路径> 为准。
> **替代关系**：（仅被替代/归档文档填写）本文档已被 <新权威文档路径> 替代，归档日期 YYYY-MM-DD。
```

**元信息强制规则**：

## 第6章 文档-代码对齐要求（核心章节）

### 6.1 对齐原则

**代码是唯一事实源（Single Source of Truth）**。专家联盟主题文档中所有关于架构、服务、端点、专家、融合策略的描述必须与 `platform/domains/alliance/` 域的真实代码严格一致。

**核心原则**：
1. 文档描述代码，代码验证文档；文档不得描述代码中不存在的架构或功能。
2. 代码变更时，相关文档必须同步更新（四归三连铁律：需求↔架构↔业务流程↔文档四方同步）。
3. 文档发布前必须通过代码对齐校验清单（§6.6）逐项核对。
4. 发现文档-代码错位时，按错位分级（§6.7）在规定时限内修复。

### 6.2 alliance 域代码结构权威描述

#### 6.2.1 11 crate 结构

`platform/domains/alliance/` 域采用 **11 crate 结构**，按层划分为：

| 层级 | crate 数量 | crate 类型 | 职责 |
|------|:----------:|-----------|------|
| proto | 3 | 协议定义层 | gRPC/HTTP 协议的 `.proto` 文件与生成代码，定义服务间通信契约 |
| core | 4 | 核心逻辑层 | 领域模型、纯业务逻辑、trait 定义、融合策略实现、专家注册表，无 I/O 依赖 |
| svc | 2 | 服务层 | 应用服务 + 基础设施适配（HTTP handler、外部 API client），承载两个运行时服务 |
| sdk | 1 | 客户端库层 | 对外暴露的类型定义 + 客户端库，供其他域或外部系统引用 |
| api | 1 | 契约层 | 域间契约定义（trait / interface / DTO），实现依赖倒置 |
| **合计** | **11** | — | — |

#### 6.2.2 目录结构

```
platform/domains/alliance/
├── proto/          # 3 crate：协议定义层
│   ├── <proto-crate-1>/
│   ├── <proto-crate-2>/
│   └── <proto-crate-3>/
├── core/           # 4 crate：核心逻辑层
│   ├── <core-crate-1>/
│   ├── <core-crate-2>/
│   ├── <core-crate-3>/
│   └── <core-crate-4>/
├── svc/            # 2 crate：服务层
│   ├── scheduler-svc/     # 调度服务（:8081）
│   └── executor-svc/      # 执行服务（:8082）
├── sdk/            # 1 crate：客户端库层
│   └── <sdk-crate>/
└── api/            # 1 crate：契约层
    └── <api-crate>/
```

#### 6.2.3 依赖方向规则

alliance 域内部遵循 DDD 依赖倒置原则：

| 层 | 允许依赖 | 禁止依赖 |
|----|---------|---------|
| proto | 无（最底层） | 任何其他层 |
| core | proto、同层 core | svc、sdk、api |
| svc | core、proto、api | 其他域的 svc（必须通过 api 层 trait） |
| sdk | core 的类型定义 | svc |
| api | core 的类型 | svc、sdk |

### 6.3 服务端点描述规范

专家联盟文档中描述服务端点时，**必须包含**以下字段：

| 字段 | 要求 | 示例 |
|------|------|------|

| 端口 | 服务监听的端口号 | `:8081` |
| 路由 | HTTP 路由路径 | `/api/v1/alliance/schedule` |
| HTTP 方法 | GET / POST / PUT / DELETE / PATCH | `POST` |
| 用途 | 端点的功能描述（一句话） | 提交专家联盟调度任务 |

**服务端点权威清单**：

| crate 名 | 端口 | 路由 | HTTP 方法 | 用途 |
|---------|:----:|------|:---------:|------|
| `scheduler-svc` | `:8081` | `/api/v1/alliance/schedule` | POST | 提交专家联盟调度任务 |

**强制规则**：

| 3 | RRF 融合 | `rrf` | 排序列表的 Reciprocal Rank Fusion（k=60） |
| 4 | 共识提取融合 | `consensus` | 文本型结果的共识提取与分歧保留 |
| 5 | 级联融合 | `cascade` | 多阶段流水线的级联合成 |
| 6 | 辩论收敛融合 | `debate-convergence` | 多专家自适应辩论与收敛检测 |

**强制规则**：
1. 文档中引用融合策略时，必须使用上表中的准确名称和英文标识。
2. **禁止**虚构不存在的融合策略。
3. **禁止**将融合策略数量描述为非6的数字。
4. 融合策略变更时，必须同步更新本文档 §6.5 和所有引用该策略的文档。

### 6.6 对齐校验清单

| 4 | 路由准确 | 文档描述的路由与实际代码路由定义对比 | 所有路由与代码一致 |

### 6.7 错位分级与修复时限

文档-代码错位按严重程度分为三级，各级修复时限如下：

| 等级 | 标记 | 定义 | 示例 | 修复时限 | 责任人 |
|------|:----:|------|------|---------|--------|
| 架构级错误 | 🔴 | 文档描述的架构与代码存在根本性不一致，导致读者无法正确理解系统结构 | 描述为"7服务架构"但实际为2 svc；描述为"15 crate"但实际为11 crate；描述不存在的 crate 或端口 | **24小时** | 开发联盟 R |
| 细节错误 | 🟡 | 文档描述的细节与代码不一致，但不影响整体架构理解 | 路由路径拼写错误；HTTP 方法错误；专家名称错别字；融合策略英文标识大小写错误 | **72小时** | 文档主责人 |
| 术语不统一 | 🟢 | 术语使用与 `docs/GLOSSARY.md` 不一致，但不影响理解 | "专家联盟"与"专家系统"混用；英文缩写大小写不一致 | **随版本修复** | 文档治理专家 |

**修复流程**：
1. 发现错位后，立即在 `docs/expert-alliance/architecture/` 下创建错位登记文档（`EA-ALIGN-错位登记-YYYYMMDD.md`），记录错位位置、等级、修复方案。
2. 🔴架构级错误必须在24小时内修复并发布更新版本；修复期间在文档头部添加"⚠️ 已知错位声明"。
3. 🟡细节错误必须在72小时内修复。
4. 🟢术语不统一随下一个版本修复。
5. 修复完成后必须重跑代码对齐校验清单（§6.6）和引用审计（§4.5）。

## 第7章 归一化处理流程（5步法升级版）

本章基于 `docs/working-reports/mox-expert-alliance-processing-mode.md` 的5步法，升级为**文档归一化专用流程**。每步包含明确的输入、输出、检查点、验收标准。

### 7.1 Step 1 · Locate（定位）

**目标**：识别专家联盟主题文档全集，建立完整清单。

**输入**：
- 归一化主题（如"专家联盟 V2 架构文档归一化"）；
- 仓库当前状态。

**处理步骤**：
1. **全量扫描**：使用 `Glob` 或 `Grep` 扫描仓库中所有与专家联盟主题相关的文档，包括：
   - `docs/expert-alliance/` 下全部文档；
   - `docs/standards/` 下专家联盟相关规范；
   - `docs/modules/` 下 `mox-expert-*` 系列；
   - `docs/working-reports/` 下专家联盟相关过程稿；
   - 其他目录中描述专家联盟的文档段落。
2. **建立清单**：输出文档清单表格，包含：文件路径、文件名、当前权威等级、当前所在目录、文档大小、最后修改日期、是否在索引中登记。
3. **识别边界**：明确哪些文档属于本次归一化范围，哪些不属于（在清单中标注）。

**输出**：
- `EA-NORM-<主题>-文档清单-YYYYMMDD.md`：完整的文档清单表格。

**检查点**：
- [ ] 清单覆盖所有与主题相关的文档，无遗漏。
- [ ] 每个文档的当前权威等级已标注。
- [ ] 归一化范围边界已明确。

**验收标准**：
- 文档清单完整率 100%（与全量 grep 结果对比）。
- 清单中每个文档的路径真实存在。

### 7.2 Step 2 · Audit（审计）

**目标**：逐文档读取，提取元信息，诊断问题。

**输入**：
- Step 1 输出的文档清单。

**处理步骤**：
1. **逐文档读取**：使用 `Read` 工具读取清单中每个文档的完整内容。
2. **提取元信息**：从每个文档头部提取元信息块（标题、版本、权威等级、编号、最后更新日期、单源声明），检查是否完整。
3. **诊断问题**：对每个文档进行以下诊断：
   - 元信息完整性（是否缺项）；
   - 权威等级合理性（是否与文档内容匹配）；
   - 引用合规性（是否含 `../`、裸名、绝对路径）；
   - 引用有效性（目标文件是否存在、锚点是否有效）；
   - 术语一致性（是否与 `docs/GLOSSARY.md` 一致）；
   - 代码对齐性（架构/服务/专家/策略描述是否与代码一致）；
   - 内容重叠度（与其他文档的段落级重复）；
   - 索引登记状态（是否在 `00-INDEX.md` 中登记）。
4. **输出诊断报告**：每个文档输出诊断结果，标注问题类型、严重度、位置。

**输出**：
- `EA-NORM-<主题>-审计报告-YYYYMMDD.md`：逐文档诊断结果汇总。

**检查点**：
- [ ] 每个文档都已完整读取。
- [ ] 元信息提取完整。
- [ ] 所有问题已标注类型和严重度。
- [ ] 代码对齐问题已识别（🔴架构级 / 🟡细节 / 🟢术语）。

**验收标准**：
- 文档读取率 100%。
- 问题诊断覆盖率 100%（每个文档至少完成8项诊断）。
- 🔴架构级错误已全部识别并标注。

### 7.3 Step 3 · Compare & Decide（比对与裁决）

**目标**：识别重复/冲突，裁决权威版本，制定归一化方案。

**输入**：
- Step 2 输出的审计报告。

**处理步骤**：
1. **识别重复**：对内容重叠度高的文档簇进行分析，判定是"平行冗余"还是"衍生关系"（原始草稿→归一化权威）。
2. **识别冲突**：对描述同一主题但内容不一致的文档，按权威链优先级裁决。
3. **裁决权威版本**：
   - 同一主题多个 🟢权威文档：保留最新/最完整的一个，其他降级或归档；
   - 过程稿结论已成熟：升级为权威文档，迁移至 `docs/expert-alliance/`；
   - 被替代文档：降级为 🟡归档，迁移至 `docs/_archive/YYYY-MM-DD/`。
4. **制定归一化方案**：输出详细的归一化执行方案，包含：
   - 每个文档的处置决策（保留/升级/降级/归档/合并/删除）；
   - 文件移动/重命名计划；
   - 引用修复计划（哪些引用需要更新）；
   - 元信息补齐计划；
   - 代码对齐修订计划；
   - 索引更新计划。
5. **三联盟评审**：归一化方案需经三联盟评审签字（开发联盟 R 主责，算法联盟/产品联盟 C）。

**输出**：
- `EA-NORM-<主题>-裁决方案-YYYYMMDD.md`：归一化执行方案（含三联盟签字）。

**检查点**：
- [ ] 所有重复文档簇已识别并裁决。
- [ ] 所有冲突文档已按权威链裁决。
- [ ] 同一主题只保留一个 🟢权威文档。
- [ ] 归一化方案已包含每个文档的处置决策。
- [ ] 引用修复计划完整。
- [ ] 三联盟已签字。

**验收标准**：
- 重复/冲突文档裁决率 100%。
- 归一化方案可执行（每个操作有明确的源路径、目标路径、操作类型）。
- 三联盟签字齐全。

### 7.4 Step 4 · Implement（执行）

**目标**：按裁决方案执行归一化操作。

**输入**：
- Step 3 输出的裁决方案。

**处理步骤**：
1. **合并文档**：对需要合并的文档，将内容整合到权威文档中，保留有价值的段落，删除重复内容。
2. **归档文档**：
   - 使用 `git mv` 将被归档文档移动至 `docs/_archive/YYYY-MM-DD/`；
   - 在归档文档头部添加归档声明块（替代关系、归档日期）；
   - 将权威等级改为 🟡归档。
3. **升级文档**：
   - 将过程稿从 `docs/working-reports/` 迁移至 `docs/expert-alliance/` 对应子目录；
   - 补齐元信息块（版本、权威等级、编号、单源声明）；
   - 在原位置留下替代声明指针。
4. **修复引用**：
   - 全量更新所有指向被移动/归档文档的引用，改为指向新的权威文档；
   - 修复所有 `../`、裸名、绝对路径引用为仓根相对路径；
   - 修复所有断锚引用。
5. **补齐声明**：
   - 为缺少元信息块的文档补齐头部元信息；
   - 为缺少单源声明的文档补齐声明。
6. **代码对齐修订**：
   - 按 §6.6 校验清单逐项修复文档-代码错位；
   - 🔴架构级错误优先修复（24h内）；
   - 更新服务端点、专家清单、融合策略描述为代码准确值。
7. **更新索引**：
   - 更新 `docs/expert-alliance/00-INDEX.md`（或对应目录的索引），登记所有文档的当前状态；
   - 确保索引声明 = 物理事实。

**输出**：
- 归一化后的文档集（物理状态已更新）；
- `EA-NORM-<主题>-执行记录-YYYYMMDD.md`：执行操作记录（每个操作的时间、结果、git commit hash）。

**检查点**：
- [ ] 所有合并操作已完成。
- [ ] 所有归档操作已完成（使用 git mv，历史可回溯）。
- [ ] 所有升级操作已完成。
- [ ] 所有引用已修复（0 处断链、0 处不合规）。
- [ ] 所有元信息已补齐。
- [ ] 所有代码对齐错误已修复。
- [ ] 索引已更新。
- [ ] 所有操作已 git commit。

**验收标准**：
- 裁决方案执行率 100%。
- 引用合规率 100%（0 处 `../`、裸名、绝对路径）。
- 引用有效率 100%（0 处断链、0 处断锚）。

**目标**：逐文件回读、引用审计、代码对齐校验、索引一致性校验，确认归一化质量。

## 第8章 反模式清单

本章列出专家联盟文档归一化中**禁止的做法**，每条含反模式名称、表现、危害、正确做法。

### AP-01 多版本并存不裁决

| 维度 | 内容 |
|------|------|
| **表现** | 同一主题存在多个 🟢权威文档或多个内容高度重叠的文档，未裁决哪个是唯一权威，读者无法判断以哪个为准 |
| **危害** | 读者困惑，引用混乱，内容冲突时无法裁决；违反单一事实源原则 |
| **正确做法** | 按 §3.4 权威链规则，同一主题只保留一个 🟢权威文档；其他降级为 🟡参考或归档，并在元信息块注明替代关系 |

### AP-02 索引声明与物理事实不符

| 维度 | 内容 |
|------|------|
| **表现** | `00-INDEX.md` 中登记的文档路径、数量、权威等级与物理目录中的实际状态不一致（如索引声称某文件在 v2/ 但实际在根目录，或索引未登记已存在的文件） |
| **危害** | 读者按索引找不到文件，或遗漏重要文档；破坏"索引声明 = 物理事实"的治理基础 |
| **正确做法** | 每次新增/移动/归档文档后，必须同步更新索引；Step 5 Verify 必须执行索引一致性校验（§7.5 第4项） |

### AP-03 文档描述过时架构

| 维度 | 内容 |
|------|------|
| **表现** | 文档中描述已不存在的旧架构，如"7服务架构"、"31微服务"、"15 crate扁平模型"、`platform/domains/ai-agent` 等旧路径 |
| **危害** | 新人按文档找不到代码；文档-代码全面分裂；违反"代码是唯一事实源"原则 |
| **正确做法** | 文档中所有架构描述必须与 `platform/domains/alliance/` 真实代码一致（11 crate、2 svc、:8081/:8082）；发布前必须通过 §6.6 代码对齐校验清单；发现过时描述按 🔴架构级错误24h内修复 |

### AP-04 使用 ../ 或裸名引用

| 维度 | 内容 |
|------|------|
| **表现** | 文档中使用 `../enterprise/02-architecture.md`、`EA-001.md`、`./design.md` 等非仓根相对路径引用 |
| **危害** | 文件移动后引用失效；引用格式不统一，难以审计和批量修复 |
| **正确做法** | 所有引用统一使用仓根相对路径 `docs/<rel-path>`（§4.1）；引用审计中发现 `../` 或裸名引用即判定为不合规，必须修复 |

### AP-05 权威等级缺失或滥用

| 维度 | 内容 |
|------|------|
| **表现** | 文档头部缺少权威等级标注；或将过程稿标注为 🟢权威；或将已归档文档标注为 🟡参考；同一主题多个 🟢权威 |
| **危害** | 读者无法判断文档可信度；权威链失效；冲突无法裁决 |
| **正确做法** | 每篇文档头部必须包含元信息块（§3.3），权威等级必须与文档实际层级和内容匹配；同一主题只允许一个 🟢权威（§3.4） |

### AP-06 术语不统一

| 维度 | 内容 |
|------|------|
| **表现** | 同一文档或跨文档中使用不同术语指代同一概念（如"专家联盟"和"专家系统"混用）；术语大小写不固定（如 `Expert Alliance` 和 `expert alliance` 混用）；使用未在 `docs/GLOSSARY.md` 登记的新术语 |
| **危害** | 术语漂移，读者困惑；违反术语单源管理原则；CI lint 失败 |
| **正确做法** | 所有术语以 `docs/GLOSSARY.md` 为唯一事实源（§5.1）；首次出现必须链接到 GLOSSARY（§5.3）；新术语必须先登记再使用（§5.2）；术语变更遵循 §5.4 流程 |

### AP-07 可视化产物与源 .md 不同位

| 维度 | 内容 |
|------|------|
| **表现** | `.html` / `.mmd` / `.json` 等可视化产物与源 `.md` 文件存放在不同目录（如源 `.md` 在 `docs/expert-alliance/v2/` 但 `.html` 在 `docs/` 根目录） |
| **危害** | 可视化产物难以关联到源文档；移动源文档时产物遗漏；违反 DOC-GOV-V1.0 可视化产物同位规则 |
| **正确做法** | 可视化产物必须与源 `.md` **同目录存放**，文件名主体一致（§2.3.2 第5条）；移动源文档时必须同步移动同位的可视化产物 |

### AP-08 个人判断混入原始结论不标注

| 维度 | 内容 |
|------|------|
| **表现** | 在引用原始文档/数据/代码结论时，混入个人判断或推测，但未明确标注哪些是原始结论、哪些是个人分析 |
| **危害** | 读者无法区分事实与观点；可能误导决策；违反"原始结论可追溯"原则 |
| **正确做法** | 引用原始结论时必须注明来源（仓根相对路径 + 锚点）；个人判断必须显式标注"【分析】"或"【建议】"前缀；不得将个人推测包装为原始结论 |

### AP-09 直接删除文档而非归档

| 维度 | 内容 |
|------|------|
| **表现** | 使用 `git rm` 或文件系统删除直接移除文档，未先归档至 `docs/_archive/YYYY-MM-DD/` |
| **危害** | 丢失历史追溯链；无法回退；可能导致引用断链且无法修复；违反"过程稿仅可位于 `_archive/`"规则 |
| **正确做法** | 任何已入 git 的文档不得直接删除（§2.4.2 第1条）；必须先归档至 `docs/_archive/YYYY-MM-DD/`，保留 git 历史可回溯；归档前必须更新所有引用 |

### AP-10 归一化后不重跑引用审计

| 维度 | 内容 |
|------|------|
| **表现** | 完成归一化操作（移动/重命名/归档/合并）后，未执行全量引用审计，直接宣布归一化完成 |
| **危害** | 可能存在未修复的断链、断锚、不合规引用；归一化质量无法保证；违反"没有验证 = 没完成"铁律 |
| **正确做法** | 归一化操作完成后必须执行 Step 5 Verify（§7.5），其中包含全量引用审计（§4.5）；引用审计通过（0 断链、0 断锚、0 不合规）方可宣布归一化完成 |
