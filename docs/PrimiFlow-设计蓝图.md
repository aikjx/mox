# PrimiFlow 全域原语智能自动化平台 —— 完整设计蓝图

> 演进定位：`Prompt → Context → Harness → Loop → Graph → PrimiFlow（κ‑τ 拓扑原语引擎）`
>
> 核心目标：用户输入自然语言业务需求 → 平台全自动完成 **需求拆解 / 业务流程建模 / 功能定义 / 模块划分 / 算法编排 / 代码生成 / 可视化拓扑图 / 全套标准化说明书**。
> 做到 **需求‑功能‑算法‑业务流‑代码 五者一一绑定可追溯**，所有链路透明可查、文档自动归档，整个系统 **自描述、自说明、可审计、可复现**。

## 〇、定位：PrimiFlow 不是新仓库，而是 OUS 的「大脑层」

PrimiFlow 构建在 **operator-unified-system（OUS v3.0.0-ai-powered）** 之上，是架在现有能力之上的**元调度层**，而非替代。它指挥大模型、规划算法、RAG、代码生成、定时任务如何组合。下列现有 crate 已提供底座，本文档标注其复用点：

| 现有 crate | PrimiFlow 中承担的角色 |
|---|---|
| `crates/operator-core` | 守恒律内核（`conservation.rs` 已实现 L1/L2/Sum 残差监控），是 κ‑τ 守恒 `C²=κ²+τ²` 的数学底座；`category.rs`/`monad.rs` 提供范畴论原语抽象 |
| `crates/flow-ai` | `topology.rs` 六维实体关系拓扑网（Dijkstra 最短路径、权重衰减、级联影响 `impact_of`）；`critpath.rs`/`dataflow.rs`/`schedule.rs`/`pipeline.rs` 提供 DAG/关键路径/调度/流水线 |
| `crates/operator-graph` | 有向加权图数据结构与基础图算法 |
| `crates/optimizer` | 资源约束优化、关键路径优化 |
| `crates/expert-alliance` | LLM 需求编译（`rbac` 鉴权、`audit` 哈希链审计、多专家协同求解） |

| `crates/business-catalog` | 业务目录、螺旋模型（`spiral.rs`）沉淀业务资产 |
| `crates/runtime` | Axum REST/WebSocket 服务、治理台 handlers |
| `crates/hermes-flow-bridge` | 流程桥接、会话录制、规范化、插件总线 |
| `frontend/` | Vue3 + Three.js 可视化画布（拓扑图/ER 图渲染） |

## 一、整套系统用到的全部算法清单（分层）

### 顶层调度核心算法（自研主算法）

**κ‑τ 拓扑原语自涌现调度算法（核心）**

守恒约束：

```
C² = κ² + τ²
```

- **κ 曲率**：复用、收敛、遵循已有业务规范、调用成熟模块；值越大代表越「保守、复用」。
- **τ 挠率**：创新、拆分、新建功能、新建子 Agent、开新业务分支；值越大代表越「激进、新建」。
- **C 总拓扑常数**：由项目规模、算力、交付周期、风险等级计算得出，是预算天花板。
- **Q 拓扑荷**：验证通过、稳定运行的完整拓扑被打上拓扑荷，存入全域拓扑知识库，永久沉淀。
- **R̂ 正则化算子**：校验循环依赖、需求‑功能不匹配、逻辑矛盾、资源超限，自动修剪无效分支。

> 它不是替代大模型，而是**元调度层**：指挥大模型、规划算法、RAG、代码生成、定时任务编排如何组合。

### 中层支撑算法包（内置可调用能力库）

| # | 算法 | 作用 | 现有落地 |
|---|---|---|---|
| 1 | 需求语义拆解 | 意图拆分算法 + 层次化需求树生成（大模型结构化输出 + 语义相似度聚类） | `expert-alliance` 需求编译 |
| 2 | 实体关系抽取 | 业务实体、角色、单据、事件、约束条件抽取 | `ai-agent` 对话知识图谱 |
| 3 | RAG 向量检索 | 全域知识库召回历史需求、业务流程、已有功能模块、现成代码片段 | 待接向量库 |
| 4 | 依赖拓扑排序 | DAG 有向无环图校验，保证业务流程先后顺序合法、消除环依赖 | `flow-ai` DAG/`critpath` |
| 5 | 冲突检测 | 多需求功能冲突、数据表字段冲突、定时任务时间冲突校验 | `flow-ai/schedule` + 新增强则 |
| 6 | 拓扑相似度匹配 | 新需求与历史已沉淀业务拓扑匹配，优先复用成熟方案 | `flow-ai/topology` `search`/`route` |
| 7 | 任务调度器 | 定时/异步/事件驱动任务编排（Cron 表达式自动生成、任务依赖链） | `flow-ai/schedule` |

### 底层基础模型能力

- 通用大模型：需求解析、自然语言转结构化规格、文档撰写、代码生成
- 代码解释器：语法校验、单元测试自动生成
- 可视化渲染引擎：自动把 DAG 拓扑数据渲染成业务流程图、ER 图、功能关联图（`frontend/` Vue3 + Three.js）

## 二、完整落地架构分层（从前端交互 → 内核引擎 → 数据层）

### 层1：前端可视化画布工作台（用户唯一交互入口）

**核心作用**：统一视图，一张关系图看见全部需求、功能、业务节点、算法、定时任务、代码文件之间的关联连线。

**功能**：
1. **需求视图**：以需求作为根节点，向外辐射关联——对应哪些功能模块、哪些业务流程、用到哪些算法、哪些代码仓库文件、哪些定时任务。
2. **拓扑画布两种模式**
   - 观测模式（默认）：引擎自动生成完整拓扑，用户只看、批注、设置约束，不用手动画图；
   - 微调模式：人工拖拽调整依赖关系、增删约束，修改后引擎重新校验整套拓扑一致性。
3. **点击任意节点展开详情面板**
   - 需求：需求原文、验收标准、优先级；
   - 业务节点：业务处理逻辑、前置条件、后置输出；
   - 功能：接口定义、入参出参；
   - 算法：算法说明、参数、κ/τ 配置、约束条件；
   - 代码：文件路径、类名、函数，自动跳转代码预览；
   - 定时任务：Cron 规则、执行时机、依赖任务、失败重试策略。
4. **一键导出整套项目说明书**（PDF / Markdown）。

> 现有基础：`frontend/` 已是 Vue3 + Three.js 画布，可直接扩展为「需求根节点辐射图」。

### 层2：需求解析与结构化建模服务

- **输入**：用户自然语言描述业务。
- **输出**：标准化结构化需求树。
- **处理逻辑**：
  1. 提取：业务目标、角色、输入输出、规则、限制条件、定时任务、外部系统对接要求；
  2. 自动拆分为一级需求、二级子需求；建立需求编号**唯一 ID**，作为全系统唯一溯源主键。

> 所有后续一切（功能、流程、代码、文档）全部绑定这个需求 ID，实现一一对应。现有 `expert-alliance` 的「LLM 需求编译」已具备结构化输出能力，本层为其封装 + 分配全局唯一 `REQ-{uuid}`。

### 层3：κ‑τ 拓扑原语引擎【系统大脑】

完整内部处理流水线：

```
结构化需求树
    ↓
知识库检索（历史拓扑、模块、代码）
    ↓
初始化 C、κ₀、τ₀
    ↓
拓扑生成器：自动生成
    ├─ 功能清单
    ├─ 业务流程 DAG 图
    ├─ 所需 Agent 任务链
    ├─ 使用的算法组件
    ├─ 数据表结构
    ├─ 接口定义
    ├─ 定时 / 异步任务
    └─ 代码模块规划
    ↓
正则化算子 R̂ 校验
    ├─ 需求‑功能覆盖校验：每个需求必须有对应功能实现，无遗漏
    ├─ DAG 环依赖检测
    ├─ 冲突检测（功能冲突 / 数据字段冲突 / 定时任务时间冲突）
    ├─ 守恒约束校验（C² = κ² + τ²）
    ├─ 资源超限校验（算力 / 周期 / 风险预算）
    ├─ 逻辑矛盾校验（约束互斥、前置后置不可达）
    └─ 自动修剪无效分支（R̂ 输出有效子图）
    ↓
拓扑荷 Q 打标与沉淀
    ↓
引擎输出物（拓扑包 TopologyBundle）
```

#### 3.1 初始化：C、κ₀、τ₀ 的确定

- **C（总拓扑常数）** 由四因子加权决定：

  ```
  C = w_scale·S + w_compute·P + w_cycle·T + w_risk·R
  ```

  其中 `S`=项目规模、`P`=算力预算、`T`=交付周期（越紧 C 越小）、`R`=风险等级（越高 C 越小，留冗余）。`w_*` 为可调权重。

- **κ₀ / τ₀ 初值分配**：在预算 `C` 约束下，先按历史复用率给一个先验偏好：
  - 若相似拓扑匹配度高 → κ₀ 偏高（优先复用）；
  - 若需求含「新建 / 创新 / 未有过」关键词 → τ₀ 偏高（倾向新建）。
  - 满足 `κ₀² + τ₀² ≤ C²` 方可进入生成；否则先降 τ 再降 κ。

#### 3.2 正则化算子 R̂ 校验（续写你截断处）

`R̂` 是一组可组合的校验‑修剪算子，对生成的原始拓扑 `G_raw` 做变换，输出**合法子图** `G_valid = R̂(G_raw)`：

1. **需求‑功能覆盖校验**
   - 遍历需求树每个叶子节点 `REQ_i`，要求存在功能节点 `FUN_j` 且边 `covers(REQ_i, FUN_j)` 存在；
   - 未覆盖需求 → 回退拓扑生成器补全功能，或标记「人工待确认」；
   - 覆盖矩阵写入五向绑定表（见第六节）。

2. **DAG 环依赖检测**
   - 对业务流程图做拓扑排序（`flow-ai`/`operator-graph` 已有）；存在环 → 定位环中节点，按 κ/τ 与依赖强度建议断边，或升级为事件驱动解耦。

3. **冲突检测**
   - *功能冲突*：两个需求要求同一资源互斥状态（如「只读」vs「可写」）→ 报警；
   - *数据表字段冲突*：不同模块定义同名字段但类型/约束不一致 → 统一或加命名空间；
   - *定时任务时间冲突*：Cron 表达式重叠且争用同一资源 → 错峰或串行化。

4. **守恒约束校验（核心数学不变量）**
   - 对每个拓扑切片验证 `C² − (κ² + τ²) ≥ 0`；
   - 若 `κ²+τ² > C²`（超出预算）→ 削减 τ（合并新建分支）或削减 κ（去重复用），直至守恒。
   - 复用 `operator-core/conservation.rs` 的残差监控，把该约束登记为一条守恒律 `KappaTauConservation`。

5. **资源超限校验**
   - 算力、交付周期、风险额度任一超 `C` 分解预算 → 标记超限节点，R̂ 修剪或降级。

6. **逻辑矛盾校验**
   - 约束互斥（A 要求「前置 B 完成」且 B 要求「前置 A 完成」）、前置条件不可达、后置输出无消费者 → 标记矛盾边。

7. **自动修剪无效分支**
   - 以上校验产生的「未覆盖需求补全后仍无效 / 矛盾不可解 / 超限不可降」的分支，由 R̂ 置为 `pruned` 并保留原因标签，不参与后续编排，但留在审计轨迹中可追溯。

> `R̂` 输出：`G_valid` + `prune_report`（每条修剪对应的需求 ID、原因、原始 κ/τ），全部写入审计哈希链（`expert-alliance/audit`）。

#### 3.3 拓扑荷 Q 打标与沉淀

- 当 `G_valid` 通过**端到端验证**（跑通一次真实执行且无 R̂ 报错）后，对其打**拓扑荷 Q**：
  - `Q = hash(G_valid 的结构指纹 + 验证通过证据)`；
  - 存入**全域拓扑知识库**（`business-catalog` 螺旋沉淀扩展），后续新需求经「拓扑相似度匹配」可直接复用带 Q 的成熟拓扑，κ 自动拉高。
- Q 是「可被信任复用」的印记，也是知识库防退化的核心：带 Q 拓扑优先于未验证拓扑被 R̂ 保留。

#### 3.4 引擎输出物（TopologyBundle）

一次完整运行产出结构化包，供层4~层7 消费：

```jsonc
{
  "requirement_id": "REQ-xxxx",
  "topology": { "functions":[], "flow_dag":[], "agents":[], "algorithms":[],
                "schemas":[], "interfaces":[], "tasks":[], "code_modules":[] },
  "constants": { "C": 12.0, "kappa": 8.2, "tau": 8.7, "Q": "abc123..." },
  "bindings": { "req_fun":[], "fun_algo":[], "fun_flow":[], "flow_code":[] },
  "prune_report": [], "audit_ref": "audit://chain/..."
}
```

### 层4：算法编排执行层

将层3 的 `algorithms` + `agents` 实例化为**可执行任务链**：

- 用 `flow-ai/pipeline.rs` 把算法组件按 DAG 串联；
- 用 `flow-ai/schedule.rs` 生成 Cron / 异步 / 事件触发规则与依赖链；
- 用 `expert-alliance` 多专家协同执行（算法专家 / 业务专家 / 数据专家 / 资源专家）；
- κ 高的分支 → 直接调用已验证带 Q 拓扑或成熟模块；τ 高的分支 → 启动子 Agent 新建求解。

### 层5：代码生成层

- 依据 `code_modules` 规划，调用通用大模型生成代码骨架与实现；
- 代码解释器做语法校验 + 自动生成单元测试（`ai-agent` 代码解释器能力）；
- 生成文件落盘到对应 crate / 模块，并回填 `flow_code` 绑定（文件路径、类名、函数名）；
- 生成的代码经 `cargo build` / `cargo test` 冒烟（复用现有 `ci_run*.sh`、`verify_tests.sh`）。

### 层6：数据层（全域拓扑知识库 + 五向绑定存储）

- **全域拓扑知识库**：存储带 Q 的成熟拓扑、历史需求树、业务模块、现成代码片段（供 RAG 检索）；
- **五向绑定存储**：以需求 ID 为主键的关系表，持久化 `需求↔功能↔算法↔业务流↔代码↔定时任务` 全部边；
- 存储介质：SQLite（`operator_dialogue.db` 同款底座）+ 向量库（RAG 相似度）。所有写操作进 `expert-alliance` 审计哈希链，满足可审计、可复现。

### 层7：可视化与文档自生成层

- 消费 `TopologyBundle`，由 `frontend/` 渲染：需求辐射图、业务流程图、ER 图、功能关联图、定时任务甘特；
- 触发**全链路文档自生成体系**（见第三节）产出四套标准化说明书；
- 一键导出 PDF / Markdown。

## 三、全链路文档自生成体系

> 目标：让系统「自描述、自说明」。每一份文档都从 `TopologyBundle` 自动渲染，且反向可溯源到需求 ID。

### 3.1 四套标准化说明书

| 文档 | 内容来源 | 触发时机 |
|---|---|---|
| **业务手册** | 需求树 + 业务流程 DAG + 角色/单据/事件 + 验收标准 | 拓扑通过 R̂ 即生成 |
| **算法说明** | `algorithms` 节点（说明/参数/κ-τ 配置/约束）+ 守恒校验记录 | 同业务手册 |
| **定时任务说明书** | `tasks`（Cron 规则/执行时机/依赖/失败重试策略）+ 冲突检测结果 | 调度编排完成后 |
| **AI 融合方案** | 哪些环节由 LLM/Agent 接管、提示词策略、人工兜底阈值、RAG 召回来源 | 端到端验证通过、打 Q 前 |

### 3.2 文档生成机制

- **模板驱动**：每类文档一套 Markdown 模板（占位符 = `TopologyBundle` 字段）；
- **五向注入**：每份文档页眉自动印「需求 ID / 拓扑 Q / 生成时间 / 审计链引用」，正文内每个功能/算法/任务节点都可点击溯源到对应需求与代码；
- **增量重生成**：微调模式改动拓扑后，R̂ 仅对受影响节点重校验，文档按 `impact_of` 级联范围局部重建，不全量重来；
- **可追溯闭环**：文档 ↔ 代码双向链接——文档点节点跳代码预览，代码注释反向标注 `REQ-xxxx` 与 `Q`。

### 3.3 自描述 / 自说明 / 可审计 / 可复现 的落地

- **自描述**：引擎输出物自带 `constants` + `bindings`，无需外部说明即懂；
- **自说明**：四套文档 + 节点详情面板自动生成；
- **可审计**：R̂ 修剪报告、Q 打标证据、全部写入哈希链；
- **可复现**：给定 `REQ-xxxx` + 知识库快照，可重新跑出完全一致拓扑与文档。

## 六、五向可追溯绑定方案

**根溯源主键**：需求 ID `REQ-{uuid}`，全局唯一，自层2 起贯穿始终。

**绑定节点类型**：

```text
Requirement(REQ) → Function(FUN) → Algorithm(ALG) → FlowNode(FN) → Code(CODE)
                        │                              │
                        └──────── Task(TSK) ───────────┘
```

**绑定边（写入五向绑定存储）**：

- `covers(REQ → FUN)`：需求‑功能覆盖（R̂ 校验项 1）
- `implements(FUN → ALG)`：功能调用的算法组件
- `executes(FUN → FN)`：功能在业务流程中的节点
- `generates(FN → CODE)`：流程节点生成的代码文件/类/函数
- `schedules(FUN → TSK)`：功能对应的定时/异步任务

**查询能力**：任意方向可追溯——

- 给定 `REQ` → 查全部 `FUN/ALG/FN/CODE/TSK`；
- 给定 `CODE`（文件路径） → 反查它服务哪个 `FUN`、归属哪个 `REQ`、带哪个 `Q`；
- 给定 `Q` → 复现其完整拓扑与文档。

**持久化**：SQLite 关系表 + 审计哈希链；向量库额外索引 `REQ` 语义以支持相似匹配。

## 八、关键不变量与验收标准

1. **守恒不变量**：对任意已发布拓扑，`C² − (κ² + τ²) ≥ 0` 恒成立（残差监控报警即失败）。
2. **覆盖不变量**：每个 `REQ` 至少被一个 `FUN` 覆盖（R̂ 强制）。
3. **无环不变量**：业务流程 DAG 不存在环依赖。
4. **可追溯不变量**：每个 `CODE` 可反查到唯一 `REQ`；每份文档可溯源到 `REQ` + `Q` + 审计链。
5. **可复现不变量**：相同 `REQ` + 知识库快照 → 相同 `TopologyBundle` + 文档（忽略 LLM 非确定性处需固定种子/锁定版本）。
