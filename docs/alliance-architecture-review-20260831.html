一、结论摘要

  1. 阻断性：mox-alliance-scheduler-core 编译失败（18 个错误），且上游 mox-alliance-scheduler-svc 因此无法构建 —— 整个"调度→执行"链路目前跑不起来。
  2. 模块级脱节："模块化配置子系统"（mox-alliance-config-core + ConfigSynchronizer + ModularWeightMatcher）是孤儿/未接入状态：config-core 不在工作区成员、无任何 crate 依赖；调度器实际用的是 RuleBasedExpertMatcher 而非 ModularWeightMatcher。
  3. 重复且未接线：存在两套融合引擎（scheduler-core 的占位 FusionEngine 与 mox-alliance-core 的完整策略版），但两套在运行时都没有被 DAG 执行引擎调用 —— 结果只被存储、从不融合。
  4. 工程健壮性缺口：任务/执行状态纯内存（重启即失）、无节点超时与并发上限、默认执行器地址指向自身端口（8081↔8082）、SDK 为全 Stub、多租户未接线。
  5. 健康部分：proto 三件套、api、mox-alliance-core、executor-core、executor-svc 均能编译；专家执行器（ExpertNodeExecutor）超时/重试/健康检查实现完整，是模块内质量最高的部分。

五、逻辑缺陷（能编译但不正确）

六、架构缺口（设计未闭环 / 未接线）

  • 模块化配置子系统整体悬空：ConfigEngine → ConfigSynchronizer → ModularWeightMatcher 链路已实现但调度器运行时（TaskSchedulerImpl）实际使用 RuleBasedExpertMatcher，配置热更新/版本/回滚能力无人消费；config-core 甚至不在工作区成员列表。
  • 融合引擎双套且均未接线：scheduler-core 的 FusionEngine 与 mox-alliance-core 的 FusionEngine 重复实现，但 DAG 执行结果只写入 state.results，从未调用任何融合。融合是全链路关键一环，当前"执行完即止"。
  • 无持久化：任务表、执行状态全部内存态，进程重启全部丢失；无存储抽象/DAO 层。
  • 无节点超时：两套 DAG 引擎的 node_timeout_ms 均未生效，节点挂死会让任务永久卡在 Running。
  • 默认端口错配：scheduler-svc 监听 8081，executor-svc 监听 8082，但 scheduler 的 HTTP 桥默认 base_url = http://localhost:8081 —— 默认配置下调度器把计划提交给了自己，链路必失败。
  • Embedded 模式为 Noop：server.rs 的嵌入式桥接是占位实现，未提供真正可用的进程内路径。
  • SDK 全 Stub：mox-alliance-sdk 三个方法均返回"not implemented"。
  • 多租户未接线：svc 层 tenant_id 统一为 Uuid::nil()，领域层虽有 tenant 概念但未贯通。
  • 接口占位：scheduler-svc list_tasks 恒返回空数组。
