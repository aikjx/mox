四、本轮关键发现（真实运行时暴露，非仅编译层面）

#严重度发现证据根因 / 说明
1严重 专家描述智能匹配失效：无论中文还是英文描述，同一任务（金融/代码/医学）都匹配到同一批 vision/medical/math/code/law 5 个专家，finance 专家永不命中 用中文「金融季度分析」与英文「financial statement analysis…」两个任务实测，节点专家完全一致（5/5 相同） ① 两个匹配器 calculate_description_score 均用 split_whitespace() 切词——中文无空格导致整句变一个词，永不匹配；② 专家描述为中文，英文查询也子串不命中；③ 任务路径从不传 required_domains，领域硬过滤形同虚设。结果：所有专家分数打平，取 HashMap 迭代序前 5。上一轮报告「finance/creative/math/… 匹配」不可复现。
2严重 结果融合未接入执行路径：任务接受 fusion_strategy 参数，但执行完 5 个节点后直接标完成，从不执行融合 executor 节点日志只到 Task ... completed successfully，无任何 fuse() 调用；svc 层 0 处引用 FusionEngine FusionEngine 仅存在于 scheduler-core 进程内 DAG 引擎（Embedded/测试用）与 mox-alliance-core 库。生产 Standalone 路径经 ExecutorBridge → 远程执行器，执行器 dag_engine 无融合步骤。fusion_strategy 存而不用。
3中 LLM 多 Provider 路由未接线：LlmRouter（优先级/轮询/延迟/成本策略 + 熔断降级，626 行）实现完整，但任务路径无任何调用点 全量检索：LlmRouter 仅出现在 llm_router.rs 自身与 lib.rs 重导出，svc/core 运行路径 0 引用 属「已实现未接线」死代码——多 Provider 智能路由、熔断保护在当前任务流中不生效。
4需确认 Expert 模式 = 本地璇玑算法，非外部 LLM 推理：无 LLM Key 时节点 0ms「成功」score=1.000 executor-expert 日志：Expert consult attempt 1/4 后立即 succeeded ... score=1.000, duration=0ms；代码追踪到 ExpertServiceImpl::consult_sync → mox_optimize()（本地 CPU 算法） 「真实专家执行」实际调用本地璇玑优化引擎（14 专家诊断 + 治理闸门），非外部 LLM。若产品预期是 LLM 推理（ReAct 循环/工具调用/AI 流式），则该项未完成，需确认设计意图。
