0总纲与适用范围

本规范是专家联盟体系的企业级基线文档，向上承接技术白皮书与最优架构分析，向下约束代码实现与质量门禁。

0.1 定位

专家联盟（Expert Alliance, EA）是 MOX 平台以"专业模型做专业事"为核心的分布式智能协作体系：多个 AI 专家（架构/算法/安全/性能/测试/数据…）通过统一协议注册、由调度器按 DAG 编排、经辩论与融合产出高质量结果。本规范将这一体系定义为可评审、可测试、可部署的企业级产品基线。

0.2 三大约束

  • 全维分析：对 EA 系统进行 8 维现状诊断（§1），任何决策必须基于证据，禁止"应该/大概"。
  • 全链路模块化：从接入到执行的每一层必须有唯一归属 crate 与清晰边界（§2），杜绝 God Module。
  • 企业级规范标准：命名、接口、错误码、配置、安全、可观测、测试、部署八大规范强制遵循（§3），作为评审/验收唯一标准。

1.1 业务与价值维度

专家联盟的价值主张：效率跃升、知识沉淀、质量保障、能力复用。核心场景是"专家协作 + 知识支撑 + 图谱推理"三位一体。业务判定：专家联盟是平台级 AI 能力中枢，与 KG（知识图谱）、KB（知识库云盘）构成三大能力域，三者必须一体化协作（呼应最优架构分析中的"前端统一工作台 + 后端模块化"结论）。

1.2 架构与技术维度

当前为五层模块化架构（接入 Gateway → 调度 Scheduler → 执行 Executor Pool → 引擎 Engine → 基础 Foundation）+ 三大支撑体系（配置中心 / 注册中心 / 可观测）。全链路六阶段管线：Intent → Team → Debate → Synthesize → Gate → Learn。

现存架构问题（证据来自最优架构分析 + 验证报告）：
  • P0 体验割裂：EA/KG/KB 分散在独立页面，跨模块上下文丢失。
  • P1 代码重复：alliance/kg_connector.rs 与 kg 域重叠；两套流程引擎、两套管线实现。
  • P2 耦合混乱：expert-svc 承担 10+ 职责（God Module 倾向）。
  • P0 测试编译失败：algorithm.rs:694、orchestration.rs:416-417 中测试用 BTreeMap::new() 与结构体 HashMap 字段不匹配。
  • P0 前端构建失败：ExpertWorkspaceView.vue 中 kbSearch 重复声明（导入函数 vs 本地 ref）。
  • P1 clippy.toml 使用无效字段 allow/deny/warn，质量门禁无法启用。

1.3 数据维度

三大能力域的数据模型应归一为统一节点-边-对象底座（呼应统一基座层方案）：文件/文档/实体统一为 Node{id,kind,props,blobRef,acl} + Edge{from,to,type,props}，物理层落在单一 OSS 对象池。EA 域新增数据：专家元数据、任务/会话、DAG 计划、融合结果、学习沉淀。

归一化方向：专家、任务、图谱实体、云盘文件同属"节点"，统一 ID 空间与统一查询原语（GET/FILTER/TRAVERSE/RANGE）覆盖全部访问模式，避免三套存储三套索引。

1.5 安全与合规维度

  • 凭证安全：所有 API Key / 密码通过环境变量引用，配置只存变量名，不存真实值；配置中心加密存储 + 权限管控。
  • 权限体系：RBAC 贯穿全链路；模块间数据隔离、租户级策略管控（复用 mox-rbac-engine）。
  • 审计：全链路审计日志（复用 mox-audit），专家调用、任务执行、配置变更可追溯。

1.6 性能与弹性维度

资源特性差异显著：图谱算法 = CPU 密集，文件上传 = IO 密集，AI 推理 = GPU 密集，扩容策略必须分离。专家联盟服务按域独立扩缩；SSE 流式输出全链路执行状态；gRPC 调用开销约 0.1–0.5ms/次，对 30s+ 的 AI 协作任务可接受，换来独立部署/故障隔离/技术选型自由。

1.7 可观测与运维维度

可观测体系 = Trace + Metrics + Logging 三位一体（复用 mox-platform-observability）。每次任务携带 trace_id 贯穿六阶段；每阶段可追踪、可度量、可审计；SSE 输出每阶段执行详情，支持实时调试与事后分析。

1.8 演进与治理维度

演进方向：更多专家类型、自动 Prompt 优化、AutoML 调参。治理要求：新增专家 = 实现 Trait + 注册 Factory + 加配置，核心代码零改动；统一基座层（mox-base-*）承接 KG/KB/EA 三域的数据与算法收敛。

2全链路系统模块化

明确每一层的唯一归属 crate、模块边界与通信协议，让"全链路"可落地、可追踪、可评审。

2.1 模块化设计原则

  • 模块独立配置：每个 AI 模块独立 LLM 配置、Graph 配置、参数集，互不干扰。
  • 即插即用：专家模块统一协议注册，支持热插拔，新增专家零改动核心代码。
  • 动态编排：基于 DAG 的任务编排，按任务特征动态组队。
  • 全维可观测：每阶段可追踪、可度量、可审计。
  • 隔离与安全：模块间数据隔离，租户级策略，RBAC 贯穿。
  • 弹性扩展：无状态服务水平扩展，CPU/IO 密集模块独立扩容。

2.2 五层架构与唯一归属

层职责归属 crate（域）
接入层 Gateway协议转换 REST/gRPC/SSE/WS、鉴权、限流、追踪、路由mox-platform-gateway-svc + 各域 api
调度层 Scheduler意图识别、专家匹配、DAG 编排、SLA 监控mox-alliance-scheduler-core / -svc
执行层 Executor Pool架构/算法/安全/性能/测试/数据专家mox-alliance-executor-core / -svc

基础层 Foundation配置中心、注册中心、记忆服务、审计日志mox-alliance-config-core / -boot-config + mox-rbac-engine + mox-audit

2.3 六阶段全链路管线（业务级）

2.4 统一基座层对接（衔接统一基座方案）

在 platform/domains/base/ 新增统一基座域，EA 域通过实现 Trait 方式接入，依赖方向单向：域 → mox-base-* → mox-cloud-* 物理口。

mox-base-query-core（统一查询）专家匹配查询 / 知识关联查询统一入口
mox-base-graph-core（图遍历）专家能力图谱、协作关系可视化复用遍历算法

mox-base-lifecycle-core（生命周期）任务/会话/版本/GC 统一管道

2.5 模块间通信协议

  • 对外：REST（管理面）+ SSE（任务流式执行）+ gRPC（服务间高性能调用）+ WebSocket（实时协作）。
  • 对内：同域内本地调用（Trait 抽象），跨域 gRPC；事件总线用于跨能力协调。
  • 协议分流：CPU 密集（图谱算法）与 IO 密集（文件上传）按域独立部署，本地调用优化。

3.5 配置规范

  • LLM 配置：primary_provider/model、fallback_chain、routing_strategy（priority/round_robin/latency/cost）、model_config 全项可动态更新。
  • Graph 配置：engine_type（neo4j/relgraph/custom/in_memory）、连接参数环境变量引用、查询超时/分页/缓存策略。
  • 密钥铁律：API Key/密码一律环境变量引用，配置中心只存变量名；支持加密存储与灰度发布/回滚。

3.6 安全规范

  • 认证：网关统一鉴权（JWT/OAuth2），SSO 复用 mox-enterprise-core。
  • 授权：RBAC + 字段级可见/可写 + 自动脱敏（复用 mox-rbac-engine / DataMasker）。
  • 隔离：模块间数据隔离、租户级策略、跨域调用最小权限。
  • 审计：全链路审计日志，专家调用/任务执行/配置变更可追溯。

3.9 部署规范

  • 独立服务：scheduler-svc / executor-svc 独立部署，按资源特性独立扩容。
  • 灰度发布：配置中心支持灰度/回滚；服务级灰度发布粒度细。
  • 优雅启停：停止接收新请求 → 等待处理中请求完成 → 释放资源 → 注销 → 退出。
  • 健康检查：L5 集成层 4 能力健康检查 + 汇总 + 历史趋势。

3.10 文档规范

  • 所有公开 Trait/方法必须有文档注释；crate 有 lib.rs 文档注释。
  • 新增专家必须随附能力模型、配置示例、测试用例。
  • 架构变更必须同步更新本规范与白皮书，保持单一事实来源。
