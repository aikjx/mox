## 开发专家联盟 · 第十轮：治理闸门专项（P1 拆解 + 3 处真实缺陷修复）

报告：`reports/architecture/alliance-governance-gate-round10-20260906.md`

### P1 原描述不成立，真正缺陷在别处

round6 留的 P1 是「mox_optimize 治理闸门在 LLM 模式下被绕过，前置/旁路/降级待用户拍板」。
查证后**三个选项都不对**：`mox_optimize(&FlowGraph, &GovernContext)` 需要图结构，
而专家咨询入参是一句自然语言，**前置治理物理不可行**；且前置也挡不住输出违规
（无法预知模型说什么）。LLM 场景唯一正确的治理位置是**后验**。

真正的缺陷是 `ConsultReport.vetoed` 契约（文档写「veto=true 时下游应强制拦截」）
在唯一消费方 gateway 被无视。

### 修复的 3 处（gateway + ai-expert-svc）

**D1 拦截契约被无视**（gateway `map_report_to_answer`）：
vetoed=true 时 analysis/solution 正文照常返回，只把标志透传给前端。
修复：拦截时不输出被否决正文，回执拦截说明 + reason，confidence 归零，加 `blocked: true`。

**D2 被否决内容污染融合**（gateway `fuse_answers`）：
按 match_score 选 dominant_view 时不看 vetoed，被否决的高分回复会成为主导方案。
修复：先过滤 vetoed 再算权重；全否决时整体拦截而非给伪结论。

**D3 否决标志本身不可信**（ai-expert-svc `parse_veto`）：
兜底是全文裸子串 `contains("否决")||contains("不可行")||contains("无法处理")`。
「方案 A 不可行，建议改用方案 B」→ 命中 → vetoed=true。
这类「否定旧方案 + 给更好替代」恰恰是最有价值的回答。
**若只修 D1/D2 不修 D3，强制拦截会把它们全吞掉 —— 修复反而造成可用性回归。**
修复：改为「整体否定」强模式表（方案不可行/该方案不可行/无法给出/建议否决/不予采纳…）。
`"方案 A 不可行"` 不含连续串 `"方案不可行"`，故不命中；`"该方案不可行"` 命中。
取向：**宁可漏报（用户仍看到内容），不可误报（正常回答被拦截）**。

### 自身踩坑（值得记住）

`fuse_answers` 首版过滤后仍写 `answers[dominant_idx]`，但 dominant_idx 是过滤后
`admitted` 的下标 —— **下标空间不一致**，会错位取到原数组其他专家。
表现为「静默给出错误专家结论」，不崩溃不报错，只有断言 dominant_view 内容才能发现。
教训：**过滤类改动必须配套断言「结果内容」的测试，只断言结构/数量抓不到下标错位。**

## 开发专家联盟 · 第十一轮：gateway 代码质量与未接线能力盘点

报告：`reports/architecture/alliance-gateway-quality-round11-20260906.md`
`cargo check -p mox-platform-gateway-svc` warning **25 → 10**，测试 **113 passed / 0 failed**。

### 分类处置（关键：不能一律清零）

- **13 处未使用 import** → 删（纯噪音）
- **1 处重复公式**（rate_limit）→ 重构去重。`new()` 算出 max_tokens/refill_rate 后从未用，
  `check()` 又把同一公式写一遍。**注意 `cargo fix` 的默认处理是加 `_` 前缀**，
  那是把「算错了地方」变成「故意不算」，重复仍在 —— 必须手工收敛到 `bucket_params()`。
- **3 处未接线能力** → 保留 warning + 文档注释写明状态（不删、不加 allow）：
  1. `workspace.rs::save_workspace_history`：history 只读不写，无追加调用点
  2. `misc.rs::save_misc_data`：tasks/projects 只有 `.lock().clone()` 读取，无 CRUD
     （性质是**功能未接线，不是数据丢失** —— 无写入即无可丢失）
  3. `experts_dispatcher.rs::dispatch_task(task_type)`：不参与调度，匹配只靠 input 关键词
- **7 处 never read 字段** → **一个都不动**：多为 `#[derive(Deserialize)]` 请求体字段
  （如 `ConsultBody.context/priority`），删掉后客户端照常传参、服务端**静默丢弃**，
  不报错不 400，是最难排查的破坏类型。

### 方法论（与第九轮 norm_fusion 同型）

编译器 dead_code / unused_* 告警**先分类再动手**：
- 指向请求/响应体字段 → 极可能是契约，不动
- 指向「语义上应该被调用」的函数 → 未接线信号，接线或标注，不要删
- 指向重复计算 → 重构去重，别让工具加 `_` 掩盖
- 只有纯未使用 import 适合直接删

`cargo fix --lib --allow-no-vcs` 可安全批量清 unused import（25→10 主要靠它），
但**改动后必须 git diff 审查**，它也会把变量改成 `_` 前缀掩盖问题。
