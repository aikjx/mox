# 2026-09-15

## 联盟域接口—功能对账（第 13 轮）

对 `platform/domains/alliance` 13 crate 做了「trait 契约 → 实现 → HTTP 端点」三层对账。

### 对账结论
- `TaskScheduler`(9方法) / `DagEngine`(9方法) / `ExpertMatcher`(4方法) / `ExecutorBridge`(6方法)
  四套契约与实现、端点**一一对应**，pause/cancel/resume 经 ExecutorBridge 转发到
  executor-svc，链路闭合。
- 发现并修复 `DagEngine` 契约缺 `get_fusion_output`：该能力原先只作为固有方法挂在
  具体类型 `DagEngineImpl` 上，`Arc<dyn DagEngine>` 取不到融合结果，违反域内 DIP 原则。

### 修复要点（重要经验）
**给 trait 补方法时，若返回类型定义在实现层，必须先把类型下沉到协议层**，
否则协议层无法声明该方法，两步缺一不可。
- `FusionOutput` 从 `executor-core/fusion.rs` 下沉到 `executor-proto/dag_engine.rs`
- Rust 陷阱：`use` 引入默认私有，在私有模块里 `pub use X` 会被外部视作
  "private struct import"（E0603），改由 lib.rs 直接 `pub use proto::FusionOutput` 转出

### 发现的最大未接线项（未删，仅标注）
`scheduler-core` 内有一套**完整但零生产调用**的平行实现：
`dag_engine.rs`(981行) + `fusion.rs`(809行)，与 executor-core 同名能力重叠。
模块文档却宣称是核心能力 → 已加「未接线（历史遗留）」标注防误接。
删除 1790 行属不可逆破坏性改动，去留待架构决策。

注意：`scheduler_core::FusionOutput` 与 `executor_proto::FusionOutput` 字段同名但
**类型不同**，且前者未实现 `Serialize`，不可混用。
