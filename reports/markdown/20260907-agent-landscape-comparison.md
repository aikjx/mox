# MOX 与主流 Agent 方案：全维度证据对照

检索与本地检查日期：2026-09-07。结论：MOX 尚无证据被称为全领域最佳或最终版本。适合定位为正在收敛的、可自主管理的企业知识与任务执行平台。

## 方法与限制

本报告是官方公开能力与本地代码/验收证据的对照，不是竞品实机测评。没有运行相同任务、相同模型、相同成本预算的多平台实验，因此不提供虚构排名、准确率或综合分。覆盖代表性产品类别，不能穷尽全球所有 Agent。官方文档证明能力有公开支持，不证明实际部署必然达到宣传效果。

MOX 是应用基础设施与领域系统的组合，不是自行训练的基础模型。应分别比较模型能力、运行框架、产品体验和企业运营；不能把语言性能等同于智能水平，也不能把一个开源 SDK 与另一家完整云服务的功能数量直接打分。

## MOX 本地证据

- 既有目录扫描：143 个 workspace crate、71 个 Vue 页面；这些是代码规模，不是成熟度或任务完成能力。
- 2026-09-07 重跑统一架构门禁：FAIL，P0=0、P1=2、P2=10。网关扇出 10、编排宿主扇出 15 被现有规则标为 P1。机器记录：[最新检查](../data/agent-comparison-architecture-20260907.json)。
- 上一轮代码整理验证了 43 条顶层路由及子路由定义等价；前端完整构建受 Vite 缺失及依赖锁不一致阻塞。这不是当前所有页面已通过验收的证明。
- SDK 蓝图归一化、动态 SQL/流程安全、领域适配器与模块启动契约有代码和局部测试；不能外推为全平台租户隔离、持久审计或跨进程恢复已验收。
- 仓库《生产就绪度评估》包含 90.15 分自评，但本次没有建立其统一评分依据与可重复测试链。该分数不能用于对外宣称超过竞品。
- 现有 README 关于其他框架无法服务化、MOX 唯一同时具备相关能力的表述过强；下列公开部署能力直接说明“只能嵌入 SDK”的对比前提不成立。

## 代表性方案对照

| 方案/类别 | 官方可确认的能力 | 对 MOX 的意义与比较边界 |
|---|---|---|
| OpenAI Agents SDK | Agent、工具、交接、护栏、会话与追踪 | 借鉴小而清晰的运行时接口；本身不是完整企业业务平台。[官方文档](https://openai.github.io/openai-agents-python/) |
| Claude Agent SDK | 提供构建在 Claude Code 能力之上的代理开发接口 | 借鉴实际工具工作循环与执行环境；模型依赖、部署和许可须单独评价。[官方文档](https://code.claude.com/docs/en/agent-sdk/overview) |
| LangGraph | 按步骤持久化检查点，支持人工介入、状态恢复与调试 | MOX 必须证明进程中断后的恢复语义，单有内存状态不够。[持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence) |
| Microsoft Agent Framework | .NET/Python、多种协作模式、开发与托管集成 | 适合比较企业应用集成与开发体验；AutoGen/Semantic Kernel 的演进不宜重复算为独立领先者。[官方仓库](https://github.com/microsoft/agent-framework)、[整合说明](https://github.com/microsoft/autogen/discussions/7066) |
| Google ADK | 多 Agent 工作流及开发、评估工具体系 | 比较测试和部署闭环，而不只是 DAG 节点数。[官方文档](https://adk.dev/)、[评估文档源码](https://github.com/google/adk-docs/blob/main/docs/evaluate/index.md) |
| CrewAI | Crews/Flows；AMP 提供部署、监测与扩展 | 不能再归类为只能嵌入进程；应比较角色协作收益和生产运营成本。[Flows](https://docs.crewai.com/concepts/flows)、[AMP](https://docs.crewai.com/enterprise/introduction) |
| LlamaIndex | 数据与工具驱动的 Agent 构建体系 | MOX 图谱应以检索、证据质量和权限过滤证明收益。[官方 Agent 文档](https://developers.llamaindex.ai/python/framework/understanding/agent/) |
| Strands + AWS AgentCore | 模型无关 SDK；运行时、记忆、身份、工具及观测服务 | 框架与云运营产品分开比较；MOX 自部署可控性与自运维成本需同时计入。[Strands](https://github.com/strands-agents/sdk-python)、[AgentCore](https://aws.amazon.com/bedrock/agentcore/faqs/) |
| Dify | 可视化流程，组合模型、检索、工具、代码、人工审核；发布应用/API/MCP 工具 | 是 MOX 产品层和低代码体验的直接对照之一。[官方能力页](https://www.dify.ai/workflows) |
| Coze Studio | Agent、工作流、知识库、插件、数据库及自部署 | 不能把自部署或一体化作为 MOX 独有能力；社区版与商业版不能混算。[官方仓库](https://github.com/coze-dev/coze-studio) |
| n8n | AI 与业务连接器组合，支持人工审批 | 比较外部系统接通成本和失败后的处理体验。[官方能力页](https://n8n.io/ai/) |
| OpenHands | 软件开发代理及沙箱执行 | 编码场景需单独比较补丁正确性、测试与环境隔离。[官方 FAQ](https://docs.openhands.dev/overview/faqs) |
| Cursor / Codex | 面向软件工程的成品 Agent | MOX 目前不能凭平台模块量宣称编码能力更强；需要同仓同任务评测。[Cursor](https://cursor.com/docs/agent/overview)、[Codex](https://openai.com/codex/) |
| Manus | 面向用户的任务与产物工具，包括浏览器、研究和内容生成入口 | 比较用户交付结果与操作成本，不能把应用页面数量视为等价能力。[官方产品页](https://manus.im/) |
| Salesforce Agentforce | Salesforce 业务平台内的 Agent 与企业应用集成 | 垂直业务上下文及既有系统集成是竞争维度；其云产品与 MOX 源码不是同交付物。[官方介绍](https://trailhead.salesforce.com/content/learn/modules/introduction-to-agentforce/get-to-know-agentforce-functionality) |

## 全维度判断

下表中的“待验证”是当前证据状态，不等于代码完全不存在。

| 维度 | MOX 当前可据实判断 | 建议验收指标 |
|---|---|---|
| 模型推理 | 取决于接入模型、上下文与任务环境，没有自有模型领先证据 | 同模型任务完成率，另设各产品最佳配置组 |
| 规划与任务分解 | 有专家编排结构，缺少统一真实任务对照 | 分解有效性、无效步骤、重新规划成功率 |
| 工具执行 | 有工具与领域接口，生态覆盖和一致语义待测 | 工具成功率、错误参数率、权限拒绝正确率 |
| 多 Agent 协作 | 调度/执行分工已存在，收益未量化 | 相对单 Agent 的质量增益、延迟及成本增幅 |
| 长任务恢复 | 有执行状态相关代码，跨进程恢复验收不足 | 杀进程、重启、超时、重复消息后的结果 |
| 幂等与补偿 | 数据基线与部分机制存在，不等于外部副作用都幂等 | 重复提交不重复执行，部分失败可补偿 |
| 人工审批与取消 | 需要全链路验证 | 挂起持久化、审批身份、取消传播、恢复权限重验 |
| 短长期记忆 | 有图谱/会话能力，正确记忆管理待验收 | 来源、过期、删除、冲突更新、越权检索测试 |
| RAG 与图谱 | 组合能力是潜在差异点 | 普通 RAG/图谱增强消融实验，事实与引用正确率 |
| 动态 SQL 与流程 | 已有实现及局部测试，是业务集成基础 | 参数/权限/发布版本/事务一致性端到端验证 |
| 租户与字段权限 | 存在相关模块，不能等同全平台隔离 | 跨租户负向测试、字段泄漏、缓存与日志隔离 |
| 提示注入与沙箱 | 不能由 JWT 或 Rust 内存安全推导已解决 | 恶意文档/工具返回、网络外传、文件越界测试 |
| 凭据与供应链 | 需要独立治理证据 | 密钥轮换、最小权限、依赖扫描、制品来源 |
| 模块边界 | 已有分层与 SDK 收敛，门禁仍失败 | 无环、可替换适配器、契约兼容、独立构建 |
| 可观测与评估 | 指标和测试存在，缺任务质量统一评测 | trace 贯通、结果评分、回归集、失败可定位 |
| 性能 | Rust 是实现选择，不是全链路性能结论 | 同负载 p50/p95、吞吐、内存、冷启动 |
| 成本 | 没有公平 TCO 对比 | 每个成功任务的模型、算力、运维与人工成本 |
| 部署与灾备 | 有启动/部署文件，不等于灾备可用 | 空机复现、升级回滚、备份恢复、恢复时间与数据损失 |
| 多模型与协议 | 应区分接口兼容和行为兼容 | 不同模型工具调用、流式、错误及协议兼容测试 |
| UI 与易用性 | 路由已拆分，完整构建仍有环境阻塞 | 新用户首次完成时间、无协助成功率、无障碍与移动端 |
| 生态与文档 | 已建源码目录，连接器广度不能宣称领先 | 接入工时、稳定契约、示例复现、升级指南 |
| 合规与许可 | 不能由源码结构或自评得出合规认证 | 数据地域、保留删除、许可清单、审计证据 |
| 商业效果 | 未提供持续使用与付费验证数据 | 用户留存、真实节省工时、业务错误率、支持成本 |

## 建议的收敛架构

统一用户入口 → 任务应用服务 → 持久任务运行时 → 可替换模型/工具适配器 → 领域核心与数据。身份授权、预算、审计和评估贯穿调用链。

确定性流程与模型自主决策使用不同执行语义，共用任务身份、状态、事件和权限契约。编排层只协调步骤，不能同时承担模型提供方适配、图谱算法、商城逻辑和 UI 数据拼装。跨进程网络调用必须有超时、错误语义和重试边界。

不应把“全部业务写入动态 SQL”当成最终归一化目标。适合声明式的 CRUD、校验和流程可以数据库化；复杂算法、外部副作用、权限边界及补偿逻辑仍需明确领域代码。也不应为追求层数而继续增加无独立职责的 crate。

优先把“专家联盟：提交任务 → 执行 → 审核 → 查看结果”做成可重复交付、可恢复、可追责的完整产品链路，再扩展领域。模块数量增长不是首要目标。

## 公平对照实验方案（尚未执行）

建议建立 100 个固定任务：知识问答 25、数据/流程操作 25、专家协作 20、故障恢复 15、安全隔离 15。保留独立测试集，避免只对演示样例优化。

框架组控制模型版本、工具权限、输入数据、硬件、调用预算与超时；成品组比较各自完整交付方案，单独披露配置、价格与限制。每个任务重复至少 3 次，输出置信区间与失败样例。质量评判由明确结果断言、证据核验和盲评结合完成，不只依赖模型自评。

记录端到端成功率、无人工修复成功率、错误成功上报率、权限违规率、恢复成功率、p95 延迟及每成功任务成本。性能和价格必须同时包含模型与外部工具成本。安全关键失败不能被综合平均分抵消。

达到明确业务场景的领先，需要 MOX 在相同边界下拿出可重复结果；“全球所有 Agent 最好、最终最强”不是现有证据能支持的结论。
