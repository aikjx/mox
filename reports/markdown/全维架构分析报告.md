## 一、执行摘要

### 1.1 系统定位

「关图 / 璇玑」是一个以**算子统一治理**为核心的企业级平台，采用 Rust（Axum + Tokio）模块化单体后端与 Vue 3 + Element Plus 前端架构。后端设计了 **6 层 8 域 DDD 矩阵**，实际落地为 **12 个业务域、127 个 crate**；前端包含 **68 个页面、27 个组件、9 个 composable、7 个 Pinia store、17 个 API 模块、约 444 个 API 导出函数**。

### 1.2 核心发现



| 维度          | 状态   | 关键结论                                                                                                  |
| ----------- | ---- | ----------------------------------------------------------------------------------------------------- |
| **架构设计**    | 中高   | DDD 分层理念完整，crate 矩阵宏大，但大量 crate 为空壳 /stub，实际可运行代码集中在网关 + KG/KB/Alliance/IAM 四个域                       |
| **接口覆盖**    | 中低   | 网关原生实现约 **148 个端点**，前端调用约 **444 个 API 函数**，大量前端请求通过反向代理转发到编排器（:3001）/ PrimiFlow（:8000），原生覆盖率约 **33%** |
| **鉴权安全**    | 低    | 迁移期 7 个路径前缀绕过认证（含 /api/system、/api/security），JWT 密钥硬编码，CORS 全开放，前端 dev 环境默认令牌 `dev-secret-token`      |
| **持久化**     | 低    | 仅 IAM 域使用 SQLite 文件持久化（22 表）；监控告警规则、联盟任务状态、会话等核心数据均为内存存储，重启即丢失                                        |
| **测试覆盖**    | 极低   | 前端仅 3 个测试文件，后端单元测试集中在网关配置层，无集成测试 / E2E 测试，无 CI/CD 流水线                                                 |
| **Mock 治理** | 中高风险 | 生产代码中存在多处 mock / 硬编码数据（AdminMonitor、AllianceTaskView、ExpertPlazaView、useWorkspaceData 等），部分已注释但残留引用   |
| **可观测性**    | 中    | 网关实现了日志环形缓冲（4096 条）、Actuator 管理面（12 端点）、Prometheus 指标占位，但分布式追踪未启用（tracing\_enabled: false），无告警通知通道    |

### 1.3 综合评分

**企业级成熟度综合得分：2.3 / 5.0**（处于 "可运行但未生产就绪" 阶段）

### 1.4 Top 3 紧急风险



1. **认证绕过 + 硬编码密钥**：7 个路径前缀在生产配置中仍为公开，JWT secret 为默认值，前端 dev 令牌可直接使用

2. **内存存储单点故障**：监控告警规则、联盟任务、会话状态无持久化，进程重启全部丢失

3. **接口覆盖率不足 + 代理依赖**：67% 的前端 API 依赖外部编排器 / PrimiFlow 代理，网关原生能力无法独立支撑前端

### 2.5 路由结构分析

**路由模式**：Hash 模式（`createWebHashHistory`），不利于 SEO 但部署简单。

**路由守卫**：



* `beforeEach`：白名单放行 → Token 检查 → 权限加载 → `requiresPermission` 校验 → `requiresRole` 校验

* `afterEach`：滚动复位 + 导航历史记录（localStorage，最近 20 条）

* `onError`：动态模块加载失败自动刷新

**路由元信息（meta）**：



* `title`：页面标题（自动拼接 "・璇玑系统"）

* `requiresAuth`：是否需要登录

* `requiresRole`：角色校验（如 `['admin']`）

* `requiresPermission`：权限码校验

* `quickNav`：快捷导航配置（工作台 / 图谱 / 知识库页面）

* `backTo`：返回按钮配置

**问题**：



1. 所有路由集中在单文件（592 行），无按域拆分

2. 大量兼容重定向路由（/expert → /expert-workspace，/plugins → /workflow/plugins 等共 12 条）

3. 404 兜底直接重定向到 /dashboard，无专门 404 页面

### 2.7 API 层封装分析

**核心实例（http.js）**：



* baseURL: `/api`（开发走 Vite 代理，生产直连）

* timeout: 30s

* 拦截器链：请求拦截（Token 注入 + X-Request-Id + project\_id 自动注入）→ 响应拦截（信封解包 + 错误归一化 + 自动重试）

**信封解包策略**（双格式兼容）：



* 新格式：`{code: 0, message, data}` → 返回 `data`

* 旧格式：`{success: true, data}` → 返回 `data`

* 失败：统一 reject 带 `[code]` 前缀的 Error

**自动重试**：



* 幂等请求（GET/HEAD/OPTIONS）：网络错误 / 502/503/504 自动重试 2 次

* 指数退避 + 随机抖动（避免惊群）

* 非幂等请求需显式 `_retryOnPost: true`

**错误归一化**：



* 优先取响应体 `error/message/detail/title`

* 缺失时按 HTTP 状态码映射中文提示（14 种状态码）

* 401 始终弹提示 + 广播 `mox:auth-failed` 事件

* 503 / 超时 / 网络错误分级提示（error/warning）

**多实例工厂**：`createHttpInstance(baseURL)` 支持管理面（`/actuator`）与业务面（`/api`）分离。

**亮点**：API 层设计企业级水准，拦截器、重试、错误归一化、项目 ID 注入均有完整实现。

**问题**：



1. `alliance.js` 使用 `export function` 风格，其他模块使用 `export const` 箭头函数风格，不统一

2. 开发环境默认令牌 `dev-secret-token`（生产禁用，但代码中保留）

3. 无请求取消的全局管理（仅提供 `withCancel` 工具函数）

4. 无请求去重 / 缓存机制

### 2.8 错误处理机制

**三层错误处理**：



1. **全局拦截器**（http.js）：统一归一化 + ElMessage 通知

2. **路由守卫**（router/index.js）：权限加载失败 `console.warn` 后继续（不阻断）

3. **组件级**：参差不齐，部分使用 try/catch，部分依赖全局拦截器

**问题**：



1. 组件级错误处理不统一，大量页面直接 `await apiCall()` 无 catch，依赖全局 ElMessage

2. 无错误边界（ErrorBoundary）组件，组件渲染错误会白屏

3. 无错误上报机制（Sentry 等），前端错误仅 console

4. 路由权限加载失败后静默继续，可能导致越权访问

#### 3.2.3 DDD 6 层 8 域矩阵完整性

设计目标为 **6 层（L0 Foundation / L1 Gateway / L2 Core / L3 Svc / L4 Sdk / L5 Api）× 8 域（ai/cloud/data/flow/kg/market/platform/voice）**。

**实际落地偏差**：



| 维度       | 设计  | 实际            | 偏差                                                  |
| -------- | --- | ------------- | --------------------------------------------------- |
| 业务域数     | 8   | 12            | 新增 alliance/base/project/foundation 4 域             |

| 每域 svc 层 | 8   | 10 域有 svc     | base/foundation 无 svc（纯 core 层）                     |
| 每域 sdk 层 | 8   | 5             | ai/base/foundation/kg/market/platform/project 无 sdk |
| proto 层  | 未设计 | 4 域有          | ai/alliance 有 proto，设计中未包含                          |

**结论**：DDD 矩阵为**理念指导而非严格约束**，实际 crate 划分更偏向按功能聚合，6×8 矩阵的完整度约 **40%**（48 个理论格子中约 19 个有实际 crate）。

### 3.4 中间件架构

**中间件分层（由外到内）**：



```
请求 → 可观测中间件（日志+指标+API启停拦截）

&#x20;    → CORS（allow\_origin=Any, allow\_methods=Any, allow\_headers=Any）

&#x20;    → 限流（令牌桶：100 req/min + 20 burst，按 IP 追踪）

&#x20;    → 认证（JWT Bearer + X-API-Key，7 个路径前缀白名单绕过）

&#x20;    → 路由分发（axum 具体度匹配）

&#x20;    → 业务处理

&#x20;    → 响应
```



| 中间件  | 实现文件                  | 状态 | 问题                                        |
| ---- | --------------------- | -- | ----------------------------------------- |
| CORS | tower\_http::cors     | ✅  | `allow_origin(Any)` 全开放，生产环境风险            |
| 限流   | rate\_limit.rs        | ✅  | 内存令牌桶，多实例部署不共享；无分布式限流                     |
| 认证   | auth.rs               | ⚠️ | JWT 验证 + API Key，但 7 个前缀绕过；JWT secret 硬编码 |
| 可观测  | actuator.rs + o11y.rs | ⚠️ | 日志环形缓冲（4096 条）+ 指标占位；无分布式追踪               |
| 请求追踪 | http.js（前端）           | ✅  | X-Request-Id 注入，但后端未透传 / 记录               |

### 3.5 错误处理体系

**统一错误类型**：`mox-error` crate 提供域编码错误体系（如 KG01001 / AI02099 / PL00999），支持错误域、错误级别、HTTP 状态码映射。

**统一响应格式**（`mox-api-protocol` crate）：



```
// 成功

{ "code": 0, "message": "ok", "data": \<T> }

// 失败

{ "code": <非0>, "message": "<错误描述>", "data": null }
```

**网关实际使用**：



* System/Security/Alliance/KG/KB 域：使用 `ApiResponse<T>` + `ok()/err()` 辅助函数

* 部分 handler：直接返回 `Json(serde_json::Value)`，绕过统一协议

* L0 health：直接返回 `Json(json!({...}))`，无 code 字段

**问题**：



1. 响应格式不统一：`{code, message, data}` vs `{success, data}` vs 裸 JSON 三种并存

2. 错误码体系（mox-error）定义了但网关 handler 大量使用字符串错误消息，未使用域编码

3. 无全局错误捕获层（axum 的 `IntoResponse` 转换分散在各 handler）

4. HTTP 状态码使用不规范：大量错误返回 200 + body.code != 0，而非 4xx/5xx

### 3.6 持久化方案



| 数据域                                                  | 存储方案         | 持久化 | 说明                                          |

| Alliance 联盟任务                                        | 内存           | ❌   | scheduler-core 进程内状态，重启丢失                   |
| Monitor 告警规则                                         | 内存           | ❌   | `Vec<AlertRule>` 内存存储，无持久化                  |

### 3.7 配置管理

**配置来源优先级**：



1. CLI 参数（`--bind` / `--port`）

2. 环境变量（`MOX_GATEWAY_HOST` / `MOX_GATEWAY_PORT` / `ORCHESTRATOR_URL` / `PRIMIFLOW_URL`）

4. JSON 配置文件（`GatewayConfig::from_file()`，已实现但未在 main.rs 中调用）

* RateLimit：enabled / max\_requests(100) / window\_secs(60) / burst(20)

**问题**：



1. `from_file()` 已实现但未使用，main.rs 直接 `GatewayConfig::default()`

2. JWT secret 硬编码为 `"change-me-in-production"`

3. 无配置热加载

4. 无环境区分（dev/staging/prod）

5. 密钥管理无方案（API Key 明文存储在 SQLite）

## 七、归一化规范（企业级标准化）

### 7.1 统一 Error 态规范

**目标**：所有 API 调用失败时有一致的用户体验和开发者处理流程。

#### 7.1.1 标准处理流程



```
// 标准模式：三要素 = ElMessage.error + error 状态 + 错误空态

const { data, error, loading } = useAsync(() => api.fetchList())

// 模板中

\<template>

&#x20; \<div v-loading="loading">

&#x20;   \<ErrorEmpty v-if="error" :message="error.message" @retry="fetchList" />

&#x20;   \<DataTable v-else :data="data" />

&#x20; \</div>

\</template>
```

#### 7.1.2 规范要求



| 要素     | 规范                                          | 反模式                                               |
| ------ | ------------------------------------------- | ------------------------------------------------- |
| 全局通知   | 拦截器统一 `ElMessage.error(msg)`，组件内**不再重复调用**  | 组件内 `catch(e => ElMessage.error(e.message))` 重复提示 |
| 错误状态   | 每个异步操作必须有 `error` ref，类型为 `Error \| null`   | 只用 `try/catch` 不保存错误状态，无法展示空态                     |
| 错误空态   | 使用统一 `<ErrorEmpty>` 组件，含：错误图标 + 错误消息 + 重试按钮 | 空白页面 / 仅 console.error/ 用 `v-if="!data"` 误判为空数据   |
| 静默请求   | 可选 / 降级请求传 `{ silent: true }`，拦截器不弹全局提示     | 所有请求都弹提示，聚合请求时刷屏                                  |
| 401 处理 | 拦截器统一广播 `mox:auth-failed`，auth store 监听后登出  | 组件内各自判断 401 跳登录页                                  |
| 错误上报   | 全局错误边界捕获渲染错误，拦截器捕获 API 错误，统一上报              | 仅 console.error，无上报                               |

#### 7.1.3 ErrorEmpty 组件规范



```
\<!-- components/common/ErrorEmpty.vue -->

\<template>

&#x20; \<el-empty :description="message" class="error-empty">

&#x20;   \<template #image>

&#x20;     \<el-icon :size="48" color="#F56C6C">\<Warning />\</el-icon>

&#x20;   \</template>

&#x20;   \<el-button type="primary" @click="\$emit('retry')">重新加载\</el-button>

&#x20; \</el-empty>

\</template>
```

### 7.2 统一 Loading 态规范

**目标**：数据加载时有一致的视觉反馈，避免页面闪烁和重复点击。

#### 7.2.1 指示器选择



| 场景            | 推荐方案                                 | 实现                                                               |
| ------------- | ------------------------------------ | ---------------------------------------------------------------- |
| 页面级数据加载       | `v-loading` 指令                       | `<div v-loading="loading">...</div>`                             |
| 表格 / 列表局部加载   | `v-loading` + `element-loading-text` | `<el-table v-loading="loading" element-loading-text="加载中..." />` |
| 首屏加载（>500ms）  | 骨架屏 `<SkeletonLoader>`               | 列表 / 卡片 / 详情页使用对应骨架                                              |
| 按钮提交          | `:loading` 属性                        | `<el-button :loading="submitting">提交</el-button>`                |
| 全屏操作（导入 / 导出） | `ElLoading.service()`                | 全屏遮罩 + 进度文本                                                      |

#### 7.2.2 规范要求



1. **禁止裸 await**：所有 API 调用必须关联 loading 状态，禁止 `await api.call()` 后无任何加载指示

2. **防抖延迟**：`v-loading` 显示延迟 ≥ 300ms（避免快速请求闪烁），使用 `nextTick` 或自定义指令

3. **按钮防重复**：提交按钮必须绑定 `:loading`，loading 期间禁止再次点击

4. **骨架屏使用场景**：首屏列表数据、详情页字段、卡片网格；**不用于**：弹窗内小表单、下拉选项加载

5. **loading 状态命名**：`loading`（列表加载）/ `submitting`（表单提交）/ `exporting`（导出中），禁止用 `isLoading` / `showLoading` 等不一致命名

### 7.3 统一 Empty 态规范

**目标**：无数据时提供清晰的空状态引导，而非空白页面。

#### 7.3.1 标准空态组件



```

\<el-empty&#x20;

&#x20; :image-size="120"

\>

&#x20;     {{ emptyAction.label }}

&#x20;   \</el-button>

&#x20; \</template>

\</el-empty>
```

#### 7.3.2 空态文案规范



| 场景     | 描述文案             | 操作按钮            |
| ------ | ---------------- | --------------- |
| 列表无数据  | "暂无数据"           | "新增 X"（如有新增权限）  |
| 搜索无结果  | "未找到匹配结果"        | "清空筛选"          |
| 权限不足   | "暂无访问权限"         | "联系管理员"（跳转 403） |
| 加载失败   | "加载失败，请重试"       | "重新加载"          |
| 首次使用引导 | "还没有 X，点击下方按钮创建" | "立即创建"          |

#### 7.3.3 规范要求



1. **禁止空白**：任何列表 / 表格区域无数据时必须展示 `<el-empty>`，禁止 `<div v-if="data.length">...</div>` 后无 else

2. **区分空态类型**：数据为空 vs 加载失败 vs 权限不足，使用不同图标和文案

3. **提供操作引导**：空态应包含可操作按钮（新增 / 重试 / 清空筛选），而非仅静态文案

4. **表格空态**：`<el-table>` 自带空态，但需统一 `empty-text` 文案，复杂空态使用 `#empty` 插槽

### 7.6 响应格式归一化

#### 7.6.1 统一响应信封

**所有 HTTP 端点必须返回统一格式**：



```
// 成功

{

&#x20; "code": 0,

&#x20; "message": "ok",

&#x20; "data": { ... }

}

// 失败

{

&#x20; "code": 40001,

&#x20; "message": "用户不存在",

&#x20; "data": null

}
```

#### 7.6.2 规范要求



| 规则        | 说明                                                                     |
| --------- | ---------------------------------------------------------------------- |
| `code`    | 业务状态码，`0` = 成功，非 0 = 失败。使用 mox-error 域编码（如 KG01001），禁止使用 HTTP 状态码作为业务码 |
| `message` | 人类可读消息，成功为 `"ok"`，失败为中文错误描述                                            |
| `data`    | 业务数据，失败时为 `null`，无数据时可省略（`skip_serializing_if`）                        |
| HTTP 状态码  | 成功返回 200，客户端错误返回 4xx，服务端错误返回 5xx。**禁止**错误返回 200 + body.code != 0       |
| 分页响应      | `data` 内统一为 `{ list: [], total: 0, page: 1, pageSize: 20 }`            |
| 列表响应      | 无分页时 `data` 直接为数组 `[...]`                                              |

#### 7.6.3 前端解包规范



```
// 拦截器统一解包，业务代码直接拿到 data

// http.js 已实现：code === 0 → return data，code !== 0 → reject

// 业务代码：

const userList = await userApi.fetchList()  // 直接拿到数组
```

### 7.7 错误处理归一化

#### 7.7.1 后端统一错误类型



```
// 所有 handler 必须返回 Result\<T, ApiError>

// ApiError 统一转换为 HTTP 响应 + 统一错误信封

pub enum ApiError {

&#x20;   NotFound(String),           // 404

&#x20;   Validation(String),         // 400

&#x20;   Unauthorized(String),       // 401

&#x20;   Forbidden(String),          // 403

&#x20;   Conflict(String),           // 409

&#x20;   Internal(String),           // 500

&#x20;   Domain(MoxError),           // 域编码错误

}

// IntoResponse 实现：统一返回 {code, message, data:null} + 正确 HTTP 状态码
```

#### 7.7.2 前端统一错误处理



| 层级    | 职责                      | 实现                                               |
| ----- | ----------------------- | ------------------------------------------------ |
| 拦截器   | 错误归一化 + 全局通知 + 自动重试     | http.js responseErrorInterceptor                 |
| Store | 保存 error 状态，提供 reset 方法 | `{ error: ref(null), setError, clearError }`     |
| 组件    | 展示 ErrorEmpty，提供重试      | `v-if="error"` + `<ErrorEmpty @retry="fetch" />` |
| 全局边界  | 捕获渲染错误，展示错误页            | `app.config.errorHandler` + ErrorBoundary 组件     |

#### 7.7.3 规范要求



1. **禁止裸 catch**：`catch(e => console.error(e))` 必须保存错误状态或向上抛出

2. **禁止吞错误**：`catch(() => {})` 空 catch 必须有注释说明原因

3. **统一错误消息**：后端错误消息必须中文，前端拦截器已做归一化，组件内不再翻译

4. **错误码透传**：拦截器 reject 的 Error 对象必须携带 `error.status` 和 `error.code`，组件可根据错误码做差异化处理

5. **401 统一处理**：拦截器广播 `mox:auth-failed`，auth store 监听后清除 token 并跳转登录页，组件内不单独处理 401

### 7.8 组件复用规范

#### 7.8.1 通用组件抽取原则



| 抽取条件     | 说明                  | 示例                                    |
| -------- | ------------------- | ------------------------------------- |
| 使用次数 ≥ 3 | 同一组件在 3 个以上页面使用     | DataTable / SearchForm / Pagination   |
| 跨域复用     | 组件不依赖特定业务域          | EmptyState / LoadingState / StatusTag |
| 复杂交互封装   | 交互逻辑 > 50 行，封装后简化页面 | ConfirmDialog / PageHeader            |
| 视觉一致性    | 需要统一样式和行为的 UI 模式    | 表单校验 / 列表筛选                           |

**禁止抽取**：仅使用 1 次的页面专属组件（放 `views/{domain}/components/`），纯展示无逻辑的简单元素。

#### 7.8.2 Props 规范



```
\<script setup>

const props = defineProps({

&#x20; // 必须指定 type + default（如有）+ required（如必需）

&#x20;   type: Array,
```

#### 7.8.3 规范要求



1. **Props 声明**：必须使用 `defineProps` 声明类型，禁止 `$attrs` 透传未声明的 props

2. **Emits 声明**：必须使用 `defineEmits` 声明事件，事件名用 camelCase

5. **样式隔离**：组件样式使用 `<style scoped>`，全局样式放 `styles/` 目录

6. **组件文档**：通用组件必须在文件顶部用 JSDoc 注释说明用途、props、emits、插槽
